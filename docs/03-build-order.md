# KayEdu — Build Order (Phase 1)

> Turns "huge project" into an ordered sequence of buildable milestones. Each milestone is a set of Claude Code sessions with a clear **done** definition. Build the **single-center daily loop first** (that's the value a center pays for); portability and portals follow. Don't jump ahead — later milestones assume earlier ones are solid.

**Legend:** each milestone lists **Goal**, **Build**, **Done when** (its acceptance gate).

---

## M0 — Environment & skeleton
**Goal:** the app runs, connects to Supabase, migrates, and renders a themed shell in AR/EN.
**Build:** scaffold Next.js; add deps; drop in `schema.prisma`, `docs/`, `CLAUDE.md`; `.env`; `prisma migrate dev --name init`; next-intl `[locale]` routing + `ar.json`/`en.json`; base layout with RTL + a placeholder brand color; shadcn init + a few primitives; Prisma singleton (`lib/db/client.ts`).
**Done when:** `npm run dev` shows a themed layout that flips AR(RTL)/EN(LTR) via the locale switch, and the DB has all tables.

## M1 — Identity, auth & tenancy (the backbone)
**Goal:** real users, memberships, center selection, and enforced isolation primitives.
**Build:** Supabase Auth (email/password) + `User` mirror on first login; `Membership`, `Center`, `CenterSettings`; `/select-center` hub; `getTenantContext()`; `lib/db/scoped.ts`; `lib/auth/permissions.ts`; route-group role gates; staff **invite** flow (`Invitation` + accept). Seed one center, one owner.
**Done when:** you log in, land on select-center (or auto-select), enter the center dashboard scoped to it, and a hardcoded test proves a user of Center A cannot load a Center B record by ID.

## M2 — Center configuration / master data
**Goal:** a center can set up its academic + operational reference data.
**Build:** Settings screens for Education Systems (name + base price), Grades (name + system), Subjects (name + grade), Rooms (name + capacity, per branch), Branches, Teacher-Timeout, Card Customization (JSON), default center-cut. Users & Roles (invite/add). All CRUD scoped + audited where sensitive.
**Done when:** a fresh center can be fully configured through the UI with no SQL, and adding a *second* center and configuring it needs zero code changes.
> **Superseded in part.** Education Systems / Grades / Subjects stop being centre-authored at **M13** (a centre picks from the global catalog instead), and the **Branches** screen and per-branch room grouping go away at **M11** when the `Branch` model is retired. This entry stays as the historical record of what M2 built; `00-master-product-spec.md` §4.1 item 10 describes the current shape.

## M3 — People: teachers & students
**Goal:** manage the humans.
**Build:** Teachers (add/edit/deactivate/delete; detail page; teacher block-list). Students (add/edit/delete; `StudentProfile` with parent info + `studentCode`; enrollment view; grade promotion; print ID card + paper). Duplicate-match on register/add. Supabase Storage for avatars + generated ID cards (with QR).
**Done when:** you can register a student once and connect them to the center; a printable QR ID card generates; a teacher can be blocked-list a student; duplicate phone/email triggers match not duplicate.

## M4 — Classes, schedules & session generation
**Goal:** the academic structure and its calendar.
**Build:** ClassGroup CRUD (subject/grade/system/room/price/**center-cut config**/capacity/attendance flags/late threshold/accepts-new/requires-confirmation); ClassSchedule (multi-day); Enrollment (add/remove/block); the **session generator** (rolling window + holiday calendar); teacher/room **conflict** detection.
**Done when:** a class with two weekly slots generates correct future sessions, a room/teacher double-book is prevented/warned, and enrolling past capacity is blocked.

## M5 — The daily loop ⭐ (reception → attendance → payment → receipt)
**Goal:** the beating heart — what a center opens every day. **This is the milestone that sells.**
**Build:** Today's Sessions dashboard (filters). Session detail: enrolled roster + add student (existing/new, drop-in or enroll) + mark attendance (Present/Late/Absent/Excused). **Reception Desk**: search by code/name/phone (+ QR scan), select session, method, status. Payment recording that **freezes the snapshots** via `lib/money.ts` in a transaction. Session receipt (total, center share, teacher share, present/absent, consecutive-absence counts). Void/correct with audit.
**Done when:** all money acceptance tests pass — fixed *and* percentage cuts compute correctly; a recorded payment is unchanged after the class cut changes; a drop-in records attendance+payment with no enrollment; consecutive-absence shows on the receipt.
**Delivered:** all of the above, gated by `npm run check:payments`. QR "scan" is a hardware barcode-scanner-friendly text match on Reception's search box (`lib/id-card.ts`'s `parseStudentQrPayload`), not a camera — no camera code exists in this app. **Not built in M5** (closed at **M10**, tracked below rather than here): session cancel/reschedule/edit (docs/02 §11); consecutive-absence surfaced on the student profile page (session receipt only for now); a per-class "Excused" toggle (all four statuses are offered on every class).

## M6 — Analytics, expenses & the Center Dashboard
**Goal:** owners see the money and the trends.
**Build:** Analytics with date filters + by-teacher (total revenue, center share, teacher share, expenses, net, averages; students total/new, teachers total/active/new) — **all read from frozen snapshots**. Expenses (categories + entries + filters). Receptionist is denied profit views. **The Center Dashboard also lands here** (spec §4.1 item 1) — it was never assigned to an earlier milestone (M1 shipped only a placeholder with people-count stat cards) and needs exactly the revenue/attendance aggregation queries this milestone builds, so `/dashboard` and `/analytics` both call `lib/db/analytics.ts` with different date-range defaults (today vs. day/week/month/year/all) instead of duplicating the math.
**Done when:** analytics numbers reconcile exactly with the underlying payment snapshots for any date range, and a receptionist cannot reach profit by UI or URL. **Delivered:** the above, gated by `npm run check:analytics` — reconciliation across an in-range/out-of-range date split, by-teacher `groupBy` correctness, and cross-center isolation on every analytics/expense query, plus a direct assertion that RECEPTIONIST holds neither `analytics.center.view` nor `expense.manage` (grantable or not). **Not built in M6** (tracked as a fast-follow, not silently dropped): the Approvals screen referenced by spec §4.1 item 9 doesn't exist yet — **built in the Approvals milestone**, below — so at M6 the Dashboard's "outstanding operational items" still surfaces only today's not-yet-started sessions.

## M7 — Teacher portal (cross-center)
**Goal:** the portability payoff for teachers.
**Build:** teacher dashboard with **center switcher**; combined + per-center schedule; sessions (search/filter, detail, print, edit description within deadline); students (search, per-teacher history); analytics per visibility; request new class/session (`ChangeRequest`) → center **Approvals** screen; block student.
**Done when:** a teacher shared by two centers sees a correct combined schedule and earnings, each scoped to that center's granted visibility, with **zero** cross-center leakage (the flagship acceptance test).
**Delivered:** teacher dashboard (`/teacher/dashboard`) — combined KPI row (centers, sessions today/this week, earnings this month) plus one card per center, each computed by its own centerId-scoped query (`lib/db/teacher-portal.ts`'s `teacherCenterSummary`) and only unioned in memory (`combineTeacherSummaries`), never a query spanning centers; the "center switcher" is the existing `/select-center` cookie flow, reused as-is. Sessions (`/teacher/sessions`, `/teacher/sessions/[id]`) — search by student, filter by date/status/grade, roster/attendance as a read-only view (marking attendance/payment stays a center-staff action), absent count with the consecutive-absence alert, earning + center earning (always shown here — this is the teacher's own session, a different thing from the center-staff `center.profit.view` gate), print (`/teacher/sessions/[id]/print`), and an unconditional description edit (`updateDescription`, pinned to `centerId` **and** `teacherId`). Students (`/teacher/students`, `/teacher/students/[id]`) — search by code/name/phone narrowed to students this teacher has an attendance record with (`teacherStudentProfileIds`), detail shows only sessions attended **with this teacher** (`studentSessionsWithTeacher`), and reuses the `StudentBlock` scope TEACHER mechanism from M3 with `refId` always resolved server-side from `ctx.user.id` — never a client-sent teacher id. Classes (`/teacher/classes`) — a request form (subject, grade, timing, capacity, attendance settings) writes a `ChangeRequest` (type `NEW_CLASS`) and lists the teacher's own past requests. Upload files for sessions is a "coming soon" placeholder card on the session detail page, per spec. Gated by `npm run check:teacher-portal` (`scripts/teacher-portal-check.ts`) — the flagship shared-teacher, two-center, zero-leakage scenario, plus a regression check that a shared teacher's block at one center does not carry to the other.
**Not built in M7** (closed at **M10** except where noted, tracked below rather than here): the **Approvals** screen that would review a `ChangeRequest` — still missing, as flagged at M6, and **built in the Approvals milestone**, below; this milestone only added the write path (`scoped(ctx).changeRequests`) and a teacher's own "my requests" list, so at M7 a request sat `PENDING` with no reviewer yet. A dedicated, filterable-by-grade **Analytics** screen (spec §4.2 item 1: "total earnings, total sessions, unique students attended") — the Dashboard's combined/per-center summary covers the same ground at a coarser grain; `/teacher/analytics` stays a disabled nav placeholder, **still not built at M10** (a deliberate scope call, see M10 below). A **teacher edit-deadline** setting for session descriptions — closed at M10. A **"trusted teacher"** flag — closed at M10. **Request new session** (`ChangeRequest` type `NEW_SESSION`, spec §4.2 item 2) — closed at M10.

## M8 — Student portal & discovery/reservation (fast-follow)
**Goal:** students self-serve; the network layer switches on.
**Build:** student schedule (past/future, detail); **Discover** (browse published offerings with filters); reserve/enroll with teacher validation (auto-accept vs confirm) → `Reservation`; my reservations; capacity/duplicate handling.
**Done when:** a student reserves a class, the center/teacher confirms per rule, and the class appears in the student's personal schedule across connected centers.
**Delivered:** `/student/schedule` (upcoming from active enrollments + past from `SessionAttendee` history, unioned per center via `getStudentContexts`, read-only, filterable by date); `/student/discover` (marketplace grid across every active center, docs/04 §10, subject/grade/day filter pills, subject-accent top border, status badge, teacher avatar+local-name, price via `lib/format.ts`, respecting `acceptsNewStudents` and both `StudentBlock` scopes); `/student/reservations` (a student's own PENDING/CONFIRMED/REJECTED/CANCELLED requests across every center, with a cancel action on their own PENDING ones). The write path (`lib/db/reservations.ts`'s `reserveOrEnroll`) branches on `ClassGroup.requiresConfirmation` exactly as specified — instant enroll writes an ACTIVE `Enrollment` directly with no `Reservation` row at all; confirmation-required writes a PENDING `Reservation`, reusing the same row across a reject/re-request cycle rather than erroring on the `(classGroupId, studentId)` unique constraint. A brand-new sign-up with zero relations anywhere can still reach Discover and make their first reservation/enrollment — `requireStudentUser()` (`lib/auth/tenant.ts`) is a looser gate than `requireExperience`, requiring only a signed-in `User`; `/select-center`'s empty state now links to Discover as the way out of what was previously a dead end for a self-registering student (docs/02 §4). Gated by `npm run check:student-portal` (`scripts/student-portal-check.ts`) — instant-enroll vs. requires-confirmation branching, capacity enforcement (checked at request time for instant-enroll, deferred to confirm time for requires-confirmation), duplicate-reservation/duplicate-enrollment prevention, both `StudentBlock` scopes, and the shared-teacher-style cross-center isolation scenario.
**Not built in M8** (tracked as a fast-follow, not silently dropped): the **Approvals** screen a confirmation-required reservation needs — still missing at M8, flagged at M6, M7, and now here a third time, and **built as its own small milestone right after this one**, below. `confirmReservation`/`rejectReservation` (`lib/db/reservations.ts`) are real, transaction-safe, capacity/block-rechecking functions with full gate coverage, but at M8 nothing in the product UI called them yet. Discover's subject/grade filters match on center-local master-data *names*, not ids, and are applied to the full combined result set in the application layer rather than pushed into each center's database query (docs/02 §14) — fine at Phase 1's pilot scale, a deliberate simplification to revisit if the platform grows past a handful of centers.

## Approvals (landed as its own small milestone between M8 and M9)
**Goal:** close the reviewer-UI gap flagged at M6, M7 and M8 — a `ChangeRequest`/`Reservation` sitting `PENDING` forever with nobody able to accept or decline it. Never assigned to a milestone number of its own in this document until now; small enough that it doesn't warrant renumbering M9/M10.
**Build:** `/approvals` (OWNER/MANAGER only, `approvals.manage`) — a combined queue of every PENDING `ChangeRequest` (type `NEW_CLASS`) and every PENDING `Reservation` at the active center. Accept/decline for both entity types, each audited.
**Done when:** accept/decline on both entity types changes status correctly, is audited, and is denied to a role without the right permission; Center A staff cannot see or act on Center B's pending requests.
**Delivered:** the queue described above, plus the decision record spec §4.1 item 9 now carries: accepting a `ChangeRequest` **flips its status only** — `lib/db/approvals.ts`'s `resolveChangeRequest`, a plain PENDING→APPROVED/DECLINED transition that refuses to re-resolve an already-resolved row — it does **not** auto-create a `ClassGroup`, because the request payload has no price/center-cut/room for staff to have decided yet (CLAUDE.md rule 2: never guess at money). Staff create the real class manually at `/classes`, reading the approved request's subject/grade/day/time/capacity/attendance details off the Approvals card. Accepting a `Reservation`, by contrast, immediately calls M8's `confirmReservation` (creates the `StudentProfile` if needed + an ACTIVE `Enrollment`) since a reservation already has everything an enrollment needs. Every accept/decline writes an `AuditLog` row (`changeRequest.approve`/`changeRequest.decline`/`reservation.confirm`/`reservation.reject`) — the first gate script in this codebase to assert on `AuditLog` shape at all. Gated by `npm run check:approvals` (`scripts/approvals-check.ts`) — both entity types' accept/decline, the no-ClassGroup-side-effect assertion, audit-row shape, RECEPTIONIST denial (mirroring M6's `analytics.center.view`/`expense.manage` pattern), and cross-center isolation on the pending queue and on each accept/decline call.
**Not built** (tracked as fast-follows, not silently dropped): **contact** and **edit-and-confirm** (spec §4.1 item 9's fuller "accept/decline/contact/edit-and-confirm") — only accept/decline exist; a manager cannot message a requester or adjust a request's details before confirming it from this screen. **Punted at M10 too, deliberately**: "contact" would need a messaging/thread entity that doesn't exist anywhere in this app — notifications are explicitly deferred (spec §2), and building one just for this one screen is new infrastructure beyond a hardening milestone's scope. "Edit-and-confirm" has no obvious shape for either entity as the data model stands today: a `Reservation` doesn't carry fields worth editing before confirming (the student's choice of class is exactly what confirming acts on), and a `NEW_CLASS` `ChangeRequest`'s missing fields (price/cut/room) are precisely the ones CLAUDE.md rule 2 forbids guessing at — "edit" would mean designing a new class-creation flow embedded in this screen, not a small addition. Revisit if a real center asks for either. `ChangeRequest` type `NEW_SESSION` **is now built** (M10) — see M10 below; the queue shows both `NEW_CLASS` and `NEW_SESSION` requests, in separate sections. No smart "prefill a new class from this approved request" convenience on `/classes` — staff re-type what they already see on the Approvals card.

## M9 — Super Admin (platform)
**Goal:** operate the platform safely.
**Build:** create/activate/suspend center tenants; plan/onboarding metadata; controlled privileged support access (audited); platform KPIs (active centers/teachers/students, sessions, adoption); global reference data where appropriate.
**Done when:** a new center tenant can be provisioned end-to-end from the admin panel, and privileged access to tenant data is logged.
**Delivered:** `/admin/centers` — `createCenterAction` provisions a Center + its CenterSettings row + a founding-Owner `Invitation` in one nested write (`lib/db/platform.ts`'s `createCenterWithSettings`), mirroring how `configureCenter` provisions a fresh center's config at M2 (no per-center branching); the invite link is shared manually, reusing `/settings/staff`'s exact mechanism, because a brand-new center otherwise has no member who could ever reach that screen to invite a first owner. The list shows every tenant with staff/teacher/student counts (`platformCenterList`, one `groupBy` per role-bearing relation rather than fetch-and-count) and an activate/suspend toggle (`setCenterActiveAction`). `/admin/centers/[id]` adds a `Center.plan` editor (free text, not a billing system — the schema column is a loose string) and per-center stats, and writes an `AuditLog` row (`platform.support.access`) on every visit — the "controlled privileged support access" the spec asks for, deliberately just an audited read-only view rather than a full masquerade/impersonation system. `/admin/platform` — active/suspended center counts, total teachers, total students, total sessions, and an adoption trend (centers created per month, last six months, read as a plain table rather than a chart), every figure through an aggregate/`groupBy`/`count` in `lib/db/platform.ts`, the same "never fetch-and-sum" discipline M6 established. **Global reference data** — nothing concrete needed it yet at Phase 1 scale, so nothing was built for it, per the milestone's own "where appropriate." Gated by `npm run check:admin` (`scripts/admin-check.ts`) — center creation/activation/suspension/plan-edit through the real production functions, platform KPIs reconciled as a delta (they are deliberately not `centerId`-scoped — a platform admin spans every tenant by design), per-center list/detail stats reconciled exactly, and every support-access view asserted to write exactly one audit row with the expected shape.

## M10 — Hardening, QA & pilot-readiness
**Goal:** trustworthy enough to run a real center.
**Build:** run **all 15 acceptance scenarios** as automated + manual tests; performance pass on rush attendance; audit coverage; backups + tested restore; error monitoring; data import (onboarding) + export (offboarding); privacy review for minors' data; seed a realistic demo center for meetings.
**Done when:** every acceptance criterion in `00-master-product-spec.md` §7 passes, and one real center can run a day of live sessions in a preview environment.
**Delivered:**

*Acceptance criteria (spec §7), automated vs. manual.* Cross-referencing all 15 against the nine milestone gates that already existed found genuine gaps at only the two the task brief predicted — **14 (performance)** and **15 (RTL)** — plus one narrower gap inside an existing gate: **8 (attendance correction is audited)** was checked for permission denial (`check:config`) but never for the actual `AuditLog` write, since that write lives inline in the Server Action rather than in a `lib/db/*` function a gate could import. Closed by reproducing the exact write `setAttendanceAction` performs (`payments-check.ts`, the same pattern `approvals-check.ts` already used for its own audit assertions) and asserting its shape/scoping. New gates: `npm run check:performance` (`scripts/rush-performance-check.ts`) — not a browser benchmark (CLAUDE.md rule 1), it validates the actual risk docs/02 §14 flags: asserts `connection_limit` is set, times a serial vs. concurrent batch of real `createAttendance`+`recordPayment` calls, and asserts the concurrent batch beats naive serial extrapolation (proof the pool grants real concurrency) while every write still lands correctly under the rush (no lost/duplicate rows, revenue reconciles exactly). `npm run check:rtl` (`scripts/rtl-check.ts`) — static-only, for the same reason: en/ar key parity across all ~1,090 translation keys, a scan for physical-direction Tailwind utilities anywhere under `app/`/`components/` (found zero), a scan for inline `toLocaleString` calls outside `lib/format.ts` (found zero), and confirmation the root layout wires `dir`/`lang` from the locale. The other 13 criteria were already covered: 1/2 by `check:teacher-portal`/`check:student-portal`'s shared-teacher/shared-student no-leak scenarios, 3/4/5/13 by `check:payments`, 6/7 by `check:classes`, 9 by `check:analytics`'s permission-map assertion, 10 by `check:isolation`, 12 by `check:people`'s duplicate-match coverage — 11 (cancelled session) was the one real gap in this group, closed below.

*Flagged gaps, resolved.* **Session cancel/reschedule** (spec §7 criterion 11, the docs/02 §11 note this build order carried since M5): `lib/db/sessions.ts`'s `cancelSession`/`rescheduleSession`, a `session.cancel`/`session.manage`-gated UI on the session detail page. Cancelling never touches attendance/payment rows (CLAUDE.md rule 2) — a payment that needs undoing stays `voidPayment`'s separate, explicit, audited job. Rescheduling re-runs the generator's own `findSessionConflicts` (WARN/DENY per the center's `scheduleConflictPolicy`) and refuses a same-class duplicate slot. **Consecutive-absence on the student profile page** (M5's other flagged gap): the student detail page now shows a per-class "absent N times in a row" alert for every active enrollment with a live streak, using the same `consecutiveAbsenceCount` the session receipt already called. **Per-class Excused toggle**: `ClassGroup.allowExcused` (default `true`, matching the pre-M10 "always offered" behavior), a settings checkbox, and a server-side refusal (`excusedNotAllowed`) everywhere EXCUSED could be submitted — the roster's `AttendanceControl` also hides the button when the class disallows it. **Teacher edit-deadline**: `CenterSettings.teacherEditDeadlineHours` (`null` = no deadline, the M7 default), a General Settings toggle mirroring the teacher-timeout pattern, enforced in `updateSessionDescriptionAction`. **Trusted-teacher flag**: `Membership.isTrustedTeacher` (default `true`), a toggle on the teacher's profile form, gating both request forms (`changeRequest.create` is necessary but not sufficient — see docs/02 §6). **`ChangeRequest` type `NEW_SESSION`**: a teacher requests a one-off session on a class they already teach (`/teacher/sessions`'s new request card); unlike `NEW_CLASS`, the request's `ClassGroup` already has a decided price/cut, so `lib/db/approvals.ts`'s `resolveSessionRequest` creates the `Session` immediately on approval — no money to guess at, the `confirmReservation`-style "approve == act" shape, not the "approve == status flip" one. **Punted, deliberately** (see the Approvals section above for the reasoning): **contact** and **edit-and-confirm** on the Approvals screen — no messaging entity exists anywhere in this app, and neither entity type has an obvious "what would you edit" shape without inventing a new flow.

*Pre-deployment checklist (spec §2.1), worked as far as reasonable pre-pilot.* **B (data & tenant security):** real RLS policies and a `rls_auto_enable()` lockdown are drafted in `supabase/m10-rls-and-storage.sql` — deliberately **not** auto-applied by any migration command, since this is security-sensitive SQL against a live Supabase project; it needs a human review-and-run. The same file provisions the `logos/`/`session-uploads/` buckets the checklist still listed as missing. **C (operations & pipeline):** `.github/workflows/ci.yml` wires `prisma migrate deploy` and all twelve `check:*` gates (plus typecheck/lint/`prisma validate`) into CI — it needs `DATABASE_URL`/`DIRECT_URL` repo secrets pointed at a dedicated CI/staging project before it can actually run; that secret provisioning is a GitHub-side action outside this session's reach. `db:seed` now populates the seeded center with realistic reference data (an education system, 3 grades, 5 subjects, 3 rooms), 4 teachers + a manager + a receptionist, 20 students, 5 classes with schedules, a full rolling session window (via the real `generateSessions`), and 4 weeks of attendance/payment history (via the real `createAttendance`/`recordPayment` — never fabricated numbers) plus a couple of expenses — idempotent, and off with `SEED_DEMO_DATA=false` for the old bare-owner seed. Left open, needing either a product decision or access this session doesn't have: **A** (email confirmation, leaked-password protection and a transactional email sender are Supabase-dashboard/vendor decisions, not code — `SEED_OWNER_PASSWORD` rotation and `NEXT_PUBLIC_APP_URL` are per-environment operational steps), the rest of **B** (service-role key hygiene is already correct in code — never `NEXT_PUBLIC_*` — but is an operational discipline to maintain, not a one-time fix; backups + a tested restore need a live project to test against), the rest of **C** (error monitoring, the cron registration for session generation, and full data import — CSV *export* would have been in-scope-sized but wasn't reached this pass; punting an untested half-feature seemed worse than punting the whole thing cleanly), and **D**'s nav-placeholder sweep (`/teacher/analytics` is the one still-disabled item, a deliberate M7 scope call, not an oversight).

*Performance pass on rush attendance entry.* `.env.example`'s `connection_limit=10&pool_timeout=20` (docs/02 §14) already matched the documented guidance; `check:performance` is what turns "should work" into "does work, measured on this database" — see above.

# Phase 1, part two — M11–M21

> M0–M10 built and hardened the single-centre daily loop. M11–M21 build the decisions settled in `00-master-product-spec.md` §5.1: the organization/branch layer, a real permissions engine, the global academic catalog, money completeness (refunds and settlements), the enrolment and approval rules, parents, ratings, a UX/data-integrity sweep, the visibility window and lifecycle states, then deployment — and, only after the pilot, offline.
>
> **Ordering is not arbitrary.** M11 comes first because every later milestone's scope depends on whether "a centre" means one branch or several. M12 comes second because the permissions engine is what M13–M19 hang their new actions on, and retrofitting a matrix onto nine milestones of hardcoded checks costs far more than building on it. Nothing after M12 should be adding a hardcoded role check.
>
> **Every milestone touching money, permissions or isolation names its `check:*` gate.** That is the same non-negotiable M5/M6 established, extended: a milestone in this range without a gate on its money/permission/isolation surface is not done, whatever the UI looks like.

## M11 — Organization / branch restructure
**Goal:** an organization is the paying customer and a centre is one branch under it, **without changing how isolation works**.
**Build:** the `Organization` model (global, no `centerId`); `Center.organizationId`; **retire the `Branch` model** — drop `Room.branchId`/`Session.branchId`, rooms and sessions belong to the centre directly. Owner memberships resolve **org-level** (every branch); Manager/Receptionist/Accountant resolve to exactly one branch; **teacher memberships unchanged**. Navbar **branch switcher** ("Whole Management" vs. one branch), reusing the existing `/select-center` cookie flow rather than adding a second switching mechanism. **Org-level analytics roll-up** (one branch or all) as a union of per-branch `centerId`-scoped queries summed in memory. The **i18n naming layer**: UI says "Branch" for `Center`, "Center" for `Organization` (`02-architecture.md` §8) — message keys only, **no code renames**. No branch-count limit.
**Done when:** an organization with two branches shows a correct all-branches roll-up that equals **exactly** the sum of the two per-branch figures; a user scoped to Branch A cannot read a Branch B record by URL or API; and `lib/db/scoped.ts`, `getTenantContext()`'s scoping and `npm run check:isolation` are **byte-for-byte unchanged** in their isolation behaviour.
**Gates:** `npm run check:branches` (new — roll-up reconciliation + branch-A-can't-read-branch-B), and **`npm run check:isolation` must still pass untouched** — that is the load-bearing assertion of this milestone, not a formality.
**Delivered:** the migration (`prisma/migrations/20260906220000_m11_organization_branch_restructure`) backfills one `Organization` per pre-existing `Center` (reusing the Center's own id as the Organization's id — a real 1:1, not a fresh seed) before making `organizationId` `NOT NULL`, then drops `Branch`/`Room.branchId`/`Session.branchId`. **Owner org-level resolution is a read-time widening in `getUserCenterRelations()` (`lib/auth/tenant.ts`), not a schema change to `Membership`** — the alternative the milestone brief offered (a nullable `Membership.centerId` with real org-level Owner rows) was passed over specifically to keep `lib/db/scoped.ts` and every non-Owner code path untouched; see `02-architecture.md` §4 for the full reasoning and its one known gap (an Owner doesn't yet appear in a sibling branch's own staff list — closes with M12's `MembershipBranchGrant`). ## M12 — Permissions engine, ACCOUNTANT, and two security fixes
**Goal:** replace the hardcoded role map and the two boolean grants with a configurable action-level matrix, and close two real leaks while the permission seam is open.
**Build:** the `PermissionGrant` matrix (`centerId × role × action × allowed`) covering every role and effectively every action; **`ACCOUNTANT`** added to the `Role` enum with a baseline of analytics + expenses, configurable thereafter; the `/settings/permissions` matrix screen (**OWNER only**); **cross-branch grants** (`MembershipBranchGrant`) so an Owner may widen a branch-scoped role's reach; removal of `receptionistCanViewProfit`/`receptionistCanCorrectAttendance` and `permissionGrantsFromSettings()`; removal of the unread `Membership.canSeeEarnings`. **Security fix 16** — a centre Owner/Manager viewing a teacher must not see that teacher's other centres. **Security fix 17** — a role or grant change invalidates or re-resolves the session immediately.
**Done when:** deny-by-default holds (an action with no row is denied to everyone, including a newly added one); the **grantable ceiling** holds in code (a TEACHER cannot be granted `center.profit.view` however the matrix is written, an OWNER cannot be stripped of ownership actions); a MANAGER cannot change the matrix, assign a role, or grant a branch — by UI **or** by direct action call; a demoted user's very next request resolves the new role; and a teacher's other memberships are invisible to a centre by UI and by API.
**Gates:** `npm run check:permissions` (new — matrix resolution, deny-by-default, OWNER-only granting, the ceiling, session invalidation, the teacher-detail leak). Every existing gate that asserts a denial (`check:analytics`, `check:approvals`, `check:teacher-portal`) is re-pointed at the matrix and must stay green — if a role silently gains something in the migration, those are what catch it.
**Delivered:** `PermissionGrant` (`centerId × role × action × allowed`) and `MembershipBranchGrant` (`membershipId × centerId`, one row per extra branch) land in two migrations — `20260906223000_m12_accountant_role` adds `ACCOUNTANT` to the `Role` enum on its own (Postgres refuses to use a new enum value in the same transaction that added it), then `20260906224000_m12_permission_matrix` creates both tables, **backfills** `PermissionGrant` rows reproducing the pre-M12 hardcoded map plus whatever each center's two settings booleans had actually granted (OWNER/MANAGER get the old `MANAGER_PERMISSIONS` baseline, RECEPTIONIST its five-action baseline plus `center.profit.view`/`attendance.correct` only where that center had switched them on, `CenterSettings.receptionistCanViewProfit`/`receptionistCanCorrectAttendance` and `Membership.canSeeEarnings`. `lib/db/platform.ts`'s `createCenterWithSettings` (Super Admin provisioning) seeds the ## M13 — Global academic catalog + bilingual names + centre-cut rework
**Goal:** subjects, grades and education systems become platform-owned reference data; the FIXED cut gets its per-system default.

## M14 — Refunds + teacher settlements
**Goal:** complete the money story — money given back, and money paid out.
**Build:** **Refunds** — mark a recorded payment `REFUNDED`, cash back, **no student balance**; the original `Payment` row preserved untouched and a `Refund` record written alongside; analytics **subtracts** the refund from collected revenue **and** from that payment's centre and teacher shares. **Settlements** — `Settlement` (`DRAFT → APPROVED → PAID`, **no partially-paid state**), totals **derived from frozen `teacherShareSnapshot` values and never recomputed**, supporting both a **single session's** teacher share (centres pay cash after each session) and a **period roll-up**; `/settlements` for the centre and `/teacher/settlements` for the teacher. Both permissioned through M12's matrix and audited.
**Done when:** a refund reduces collected revenue and both shares by exactly its amounts, leaves the original row's money fields untouched, and creates no balance anywhere; a settlement's total equals the sum of the frozen snapshots in its scope and **stays correct after the class's cut changes**; and no transition on either is possible without permission or without an audit row.
**Gates:** `npm run check:settlements` (new — refund arithmetic on revenue and both shares, settlement totals derived not recomputed, transition permissions, audit shape). `npm run check:payments` and `npm run check:analytics` must both still pass — this milestone edits the ledger's readers, and those two are what prove it did not edit its history.

## M15 — Approvals, enrolment, capacity, reschedule + teacher centre-directory onboarding
**Goal:** the rules that govern who gets into a class, and what happens when a session moves.
**Build:** centre approves student enrolment requests at `/approvals`; **teachers get their own approvals page** for students joining their classes; requests check **both `StudentBlock` scopes** and refuse when blocked, at request **and** approval time; a **rejected student cannot re-request the same class for 7 days**, with the UI **saying so** when they try. **Capacity:** enrolment **hard-capped by room capacity**, refusing with *"change the room or increase its capacity"*; **session attendance may exceed it** (25 in a 20-seat room is fine); a student may still *request* a full class, but staff cannot manually add or approve past the cap. **Reschedule with linkage:** `Session.rescheduledToId` written immediately; target may be a future date or the same day at a different time; the room must be free for the **entire** start→end window; the same rule whether a teacher or centre staff initiates. **Cancelled-session guard** — close spec §7.1's verified gap: server-side refusal of attendance and payment on a `CANCELLED` session, plus a read-only roster. **Teacher onboarding:** a teacher belonging to no centre gets a **centre directory** (`/teacher/centers`), never the student Discover screen, and can request to teach a session or a class pending that centre's approval.
**Done when:** a blocked student is refused at both request and approval; a rejected re-request inside 7 days is refused **and explained**; enrolment past capacity is refused while attendance past capacity succeeds; a reschedule whose target room is free at the start but busy before the end is refused; a cancelled session refuses attendance and payment **by direct action call**, not just in the UI; and a zero-centre teacher lands on the directory.
**Gates:** `npm run check:enrollment` (new — block scopes at both points, the cooling-off, the capacity split, the full-window reschedule, the cancelled-session refusal). `npm run check:classes` and `npm run check:approvals` extended and still green.

## M21 — (post-pilot) Offline resilience for the reception loop
**Goal:** the desk keeps working when the internet does not — **if the pilot proves it needs to**.
**Precondition: OD-7.** Do not start this before the pilot has measured how often, and for how long, Center 60 actually drops during a rush. Building it speculatively is the worst outcome; discovering the need after the pilot fails is the second worst.
**Cost, stated honestly:** this app has **no client data layer today** — every read is a Server Component, every write a Server Action. Scoped offline means **building one**. Budget for that, not for a feature flag.
**Build:** an IndexedDB queue for the **reception loop only** — check-in, attendance, payment; nothing else. **Graduated behaviour:** full function **0–60 minutes** offline → **block new writes at 60 minutes** rather than accumulating unbounded unsynced money → **never auto-discard the queue**, only a deliberate, audited **Owner** discard. **Design constraints:** the **client never computes money** — a queued item stores **intent only**, and the server computes every snapshot at sync time through the same `lib/money.ts`/`recordPayment` path a live write uses (CLAUDE.md rules 2 and 3 apply to a queued write exactly as to a live one); **every queued action carries a client-generated UUID the server dedupes on**, because a queue that retries must be safe to replay.
**Done when:** a reception session survives a tab close and a 60-minute outage with every write landing exactly once on sync; replaying the same queue twice produces no duplicate `SessionAttendee` or `Payment` rows; **no money value is ever computed on the client** (asserted, not reviewed); and a discard is impossible without an Owner and an audit row.
**Gates:** `npm run check:offline` (new — replay idempotency on the client UUID, the 60-minute threshold behaviour, and a static assertion that no client bundle imports `lib/money.ts`). `npm run check:payments` and `npm run check:performance` must both still pass — this milestone changes how money reaches the ledger, and those two are what prove the ledger itself is unchanged.

## Sequencing notes
- **Demo shell** can be pulled forward: after M0–M1 + a themed M5 with seed data, you have a clickable, brand-swappable demo for owner meetings — even before the deeper milestones are complete.
- **Multi-center** is proven at M2 (config) and M7 (teacher portal), not bolted on at the end — the architecture carries it from M1. **Multi-*branch*** is proven at M11 the same way, and deliberately as an additive layer: `center_id` stays the sole isolation key, so `check:isolation` passing unchanged is the milestone's real acceptance test.
- **Money** is concentrated in M5/M6 and gated hard by tests. **M13, M14 and M21 all touch money again** — the centre-cut rework, refunds/settlements, and the offline queue respectively — and each is required to leave `check:payments` passing unchanged. A milestone that edits money's *readers* must prove it did not edit money's *history*.
- **M11 before M12 before everything else**, and not by preference: every later milestone's scope depends on whether "a centre" means one branch or several (M11), and every later milestone adds actions that must land in the matrix rather than in a hardcoded check (M12). Retrofitting either is far more expensive than sequencing for it.
- **M20 is a gate, not a feature.** It exists so `00-master-product-spec.md` §2.1 stops being a list nobody owns. Two of its items are blocked on open decisions (**OD-1** domain, **OD-4** export scope, `00-master-product-spec.md` §2.2) — resolve those before the milestone starts, not during it.
- **M21 is conditional on evidence** (**OD-7**). It is the only milestone in this document whose first task is deciding whether to build it at all, and the only one that requires building infrastructure (a client data layer) this app has none of.
- Each milestone = one durable Claude Code working session (or a few), starting from `CLAUDE.md` + the relevant doc section, so context cost stays low.
