## 1. What KayEdu is (in one paragraph)

KayEdu is a **multi-tenant, web-based ERP for private education centers** in Egypt, with connected portals for teachers, students and (as of M16) parents. An **organization** — the paying customer — runs one or more **branches**, and each branch runs its daily operations through it: students, classes, sessions, attendance, per-session payments, teacher settlements, expenses, and analytics. Teachers and students each have **one KayEdu identity** that can connect to multiple centers. Phase 1 is the operational foundation; Phase 2 (mobile apps, homework, exams, grades, AI assistance, and everything else in [`05-phase-2-backlog.md`](./05-phase-2-backlog.md)) builds on top of it later and is **out of scope for now**.

## 2. Locked decisions (do not re-litigate without updating this file)

These are settled. They shape the schema and the whole build.

| Area | Decision |
|---|---|
| **Tech stack** | Next.js (App Router) + TypeScript, PostgreSQL via **Supabase** (Auth + Storage + Postgres), Prisma ORM, Vercel hosting (Frankfurt region), shadcn/ui, Tailwind, `next-intl` for i18n. |
| **Tenancy** | **Single shared database**, isolated by `center_id` on every tenant-scoped table. **Not** database-per-center. Adding a center = insert a row + upload a logo, no code changes. |
| **Organization & branches** | An **`Organization`** is the paying customer; a **`Center`** is one branch under it and stays the tenant. `center_id` remains the **sole isolation key** — the org layer adds roll-up and cross-branch role grants, and changes nothing about how isolation is enforced. See §5 "Branch architecture". **Each organization has a branch limit** (`Organization.maxBranches`, default 1) that only a platform admin sets; an Owner adds branches up to it from Settings → Branches, and the admin can add a branch to an existing organization (F1 — OD-12 decided (a)+(b), §5.1). |
| **Naming (UI vs. DB)** | The UI says **"Branch"** where the DB says `Center`, and **"Center"** where the DB says `Organization`. Resolved **entirely in the i18n layer** — a full DB rename is Phase 2 (`05-phase-2-backlog.md` entry 18). |
| **Branding** | Per-center logo, name, and theme color — a **theming layer** separate from data isolation. |
| **Identity** | One global `User` per person. Their relationship to a center is a separate **Membership** (role-scoped). Attendance, payments, enrollments hang off the membership/enrollment, never the raw user. |
| **Permissions** | A **configurable action-level permission matrix** covering every role × every action (§3). Deny-by-default and server-side enforcement are non-negotiable. **Only OWNER** may grant roles or permissions. |
| **Academic catalog** | Subjects, grades and education systems are **platform-owned global catalog** entries, each with an Arabic and an English name. Only a **platform admin** adds, edits, deactivates or deletes an entry (R8 — the M13 suggestion queue is gone: a centre that needs an entry contacts us). Centres pick from the catalog; a centre edits only its own price and its own **display name, one per language**, for a picked entry. Person names stay single-valued and never vary by locale. |
| **Financial model** | **Pay-per-session only.** Recorded at the desk (offline). No online payment gateway in Phase 1. |
| **Center's cut** | Configured on the class as **`PERCENTAGE`** (a percent of the collected amount) or **`FIXED`** (the exact piastre amount of the session price the **centre** takes). Each education system carries a **configurable default fixed centre share** used when a class is set to FIXED, overridable per class and per session. Framed centre-side on purpose — see §5 "Center cut". |
| **Refunds** | **Cash-back only, no student balance.** A recorded payment can be marked `REFUNDED`: the original row is preserved and a refund record is written, permissioned and audited. Void and refund are **different things** (§5). |
| **Teacher settlements** | A settlement/payout record with **DRAFT → APPROVED → PAID** and no partially-paid state, totalled **from frozen snapshots only**. Supports both a single session's teacher share and a period roll-up. **SEC-2b:** a settlement **claims** the payments it counts — a payment belongs to at most one live settlement, enforced by the database — a DRAFT may be **CANCELLED** (releasing its claims), and a non-OWNER never approves or pays a settlement they created (§5.1 "Security decisions (SEC-2b)"). |
| **Data visibility window** | By default **no centre-side role may read data older than 1 calendar month**. Platform admin bypasses; per-centre configurable. A **read restriction, never a deletion**, enforced in the data layer. Settlements and audit logs are carved out. See §5. |
| **Center lifecycle** | `ONBOARDING / ACTIVE / GRACE / SUSPENDED / ARCHIVED`, replacing the `active` boolean. **`Center.plan` is removed entirely** — no plans, no module entitlements. |
| **Student debt** | **Does not exist** in Phase 1. No "owes money" balances. Attend = pay, or not counted. |
| **Prepaid / packages / discounts / monthly subscriptions** | Not in Phase 1. Schema stays flexible so they *can* be added later, but nothing is built for them now. |
| **Drop-in attendance** | Supported. A student can attend a session **once without being enrolled**, or be a regular enrolled student. |
| **Payment methods (recorded, not processed)** | **Configurable per centre (R1).** A new centre starts with Cash, InstaPay and Vodafone Cash; staff add, rename, deactivate or delete methods at Settings → Payment methods. Every payment freezes the method's name at record time (§5.1 "Payment methods configurable per centre"). |
| **Notifications** | **Deferred.** In-app only later; no SMS/WhatsApp cost in Phase 1. The notification layer is designed so WhatsApp/SMS plug in later without rework. |
| **Languages** | Arabic + English, full **RTL** support, from day one. |
| **Check-in methods** | ID card with QR **and** manual search by student code / name / phone. All available. |
| **Class periods & sessions** | *(Revised R4 — was "rolling-window session generation".)* A class has a **period** — a start and an end date — typed by hand or filled from one of the centre's **term presets** (the dates are copied, never linked). Creating a class creates **every session of its period** from today on, one per matching weekly slot, skipping the holiday calendar; editing its slots, period, teacher or rooms re-fits its untouched upcoming sessions. There is no rolling window, no generator and no cron (§5.1 "Class periods and centre terms"). Per-session cancel/reschedule as before. **R5:** staff may also add a session by hand — an **extra session** on a class, or a **one-time session** that belongs to no class — never in the past; the engine never touches a hand-made session (§5.1 "Manual and one-time sessions"). **R6:** the New class dialog takes the class's **weekly rows** and creates the class, its schedules and every session in one step — optionally with a **brand-new teacher in the same transaction** (§5.1 "Creating a class in one step"). |
| **Offline resilience** | No full offline mode in v1. Resilient optimistic UI + retries so a brief internet drop doesn't lose data. A scoped **offline reception loop** is planned **post-pilot** (M21) and only if Center 60's real connectivity justifies it — see the open decision in §2.2. |
| **Deployment gate** | Nothing goes to production until there's a signed contract with the first center. |

### A. Auth & email

- [ ] **Turn on Supabase email confirmation AND set `REQUIRE_EMAIL_CONFIRMATION=true`** (SEC-2a, D-01). *Confirm email* stays **off on dev** until a domain exists (OD-1) so dev accounts sign in instantly, and the app does not rely on it: since SEC-2a an email alone never links a login to a person a centre created — it opens a claim staff approve in person (§5.1 "Security decisions (SEC-2a)"). Production needs both layers: the dashboard toggle (Authentication → Providers → Email → *Confirm email*) so Supabase proves the address, and `REQUIRE_EMAIL_CONFIRMATION=true` so the server also checks `email_confirmed_at` on every email-based link (an invitation, staff linking an existing account). **A production deployment refuses to start with either missing** (`instrumentation.ts` → `lib/auth/production-guard.ts`, `VERCEL_ENV=production` or `KAYEDU_ENV=production`). The code paths exist: sign-up/sign-in without a session show "check your email" with a rate-limited resend, the confirmation link lands on `/[locale]/auth/confirm`. Until both are on, **anyone can register with an email address they do not control** — harmless to staff-created records now, but an account's email proves nothing.
- [ ] **CAPTCHA (Turnstile) on sign-up and sign-in** (SEC-27, deferred from SEC-2a; D-18 kept it at M20 when SEC-2c decided the rest of D-18). The app-side per-email and per-IP limits (`lib/rate-limit.ts`, Postgres-backed) are in place, and since SEC-2c so are the per-account and per-IP limits on reservations, self-enrolment and the teach-here request; a CAPTCHA needs the domain (OD-1) and a Turnstile site key.
- [ ] **Password reset flow** (SEC-66). The auth-confirm route exists; the forgot/reset pages need the transactional email sender below.
- [ ] **Delete the legacy dev auth users that still accept the historical seed password** (SEC-36). Thirteen `auth.users` on the dev project, none linked to an app user, still accept the password that was once committed in git history. Deleting auth users is destructive on a shared project, so it is the person's action (Supabase dashboard → Authentication → Users), not tooling's.
- [ ] **Wire a real transactional email sender** (e.g. Resend) once we own a domain, with SPF/DKIM configured. Today staff invite links are **copy/paste-shared manually** by the inviter (`02-architecture.md` §3, `createInvitationAction` → `InviteForm`), which is correct for Phase 1 and unworkable for a real center inviting a dozen staff. Same sender covers password reset and any future notification use. Note: this is **delivery plumbing**, not the deferred notifications feature (SMS/WhatsApp stay out of scope per §6).
- [ ] **Enable leaked-password protection** in Supabase Auth (HaveIBeenPwned check) — currently off.
- [ ] **Rotate / retire the seeded demo credentials.** `prisma/seed.ts` creates (or resets) real Supabase Auth users — `email_confirm: true`, every one on the reserved domain in **`SEED_EMAIL_DOMAIN`** (default `example.com`), all sharing the one password in **`SEED_PASSWORD`** (required, ≥ 6 characters, no default, never printed) — except the platform admin, whose password is **`SEED_ADMIN_PASSWORD`** (required, ≥ 6 characters, must differ from `SEED_PASSWORD`; D-21, SEC-2a) — for the 23 accounts in `docs/dev-accounts.md` (a platform admin, the owners/managers/receptionists/accountants, teachers, students and parents), so every role can be signed into and tested. It refuses to run against a production project or environment (a committed `PRODUCTION_PROJECT_REFS` list in `prisma/seed-data/production-refs.ts`, plus `VERCEL_ENV`/`KAYEDU_ENV=production` — SEC-70; add the production ref there at M20), and unless `DATABASE_URL`'s project ref equals `DEV_PROJECT_REF`, begins with an Auth preflight (`npm run seed:preflight` runs the same check ahead of the wipe), stamps the accounts it makes with a marker and resets only those — an auth user with a seed address that lacks it is refused, never overwritten — touches no auth user outside its list, and **`npm run db:seed` must never run against production.** Its companion `npm run db:wipe-dev` is fenced the same way (`ALLOW_DEV_WIPE=yes`, matching project ref, a typed confirmation) and is only ever run by the person, never by tooling. The first real owner is provisioned through the admin panel + invite flow (M9), not the seed.
- [ ] **Remove the `noindex`** (F5). While `ALLOW_AUTO_CONFIRM_DEMO` is set (demo data), every page carries `robots: noindex, nofollow` (`noIndexDemo` in `lib/auth/auth-config.ts`, read by the root layout) so seeded branches and teachers are never indexed as real ones. Unsetting the flag at M20 lifts it; confirm the public Explore pages (§4.7) then render without `noindex` before a real centre is listed.

### B. Data & tenant security

- [ ] **Confirm the Data API lockdown on the production project.** *(Rewritten at SEC-2a — the M10 plan of per-tenant policies is dropped, D-19 (a).)* The posture is **deny-all**: RLS on every `public` table, **zero policies**, and no privilege for `anon`/`authenticated` on the schema, tables, sequences or functions, now or through default privileges — a checked-in migration (`prisma/migrations/20261017090100_sec2a_data_api_lockdown`) that `prisma migrate deploy` applies to every project, so a freshly provisioned project is never open to the anon key (SEC-10). The old `supabase/m10-rls-and-storage.sql` is deleted (it aborted on tables that no longer exist and missed fourteen that do — SEC-30).

- [ ] **Service-role key hygiene.** `SUPABASE_SERVICE_ROLE_KEY` lives in the local `.env` for the seed. In production it exists only as a Vercel server-side env var — never `NEXT_PUBLIC_*`, never in a client bundle. - [x] ~~**Create the remaining Storage buckets + policies.**~~ — **Closed at SEC-2a (D-19 (a), D-25 (b)).** The four buckets — `avatars` (1 MB, PNG/JPEG/WebP), `id-cards` (2 MB, the server-generated SVG), `logos` (512 KB, PNG/JPEG/WebP) and `session-uploads` (20 MB) — are created or corrected by the lockdown migration, all **private**. - [ ] **Backups + a *tested* restore**, and a privacy/legal review before handling minors' data (`02-architecture.md` §12). Needs a live project and legal/product sign-off this session cannot provide.
- [ ] **Legal review of retention and erasure for minors' data** (OD-2, SEC-29). The audit log already keeps ids and amounts only (D-20, SEC-2b); what still needs a lawyer is how long a centre keeps a deactivated student's record and how a parent's erasure request is honoured while the money and attendance history stays. Until the rule exists there is no anonymisation routine to build.

## 3. Roles & permissions

**Six roles at Phase 1 kickoff, eight now** — and only some of them are database enum values, which is where the old "six hardcoded roles" wording quietly misled. Two counts exist and both are correct:

- **`Role` (the Prisma enum) = centre memberships only.** `OWNER`, `MANAGER`, `RECEPTIONIST`, `TEACHER`, and — as of **M12** — `ACCOUNTANT`. These are the values a `Membership` row can hold.
- **`TenantRole` (the resolved context type) = the enum plus the two relationships that are not memberships**: `STUDENT` (a `StudentProfile`, not a `Membership`), `PLATFORM_ADMIN` (the global `User.isPlatformAdmin` flag), and — as of **M16** — `PARENT`. This is what `can()` is keyed on (`02-architecture.md` §6).

So: **five membership roles, eight resolved roles.** Whenever a doc says "roles," it means the resolved set unless it names the enum.

| Role | Kind | Scope | Core capability |
|---|---|---|---|
| **Super Admin (KayEdu)** | `User.isPlatformAdmin` | Platform | Create/suspend center tenants, platform KPIs, support, audit, manage the global academic catalog. Never browses tenant data casually. Bypasses the data-visibility window (§5). |
| **Owner** | `Membership` | **Organization** — every branch under it | Full control: money, staff, config, everything a Manager can do + ownership actions. **The only role that may grant roles or permissions**, the only one that may widen another member's branch access, and (F1) the only one that may add a branch to the organization, within the limit a platform admin sets. |
| **Manager** | `Membership` | One branch (unless the Owner grants more) | Runs the branch: teachers, classes, students, sessions, analytics, expenses, config, approvals, delete rights, teacher-edit deadlines. |
| **Receptionist** | `Membership` | One branch (unless the Owner grants more) | Daily ops: reception desk, check-in, record attendance + payment, add students, view today's sessions, **end a session** (`session.close`, R2). **Cannot** see center profit/settlement unless granted. |
| **Accountant** *(M12)* | `Membership` | One branch (unless the Owner grants more) | Baseline: **analytics + expenses**. Everything beyond that baseline is configurable through the matrix like every other role. Deliberately *not* given staff management, class management or attendance rights by default. |
| **Teacher** | `Membership` | One or more centers | Their own schedule, sessions, students, analytics/earnings, request new classes/sessions, block students, approve students joining their classes. Only sees data for centers they belong to. Membership scope is unchanged by the org layer. |
| **Student** | `StudentProfile` | One or more centers | Discover/reserve classes, see personal schedule, enrollments, own attendance history, rate sessions they attended. |
| **Parent** *(M16, F3)* | `FamilyLink` (F3; was `ParentLink`) | One or more children, at whatever centers those children attend — linked by a one-time code, even before the child joins a branch | A child selector plus a per-child mirror of the student portal. Read-only. Never a superset of what the child can see. |

**From hardcoded map to configurable matrix (M12).** Phase 1 shipped a hardcoded `Record<TenantRole, Permission[]>` plus exactly two boolean grant columns on `CenterSettings`. That is replaced by a **stored, action-level permission matrix**: every role × effectively every action in the app, editable per centre. The invariants survive the change unchanged:

- **Deny by default.** An action with no explicit grant is denied. A new action added to the codebase is denied to everyone until someone grants it.
- **Server-side is authoritative.** `can()` on the client only hides controls; the loader/action check is the boundary (`02-architecture.md` §6).
- **Only OWNER grants.** Granting a role, changing the matrix, or widening a member's branch access are OWNER-only actions, and every one of them is audited.
- **Grants widen, never narrow.** A configured matrix cannot hand a role something the platform forbids for that role (a TEACHER can never be granted `center.profit.view`), and cannot be used to strip an OWNER of ownership actions.

**Permission rules that matter:**
- A Receptionist seeing **center profit** is **denied by default**.
- A Teacher sees their **own earnings/analytics by default** — no center grant needed. A teacher's own session earnings are not `center.profit.view`; that distinction is load-bearing and documented in `02-architecture.md` §6.
- Attendance **corrections**, **financial corrections**, **refunds** and **settlement transitions** require elevated permission and are **audited**.
- Teacher's **deadline to edit a session** is set by the center manager (a center setting).
- **Delete** of teachers/students is a Manager/Owner action, not Receptionist.
- **Changing a user's role invalidates or re-resolves their session immediately** (§5, security fix 17) — a demoted user must not keep their old rights until their cookie happens to expire.

> Full permission matrix (action × role) lives in `02-architecture.md` §6. This section is the intent.

Who sees what in it follows §5 "Branch architecture": an **Owner** sees every branch under their organization plus the all-branches roll-up; a **Manager / Receptionist / Accountant** sees the one branch their membership names, or the several the Owner has granted them, and sees the roll-up only when they hold more than one. Selecting a specific branch sets the active `centerId` — the same cookie mechanism that already exists — so every screen below stays exactly as `centerId`-scoped as it is today. The roll-up is **analytics only**; no operational screen ever spans branches.

0. **Auth** — login/register. Owners/Managers/Receptionists are **invited by email**. An older batch can be undone only once every newer one is.

Block/remove student from session. **R2:** a check-in has no status picker — the server sets Present or Late from the arrival time — and staff correct marks from the roster only while the session is live; **End session** (`session.close`) closes it for good, the closed page shows a banner, locks every attendance/payment control and leads with the receipt and its Print button (`/sessions/[id]/print`), and the receipt gains a **"Changes during session"** section (§5.1 "Session lifecycle"). **R5:** a **"New session"** button adds an extra session to a class or a one-time session with no class (its own title, price and cut; everyone a drop-in); the list and detail mark them **"Extra session"** / **"One-time"**, and the detail page offers **Delete** only while such a session is untouched and in the future (§5.1 "Manual and one-time sessions"). **T2 — the session page checks in confirm-then-write, through reception's function.** Picking a student (the roster's **Check in** button, a suggestion in the add-student search, or a candidate row) opens reception's confirm panel (photo, name, code, Enrolled / Drop-in, price, payment method, Cancel / Check in) in a dialog — a full-screen sheet on a phone — and **writes nothing until its confirm button**; Cancel, Escape, closing the dialog or leaving the page writes nothing, and no "pending check-in" is stored on either side. Accepting a `Reservation`, by contrast, **does** immediately act — it calls the same `confirmReservation` (M8) that creates the `StudentProfile` (if needed) and the `ACTIVE` `Enrollment`, because a reservation already carries everything an enrollment needs (an existing `ClassGroup`); there is no missing-data problem to defer. A `NEW_SESSION` `ChangeRequest` (M10) is the same shape as a `Reservation`, not a `NEW_CLASS` one: it names an **existing** `ClassGroup`, which already carries everything a real `Session` needs — price, center-cut, room — so there is nothing left for a center to decide that a `NEW_CLASS` request is still missing. Accepting immediately creates the `Session` (`lib/db/approvals.ts`'s `resolveSessionRequest`), re-running the exact same teacher/room conflict check every slot write uses (`findSessionConflicts`, against every other class's sessions on the requested date; since R4 a deactivated class takes no new session at all) and respecting the center's own `scheduleConflictPolicy` — DENY refuses it outright; **since R3**, WARN refuses it too, with the conflict list, until the approver ticks "I understand, create anyway" (§5.1 "Double-booking needs explicit confirmation"), and the session is created on the class's whole room set — the identical rule `rescheduleSession` (spec §7 criterion 11) applies to a manually-moved session. No money, room, or scheduling decision is ever guessed at here; the only thing "accept" adds beyond a `NEW_CLASS` accept is that there's nothing left to add.

A centre never sees JSON. **Data visibility window** — the per-centre override of the 1-month default (§5). Users & Roles (invite by email or add existing user by email) — **centre staff only (R9)**: Owner, Manager, Receptionist and Accountant. Teachers are added and managed on the **Teachers** page, never here (§5.1 "Users & Roles lists centre staff only").
11. **Teacher settlements (delivered M14)** — the payout register (`/settlements`): a teacher's payable, **derived from frozen `teacherShareSnapshot` values and never recomputed**, as either a single session's share (settled right from the session detail page, next to its receipt) or a period roll-up (a small form on `/settlements`: teacher + date range). `DRAFT → APPROVED → PAID`, no partially-paid state, `settlement.manage`-gated and audited (`settlement.create`/`settlement.approve`/`settlement.pay`). Deliberately visible **outside** the data-visibility window — a teacher must always be able to verify they were paid (§5). `/teacher/settlements` is the teacher's own read-only mirror, unioned across every centre they teach at.
12. **Refunds (delivered M14)** — marking a recorded payment `REFUNDED` (cash back to the student; **no balance is ever created**) via a Refund button on the session roster, right beside Void. The original `Payment` row is preserved untouched and a `Refund` record is written alongside it. `payment.refund`-gated and audited. Distinct from a void — see §5 "Void vs. refund". `/refunds` is the centre's read-only refund ledger.
13. **Settings → Branches (delivered F1)** — **OWNER only** (`organization.branch.create`, an ownership action no matrix row can grant — §3, `02-architecture.md` §6). Shows "**2 of 3 branches used**" against the limit a platform admin sets, every branch of the organization with its lifecycle badge (archived ones listed but not counted), and **Add branch** — disabled with its reason at the limit. The Add branch dialog takes the name (Arabic, required), the name (English, optional), a theme colour (picker + swatches), the timezone (default: the current branch's), and **"Copy setup from <branch>"** (default: the current branch) with six ticks, all on: catalog selections (with the branch's renames and base prices), payment methods, terms, holidays, the permission matrix, and the general settings (default cut, late threshold, conflict policy, visibility window, teacher edit deadline). **Never copied:** rooms, classes, sessions, people, money, the ID-card layout, the logo. The new branch takes the lifecycle state of the branch the Owner acts from; afterwards only the admin transitions it. It is in the branch switcher and on `/select-center` at once (§5.1 "Branch architecture").
    **Branch-aware people adds (F1).** Settings → Staff **Invite** and Teachers → **Add teacher** gain a **Branch** select listing the branches where the actor holds that same permission (`membership.role.assign` for an invitation — OWNER only, D-22 unchanged — and `teacher.manage` for a teacher), hidden when there is only one, defaulting to the active branch. The server never trusts the posted branch: it re-resolves the actor's context there through the ordinary resolution, checks the permission at that branch, and writes scoped to it; the confirmation names the branch when it is not the active one.

## 5. Resolved business rules (Phase 1)

**Identity & duplicates.** One `User` per person, keyed on their **global email** — the login credential, confirmed by Supabase in production. **A phone is not an identity key** until phones can be verified (backlog entry 12; SEC-2a, D-02): nothing links on a phone, and a self-typed phone is never stored on the global `User`. Registering an existing person at a new center creates a **new membership/enrollment**, never a duplicate person. Duplicate-matching + merge is a defined workflow (details in data model).

**Contact details are center-local (revised, M3).** `User.email`/`User.phone` are the person's **global auth credentials** — how they sign in, set once. What a center has on file for a teacher or student (their phone, alt phone, email as *that center* knows them) is a **separate, center-local record** on `StudentProfile`/`Membership`, always editable by that center regardless of whether the person is shared elsewhere. Duplicate-matching on add/register checks **both**: the global `User` contacts and every center's existing local contact record, because a person may have been entered somewhere with a contact that never made it onto their global `User`. No match → create the person (the entered contact seeds the global `User` at that one moment) and the center's own local record. A match → link a new membership/profile to the existing person and write the entered contact as this center's local record only, touching nothing global. Full detail in `01-data-model.md` §6.

**Money — the sacred rules.**
- Charge basis = **one session**. Price comes from the class (or session override).
- The **center's cut** is configured on the class as either `FIXED` or `PERCENTAGE`. Teacher share = collected amount − center cut.
- **Snapshot at payment time.** When a payment is recorded, freeze `price`, `center_share`, and `teacher_share` onto the payment row. **Never recompute historical money from current settings.** If a class's cut changes later, past payments keep their old numbers. **Every rule below leaves this one untouched** — settlements, refunds and the per-education-system default all read or produce snapshots, none of them recompute one.
- No debt: if a student didn't pay, there's no balance — they're simply an unpaid attendee/absent per the roster, with no money recorded.
- Corrections/refunds are permissioned and audited; a correction writes a **new** audit-tracked change, it does not silently overwrite history.

**Center cut — what FIXED actually means (settled).** `PERCENTAGE` is unchanged: the centre takes `round(amount × value / 100)`. **`FIXED` means the exact piastre amount of the session price that the *centre* takes** — a 120 EGP session with `FIXED 15 EGP` yields 15 EGP to the centre and 105 EGP to the teacher. The framing is deliberately **centre-side**, and the alternative framing a teacher sometimes asks for — *"pay me a flat 200 EGP per session regardless of how many students show up"* — **is not expressible in this model and is not supported in Phase 1.** It cannot be: the teacher's share is derived per payment from what a student actually paid, so a headcount-independent flat fee has nothing to derive from when two students turn up instead of twenty, and would require a per-session teacher payable that exists whether or not anyone paid. That is a second financial model (a guaranteed fee, with the centre absorbing the shortfall), not a configuration of this one. If a centre needs it, it is a Phase 2 conversation with its own snapshot rules — not something to approximate by setting `FIXED` and hoping the headcount holds.

**Per-education-system default fixed share.** Each education system carries a **configurable default fixed centre share** — e.g. American 40 EGP, IGCSE 50 EGP — used as the **default** when a class's cut is set to `FIXED`. It is **overridable per class and per session**. It is a default at configuration time only: it seeds the class's `centerShareValue` and is never consulted again at payment time, so changing a system's default never moves a class already configured, let alone a payment already recorded. The split math itself stays in exactly one place (`lib/money.ts`, CLAUDE.md rule 3).

**Void vs. refund — two different things, and both now exist.** These were conflated in earlier drafts ("corrections/refunds" as one phrase). They are not the same event and must not share a mechanism:

| | **Void** | **Refund** |
|---|---|---|
| **What happened** | The payment should never have been recorded — wrong student, wrong session, wrong amount, fat-fingered entry. | The payment was correct and the money is now being given back to the student, in cash. |
| **Effect on the row** | `voided = true` + reason; money fields untouched. A corrected `Payment` may then be written as a **second** row. | Original row **preserved untouched**; a **refund record** is written alongside it, referencing it. |
| **Effect on analytics** | The voided payment simply is not counted — it was never real revenue. | Collected revenue is **reduced**, and so are that payment's centre and teacher shares. The revenue *was* real and is being reversed. |
| **Effect on the teacher** | Nothing to settle — there was no valid payment. | The teacher's share of that payment is reversed too. If it's already inside a `DRAFT`/`APPROVED` settlement, that settlement's total is adjusted down immediately; a settlement already `PAID` is never rewritten (§ "Teacher settlements") — the loss is handled outside the record. |
| **Creates a balance?** | No. | **No.** Cash back, nothing owed either way, no student balance anywhere (§2 "Student debt" is unchanged). |

Both are permissioned and audited. Neither ever `UPDATE`s a money field on the original row.

**Refunds (delivered M14).** `lib/db/refunds.ts`'s `refundPayment` is the only writer of a `Refund` row — permissioned through `payment.refund` (a new, elevated action alongside `payment.void` in M12's matrix, not granted to RECEPTIONIST/ACCOUNTANT/TEACHER by default) and audited as `payment.refund`. Phase 1 supports **whole-payment refunds only**: a refund's `amount`/`centerShareReversed`/`teacherShareReversed` are always exactly the original payment's own frozen `amount`/`centerShareSnapshot`/`teacherShareSnapshot` — there is no partial-refund UI or schema field, matching "mark a recorded payment REFUNDED" rather than inventing a proration model nothing asked for. A voided payment can never be refunded (it was never real revenue) and a refunded payment can never be refunded twice. `lib/db/analytics.ts`'s `revenueTotals`/`revenueByTeacher` subtract every refund's reversal amounts from collected revenue and from both shares, for the same date range/teacher the refund's own session falls in — the underlying payment itself is not voided, so it still contributes to the raw aggregate; the refund is what nets it back out. Refunding a payment already claimed by a settlement also live-adjusts that settlement's total when it hasn't been paid out yet — see "Settlement totals" below. The centre-side `/refunds` screen is a read-only ledger; the write path is a Refund button on the session roster where the payment is displayed (`app/[locale]/(center)/sessions/[id]/session-roster.tsx`), the same place Void already lives.

**Teacher settlements (delivered M14).** A settlement record moves `DRAFT → APPROVED → PAID`. There is **no partially-paid state** — a settlement is either fully paid or it is not, because a partial state invites exactly the "how much is still owed" bookkeeping the no-debt rule refuses to carry. Totals are **derived from the frozen `teacherShareSnapshot` values and never recomputed** from current class config — see "Settlement totals" just below for exactly how a *later refund* is handled, which is different from a config change. Two shapes are supported and both are first-class, because real centres do both: **per-session** — a centre paying a teacher cash right after each session marks that single session's teacher share paid — and **period roll-up** — a settlement covering a date range. Every transition is permissioned (`settlement.manage`) and audited. Settlement records are **carved out of the data-visibility window** (below): a teacher who cannot read a settlement from four months ago cannot verify they were ever paid, which would make the record worthless.

**Settlement totals: frozen at creation, live-adjusted while unpaid, immutable once PAID (M14, revised in the M14 follow-up).** A settlement's total is computed once, at creation, as the sum of `teacherShareSnapshot` across non-voided **and non-refunded** payments in scope — a class's centre-cut config changing afterward never moves it (§5.1 "Center cut"), and an already-refunded payment is **excluded from a new settlement's total at creation** (it never gets a share counted for it in the first place).

A *later* refund on a payment already inside a settlement's scope is handled by status, and the two paths are deliberately different:
- **DRAFT or APPROVED** — the payout has **not yet left the centre**. `refundPayment` (`lib/db/refunds.ts`) finds every such settlement in the refunded payment's scope and subtracts that payment's `teacherShareReversed` from its `totalAmount`, in the same transaction as the refund, audited as `settlement.adjust` (before/after totals) alongside the `payment.refund` audit row. A centre can still correct a payout it hasn't made yet, and this is that correction happening automatically rather than requiring staff to notice and fix it by hand.
- **PAID** — the total is **never** touched. The money is already out the door; a refund on a payment inside a paid settlement's scope is a real loss the centre absorbs (or recovers from the teacher directly, outside this system) — this is the existing "a settlement already PAID is not rewritten... the reversal lands in the next period" rule, unchanged.

**What "in scope" means, precisely (R2, made exact by SEC-2b).** Since SEC-2b a settlement **claims** the payments it counts (`SettlementClaim`, one row per payment, written in the same transaction that creates it), so "had this settlement counted the payment" is a lookup, not an inference: a later void or refund adjusts a DRAFT/APPROVED settlement only if it holds that payment's **live claim**, and the claim is released in the same step, so a settlement's total always equals the sum of its live claims. A payment on a session that was still live when a period was settled was never claimed, so giving it back reduces nothing. Voids and refunds share the rule (`lib/db/settlements.ts`'s `adjustUnpaidSettlementsForReversal`), audited as `settlement.adjust`. A closed session refuses voids and refunds altogether, so in practice only a settlement with no claims at all (written before claims existed) can still be adjusted, by the old R2 rule.

This was chosen over two alternatives considered and rejected: **refusing the refund outright** while any non-PAID settlement claims the payment — rejected because nothing in this system can cancel or un-scope a DRAFT settlement, so a legitimate refund could be stranded behind a payout decision nobody can undo; and **blocking the settlement's own next transition** (leaving `approveSettlement`/`paySettlement` refuse once a refund has touched its scope) without fixing the number — rejected because it leaves a wrong total sitting in the record indefinitely, visible to the teacher, until a human notices and does something about it. Live-adjusting the total while it can still be corrected, and freezing it the instant real money moves, keeps the number honest without inventing a settlement-cancellation feature this milestone doesn't otherwise need. Duplicate-claiming the same money is refused outright, not merely discouraged — **by the database since SEC-2b** (D-05 (c)): a payment holds at most one live claim (`SettlementClaim_one_live_per_payment`), whichever shapes are involved, so a session settlement and a period covering the same session can never both pay it, and two concurrent creates for one teacher serialize on a lock and the second claims nothing. A second settlement of a session already settled is refused (`sessionAlreadySettled`); a period that would claim nothing over a range another live period already covers is refused (`overlappingSettlement`); an overlapping period that **does** pick up unclaimed money — a session still live when the first period was settled — is allowed (this answers the former OD-8). A DRAFT may be cancelled (D-16), releasing its claims for a corrected one. *(SEC-2b added a "cancel DRAFT" transition (D-16), which releases the draft's claims; the live adjustment above stays the rule for a refund on a payment an unpaid settlement holds.)*

**Attendance.**
- Statuses: **Present, Late, Absent** — exactly three (R1, §5.1 "Excused removed"). A student who is neither present nor late is absent; there is no excused/neutral fourth state and no per-class toggle.
- **Late threshold** (minutes) is per class.
- Consecutive-absence and total-absence counts are derived from attendance history (`lib/db/attendance.ts`'s `consecutiveAbsenceCount`, M5) and surfaced on the session receipt. *(M10: now also surfaced on the student profile page — a per-class "absent N times in a row" alert for every active enrollment with a live streak.)*
- **Present or Late is decided by the server at check-in (R2)** — now, in the centre's timezone, against the session's start plus the class's late threshold; nobody picks it. **Absent is what closing the session writes** for every enrolled student who never checked in.
- **Corrections only while the session is live (R2).** Once a session is closed its attendance is final (§5.1 "Session lifecycle").
- Corrections require permission and are audited; sessions have an **edit deadline** for teachers, set by the manager. *(M5: attendance corrections are permissioned and audited — `attendance.record` for a first mark, `attendance.correct` for changing an already-marked row. M10: the teacher edit-deadline setting is real — `CenterSettings.teacherEditDeadlineHours`, `null` = no deadline, a General Settings toggle, enforced in the session-description edit action.)*

**Scheduling.**
- A class can meet on **multiple days/times**.
- A class has a **period** (start + end date). Its sessions exist for every matching weekly slot in that period from today on, holidays skipped — created when the class is, re-fitted when it is edited (R4, §5.1 "Class periods and centre terms"). There is no rolling window.
- Staff may add a session by hand — an extra session on a class or a one-time session with no class — for today or later only (R5, §5.1 "Manual and one-time sessions").
- Teacher and room **conflicts** are detected/warned per configured rules — **within one centre only** (settled). A teacher double-booked between two *different* centres is **not** detected, deliberately: finding that clash means one centre learning that a teacher works elsewhere, when, and with whom, which is exactly the disclosure M12's teacher-detail fix closes on purpose. Cross-centre detection needs a teacher-consented free/busy model and is `05-phase-2-backlog.md` entry 2. Within a centre, the branch layer changes nothing — rooms and sessions belong to the centre directly (see "Branch architecture"), so the existing checks already cover every room a centre has. **R3:** a booking occupies its whole room set (primary + combined extra rooms), and a double-booking is saved only after explicit confirmation under WARN, never under DENY (§5.1).
- Cancel/reschedule updates affected rosters and (later) notifications; material changes are audited. *(M10: `lib/db/sessions.ts`'s `cancelSession`/`rescheduleSession`, gated on `session.cancel`/`session.manage`. Cancelling never touches money/attendance; rescheduling re-runs the same conflict check every slot write uses. Notifications stay out of scope per §2. **SEC-2b (D-07):** both are refused while the session holds an active payment — staff void or refund first, each with its reason — and a cancelled or rescheduled session closes at the end of its day like any other, so no void or refund path stays open on it.)*

**Reservations / enrollment.** *(M8, `lib/db/reservations.ts`'s `reserveOrEnroll`.)*
- A class flags **accepts-new-students** and **requires-confirmation**. If confirmation is required, a student request is **Pending** until center/teacher accepts; otherwise it's **Confirmed** immediately — implemented literally as "no `Reservation` row at all, an active `Enrollment` written directly" for the instant path, `ReservationStatus` genuinely not applicable there.
- Capacity is enforced; full-class behavior (reject vs waitlist) is a defined rule (default: block enroll when full). For an instant-enroll class this is checked at request time, refusing the write outright (`classFull`). For a confirmation-required class it is deliberately **not** checked at request time — a center may legitimately want more requests than seats so it can choose who to confirm — and is re-checked in `confirmReservation` instead, at the moment a seat is actually claimed.
- Duplicate enroll/reservation is prevented. `Reservation` is unique on `(classGroupId, studentId)` with no `centerId`/`status` in that key (docs/01-data-model.md §2), so — like `Enrollment` — the row is reused across its lifecycle: a REJECTED/CANCELLED request re-requested later resets the same row to PENDING rather than inserting a second one, which the unique constraint would refuse.
- A student's identity is the global `User` (CLAUDE.md rule 4); their center-local `StudentProfile` is created the moment a seat is actually claimed — instantly for the immediate-enroll path, or on confirmation for the pending path — never merely from sending a request. This is the self-serve "connect to a center" mechanism docs/02-architecture.md §3 refers to for students.

**Blocking.** Teachers (and centers) can block a student from a teacher/class/session. A blocked student cannot enroll or be added.

**Teacher inactivity.** A center-configurable **timeout** (N days with no completed session, counting from last completed session) flips a teacher to inactive; `none` disables it.

## 5.1 Settled decisions (recorded so they read as decided, not missed)

> Everything in this section is a **choice with a reason**, not a gap. Several of them look, from the outside, like something a more thorough build would have done differently — which is precisely why the reasoning is written down rather than left to be rediscovered as a "bug" later.

**Check-in & the QR payload — static, printed, centre-scoped.** The ID card encodes `KAYEDU|{centerId}|{studentCode}` and nothing else: no session, no timestamp, no rotating token. This is deliberate on four counts. **Offline reliability** — a printed card scans with no network, no battery and no app; a session-aware token needs a live server at exactly the moment (the rush) when the connection is least reliable. **No smartphone dependency** — a great many students do not carry one, and a check-in method that assumes they do is a check-in method that fails for the students it fails for, silently. **It is already centre-scoped** — a card issued by Centre A carries A's `centerId` and reception refuses a payload from anywhere else, so a card is not a platform-wide credential. **The anti-impersonation control is reception's photo check, not the code** — a human comparing the face in front of them to the photo on the screen is what stops a borrowed card, and no token scheme replaces that. Two consequences follow and both are load-bearing: the scan result **must display the student's photo** (see §7 criterion 16 — this is currently missing, and M18 fixes it), and a dynamic token stays in `05-phase-2-backlog.md` entry 1 until an observed impersonation problem justifies the trade.

**Reception check-in — session-first, scan-then-confirm (R7).** The desk is built around the question the receptionist is actually answering: *which session am I admitting students to right now?* So (1) **a session can be selected first** (`?session=<id>` in the URL) and every scan or typed student then goes to *that* session; the id is untrusted input and is **re-validated on every request** — this centre, dated today in the *centre's* timezone, not cancelled, rescheduled or closed — and an invalid one leaves session mode with a notice; (2) **a scan never records anything**: it resolves who the card belongs to and opens a confirm panel with the **photo** (the anti-impersonation control above), name, code, whether they are enrolled in the class (otherwise a drop-in, exactly as before), the session's price (read from the server, never computed on the client) and the payment method (default: the last one used in this session mode, else the first active); **one Enter or tap** then calls the existing `checkInAction` — the same attendance helper (`createAttendance`, Present/Late decided by the clock, R2) and the same money helper (`recordPayment`, frozen snapshots) as every other path; (3) **the refusals are specific and leak nothing across branches** — already checked in ("is already checked in at 4:05 PM", no second row), blocked (either `StudentBlock` scope), inactive, not found, and *a card issued by another branch*, which is refused on its centre id alone and answers identically whether or not that code exists there (student codes restart at 1001 in every centre, so a bare code is ambiguous across centres — it only ever resolves inside the desk's own centre); (4) **every picker that offers a session shows its teacher** — "session · teacher · time", the teacher being the centre-local `Membership` name, a one-time session showing its own title — and **closed, cancelled and rescheduled sessions are never offered**; (5) **End session works from a session's card** by reusing R2's `endSessionAction` (`session.close`, irreversible, refused before start) and its receipt component, opened in the shared dialog with Print — no second implementation of closing or of the receipt. *Scanner reality:* the scanner is a USB keyboard-wedge device, so what reaches the input is typed text; the single parser (`lib/id-card.ts`) tolerates prefix/suffix noise, full-width and Arabic-Indic characters and case, and accepts a bare student code, **without changing the payload format**. A scan taken while an **Arabic keyboard layout** is active cannot be read reliably (the letters of `KAYEDU` and of the centre id arrive as Arabic letters); the desk detects that and says so rather than guessing — see `03-build-order.md` R7 and backlog entry 19.

**"Today" is the centre's calendar day, everywhere (R7b).** Every "today", trailing "this week", month-to-date "this month", default date filter, date-picker "today" marker and data-visibility floor is the calendar day **in the centre's own `CenterSettings.timezone`** — never the UTC day, never the server's, never the browser's. Reason: `Session.date` is a stored day marker and session times are the centre's wall-clock, so a screen that reads the UTC day shows *yesterday* between 00:00 and 03:00 in Cairo (+03:00 until the late-October DST end, +02:00 after), which is exactly when a night-owl centre or an early opener looks at it, and which made the dashboard, the sessions list and the reception desk disagree. **One helper owns it** (`lib/scheduling.ts` `todayInTimezone`, resolved through `Intl`/IANA data — no hard-coded offset); a second derivation is a bug and `npm run check:timezone` fails on one. **A cross-centre view** (teacher dashboard and schedule, student schedule, rating pop-up) computes each centre's own day in that centre's query and sums in memory — there is no global day. **Where one combined value is unavoidable** the rule is documented and tested: the "Whole Management" analytics roll-up resolves its single range against the active branch's timezone; the student schedule's date-picker marker uses the zone all the student's centres share, else `Africa/Cairo`. **Consequence recorded here because it is a behaviour change:** the teacher edit deadline (`teacherEditDeadlineHours`) counts from the start of the session's day *at the centre*, not from UTC midnight — it now lands 3 hours (summer) or 2 hours (winter) earlier than before. No stored data changed; no migration. See `03-build-order.md` R7b and `02-architecture.md` §11.

**Branch architecture (delivered M11).** A new **`Organization`** model is the paying customer. The existing **`Center`** becomes the branch-level tenant and gains a required `organizationId`. **`center_id` remains the sole isolation key** — `lib/db/scoped.ts`, `getTenantContext()` and the gate scripts' isolation model do not change, and that is the point of doing it this way: the org layer is additive, so nothing that currently guarantees isolation has to be re-proven (`npm run check:isolation` passes with its fixture swapped from the retired `Branch` model to `Room` — a like-for-like non-money model — but its assertions are untouched). **Owner org-level reach is a read-time widening, not a schema-level org membership**: an Owner's real `Membership` row still names exactly one branch; `getUserCenterRelations()` (`lib/auth/tenant.ts`) additionally resolves every sibling branch under the same organization at read time (`lib/db/organizations.ts`), so `Membership.centerId` needed no schema change at all — see `02-architecture.md` §4 for the full reasoning and the trade-off (an Owner doesn't yet appear in a sibling branch's own staff list; closing that belongs with M12's `MembershipBranchGrant`). **Manager / Receptionist / Accountant** hold **centre-level memberships** naming exactly one branch, unless the Owner explicitly grants additional branches (M12). **Teacher memberships are unchanged** — a teacher belongs to centres, exactly as today, and the org layer neither widens nor narrows that. The navbar branch switcher (`/select-center`) gained a **"Whole Management"** option, reusing the **same** `kayedu_center` cookie as a branch selection — its value is an Organization id instead of a Center id, resolved by `getTenantContext()` alone, never a second cookie — so which `centerId` is active for any operational screen is never widened, only exposed to Analytics via `TenantContext.rollupOrganizationId`. Analytics gains an **org-level roll-up** (one branch, or all), computed as a union of per-branch scoped queries (`npm run check:branches` proves the roll-up equals exactly the sum of the branches' own figures, and that Branch A still cannot read a Branch B record — one non-money model, one money-bearing model). The old **`Branch` model is retired**: `Room.branchId` and `Session.branchId` are dropped, and rooms and sessions belong to the centre directly — the old `Branch` was a location sub-entity under a tenant, which is the job the centre itself now does; the old Branches settings screen and its CRUD are removed. **Branch limits and adding a branch (decided and delivered F1 — OD-12, options (a)+(b)).** *(Replaces "there is no limit on branches per organization".)* Each organization carries **`maxBranches`** (≥ 1, default 1; the migration backfilled `max(1, its non-ARCHIVED branch count)`), and **counted branches are its non-ARCHIVED centres**. **Only a platform admin changes it** (`/admin/organizations/[id]`, audited `platform.organization.limit.update`); lowering it below the current count only blocks new branches. Two ways a branch joins an organization: **(a)** the admin's Create form, "Add to an existing organization" (§4.4), and **(b)** an Owner's self-serve **Settings → Branches → Add branch** (§4.1 item 13), the new OWNER-only action `organization.branch.create`. Both run in **one transaction**: lock the organization row (`SELECT … FOR UPDATE`), recount, refuse `branchLimitReached` at the limit, create the centre through **the same provisioning path** (`provisionBranch` → `provisionCenterBaseline` — there is no second implementation), and audit. The Owner path's data function (`lib/db/branches.ts`'s `addBranchAsOwner`) is the authority: it takes the acting branch, never an organization id, re-resolves the actor itself, so a branch can never be added to another customer's organization, and "Copy setup from" must be a branch of the same organization. **What a branch costs is still OD-3** — until that is answered, the limit is the only lever. Proven by `check:branches` §4 (two concurrent adds at limit-1 → exactly one; the ceiling; the copy carries the ticked setup and never people, rooms, classes or money; another customer's organization is unreachable) and `check:admin` §8. Naming is resolved in the **i18n layer only** (see §2) — the full "Center"→"Branch" sweep across every screen (including the Super Admin's `/admin/centers`) is done, message values only, no code renames: a full DB rename is still `05-phase-2-backlog.md` entry 18.

**Global academic catalog.** Subjects, grades and education systems are **platform-owned**. A centre **picks** entries from the catalog rather than authoring its own. For a picked entry, a centre may edit **only its own price and its own display name — one optional name per language (`displayNameAr`, `displayNameEn`)** — never the canonical entry. Every catalog entry carries **both an Arabic and an English name**, so a subject reads correctly in either locale without a centre translating anything.

**R8 — platform-admin-managed catalog; the suggestion queue is removed (reverses part of M13).** M13 let centres *suggest* additions and corrections into a queue a platform admin reviewed. That is gone — the suggestion model, its status enum, the centre "suggest" controls and the admin review queue are all removed (history: `03-build-order.md` M13 and R8). Decision: the catalog stays global, but if a centre needs an entry **it contacts us and the platform admin adds it directly**. The rules, all enforced in the data layer (`lib/db/catalog-admin.ts`), not the UI:

- **Writes are platform-admin only.** Add, edit names, edit `defaultFixedCenterShare`, deactivate, reactivate, delete — every one re-checks that the acting user is `isPlatformAdmin`, so a direct call from any centre role (or anyone else) is refused. Each write is audited (`platform.catalog.create | update | deactivate | reactivate | delete`, before/after, no `centerId`).
- **Both names, always.** Every entry needs `nameAr` **and** `nameEn`, trimmed, 1–80 characters. A name may not repeat — compared case-insensitively, English and Arabic each — among the entries of the **same parent** (all education systems; the grades of one system, or the parentless grades; the subjects of one grade, or the parentless subjects), deactivated entries included.
- **Delete is a hard delete only if nothing references the row** (no centre selections, classes, student profiles, one-time sessions or child entries); otherwise it is refused with the counts and the admin is offered **Deactivate**. A deactivated entry disappears from every picker, Discover filter and the centre catalog "add" list, **and cannot be newly assigned** (class, student grade, one-time session, teacher request), but it keeps rendering — through the one label resolver — in classes, sessions, history and analytics, and an existing class or student that already has it can still be saved unchanged.
- **A centre's rename is bilingual.** Two optional fields. In the Arabic UI the label is `displayNameAr`, else the canonical `nameAr`; in the English UI `displayNameEn`, else the canonical `nameEn`. An Arabic override **never** shows in the English UI and vice versa, and another centre is unaffected (`02-architecture.md` §8 "Catalog label resolution"). **Person names stay single-valued and do not change with locale**: a person has one name per relationship (the centre-local name, `01-data-model.md` §6), not an Arabic one and an English one — a human's name is not a translatable string, and pretending otherwise creates two records of the same person that drift. This also unblocks the portability the platform is sold on: with a global catalog, "IGCSE Physics" means the same thing at every centre, which is what makes Discover's cross-centre filtering (`02-architecture.md` §14) able to stop matching on strings.

**Approvals & enrolment (delivered M15).** A centre approves student enrolment requests from `/approvals` (§4.1 item 9) — `lib/db/reservations.ts`'s `confirmReservation`/`rejectReservation`, unchanged in shape since M8. **Teachers get their own approvals page** (`/teacher/approvals`, spec §4.2 item 6) for students enrolling in *their* classes — a separate queue reading the exact same `Reservation` rows (`scoped(ctx).reservations.listPendingForTeacher`), gated on a new matrix action (`reservation.manage.own`, TEACHER baseline) and pinned in the Server Action to reservations whose class this teacher actually teaches, because the permission alone only proves "some teacher may use this queue." Two rules apply to both queues, both already true of `confirmReservation`/`rejectReservation` before this milestone and now covered by `npm run check:enrollment` directly: a request **checks both `StudentBlock` scopes** (TEACHER and CLASS) and is **refused** when the student is blocked from that teacher or that class, at request time (`reserveOrEnroll`) **and** approval time (`confirmReservation`) independently — a block placed between the two refuses the approval; and a **rejected student cannot re-request the same class for 7 days** — `Reservation.rejectedAt` (a new column, stamped by `rejectReservation`) is the whole mechanism, read back by `reserveOrEnroll` via `lib/capacity.ts`'s `isInCooldown`/`cooldownUntil`, and the Discover reserve action surfaces the exact retry date (`StudentDiscover.errors.coolingOff`) rather than a bare refusal. The cooling-off is per (student, class), not per centre, and does not reset on re-request — only a later rejection restarts it.

**Capacity (delivered M15; the "two fields" rule below is reversed by R3 — see "Class capacity removed").** Enrolment is **hard-capped**, and the cap was **the more restrictive of two real, pre-existing fields** — `ClassGroup.capacity` (a centre's own planning target, since M4) and `Room.capacity` (the physical seat count, since M4/M11) — via `lib/capacity.ts`'s `enrollmentCap(classCapacity, roomCapacity)`, which takes the smaller of the two non-zero values (0 = unlimited on either). `isAtCapacity` is the shared refusal check `reserveOrEnroll`, `confirmReservation` and the centre-staff `enrollStudentAction` all call. The refusal message is **generalized to name a fix that works regardless of which field is actually binding** — *"increase the class's capacity or move it to a room with more seats"* (`Classes.errors.classFull`/`Approvals.errors.classFull`/`StudentDiscover.errors.classFull`/`TeacherApprovals.errors.classFull`) — not a bare "class full," and not a message that names only the room: an earlier draft of this copy said "change the room or increase its capacity," which is actively wrong when the class's own (smaller) `capacity` is the binding constraint and the room has seats to spare — telling staff to enlarge a room that was never the problem fixes nothing. The compound "or" phrasing means at least one half is always the real, actionable fix, whichever field turns out to be binding. **Session attendance may exceed either cap**: `createAttendance` (`lib/db/attendance.ts`) has no capacity check at all, by design — 25 people in a 20-seat room is a real and acceptable thing on the day, and blocking the desk from marking a student present who is physically standing there would be absurd. A student **may still submit an enrolment request** when the class is full (`reserveOrEnroll` never checks capacity for a `requiresConfirmation` class), but **staff cannot manually add or approve past the cap** until one of the two limiting fields changes — `confirmReservation` and `enrollStudentAction` both re-check the same `enrollmentCap` at the moment a seat is actually claimed. `npm run check:enrollment` proves the split directly: enrolment refusal and attendance success in the same run, against the same over-subscribed room.

**Reschedule with linkage (delivered M15).** A rescheduled session **links to its replacement immediately** — `lib/db/sessions.ts`'s `rescheduleSession` now **creates a new `Session` row** at the target date/time and writes the original's `rescheduledToId` in the same transaction, rather than mutating the original row in place (the pre-M15 behaviour) — so the original is never silently turned into the new one, and whatever attendance/payments it already carries stay exactly as recorded (CLAUDE.md rule 2). The target may be a **future date or the same day at a different time**. The **room must be free for the entire start→end window**, not merely at the start instant — this was already true of `lib/scheduling.ts`'s `timeRangesOverlap`/`findSessionConflicts` (a real half-open interval comparison, not a start-instant check) before this milestone; `npm run check:enrollment` adds the first direct assertion of it (a target free at its own start but occupied before its own end is refused under DENY). The **same rule applies whether a teacher or centre staff initiates** it — `rescheduleSession` takes no caller-identity parameter at all. **A session carrying a `rescheduledToId` is closed to new attendance and payment**, exactly like a `CANCELLED` one (see the cancelled-session guard below) — `deriveSessionDisplayStatus` reports it as `RESCHEDULED`, taking precedence over both the stored `status` and the clock, and its roster renders read-only with a link to the replacement.

**Cancelled-session guard, extended to rescheduled sessions (delivered M15, closes spec §7.1's verified gap).** `lib/db/attendance.ts`'s `createAttendance`/`updateAttendanceStatus` and `lib/db/payments.ts`'s `recordPayment` now refuse a `CANCELLED` session's attendance/payment **and**, as of this same milestone, an already-**rescheduled** one's too (`SessionClosedError`, thrown with `reason: "sessionCancelled" | "sessionRescheduled"`) — a single choke point every write path funnels through, so a future caller cannot forget the check the way every existing caller did before M15. The four production Server Actions (`setAttendanceAction`, `addNewAttendeeAction`, `checkInAction`; T2 retired `addExistingAttendeeAction` — an existing student's check-in is `checkInAction` everywhere) catch it and surface the same refusal a direct call to the underlying function produces; `npm run check:enrollment` asserts the direct-call refusal itself, not just the UI.

**Teacher onboarding (delivered M15).** A teacher who belongs to **no centre** lands on the centre directory (`/teacher/centers`), never the student Discover screen — `lib/auth/tenant.ts`'s `requireTeacherUser()` (mirroring `requireStudentUser()`) never redirects a zero-relation user away, and `getTenantContext("teacher")` now redirects a zero-relation teacher-experience request to `/teacher/centers` instead of the generic `/select-center` empty state. From the directory they **request to teach a class** at a centre they browse — a `NEW_CLASS` `ChangeRequest` written directly with an explicit `centerId` (`requestToTeachAction`, no `TenantContext` to resolve since there is no `Membership` yet), reviewed at that centre's own `/approvals` through the **exact same** `resolveChangeRequest` path any other `NEW_CLASS` request uses — a plain status flip, no `ClassGroup` auto-created, identical to the decision record in §4.1 item 9. Approving it does **not** create a `Membership` either: staff still add the teacher through the ordinary Teachers-screen flow, reading the approved request's details off the Approvals card, exactly as they already do for a connected teacher's own class request. `/select-center`'s empty state now offers this alongside the existing "browse classes" link, since a brand-new sign-up's intent (student or teacher) isn't known until they pick one.

**Parent role & portal (delivered M16; access rewritten F3 — OD-6 decided).** A **PARENT** role; the parent gets a **child selector** and a portal mirroring the student portal per child (§4.5). Since F3 the relation is a **`FamilyLink`** between two global `User`s — the parent's account and the student's account — with **no `centerId`** (a cross-cutting identity relation, like `SessionRating`), so a link can exist **before the child joins any branch**. It grants no tenant read by itself: the portal reads each child's data **through that child's own active `StudentProfile`s at accessible branches**, with the student portal's own centre-scoped reads (`lib/db/parents.ts`'s `activeChildLinks` is the only read any parent-portal page builds on). The rules, all enforced in `lib/db/parents.ts`, never in a form:
- **Access needs a secret, never a phone.** A link is created only by accepting a **one-time code**. A phone match grants nothing and creates nothing — sign-up no longer originates anything (the M16 phone origination, `originateParentLinks`, is gone), and nothing matches, links or refuses on a phone. A parent phone on a student record is contact data only.
- **The code.** 8 symbols from an unambiguous alphabet (no `0 O 1 I L`), shown as `XXXX-XXXX`; stored as its **sha256 only** (plus a two-character hint so lists can tell codes apart — a database CHECK refuses anything that is not a hash); shown **in full once**, at creation. **No time limit** (founder's decision), **single use** (a conditional PENDING → ACCEPTED update — of two accepts racing on one code exactly one wins), revocable; regenerating revokes the previous code for that slot.
- **Two ways to get one.** (a) **The student** — Account → Family → **Invite a parent**: the parent's first and last name and phone (the student's *declared* parent contact, normalized by `lib/phone.ts`, never an identity key) → a PENDING invitation and its code, with Copy and **Share on WhatsApp** (`https://wa.me/?text=…`, the join link carrying the code in its fragment). The student can cancel a pending invitation or make a New code for it. (b) **The branch** — `/students/[id]` → **Parent access** → **Generate parent code** (`parent.link.manage`, the OWNER/MANAGER baseline): shown once in a dialog with **Print** → a small slip (branch, student, code, join link, short Arabic and English instructions, "hand this to the parent in person"). Audited `family.code.issue`. It works for a staff-created student with **no login**, since the link targets the student's global `User`. One live code per (student, branch).
- **Slots.** At most **3** per student — active links plus pending invitations, any source; at most **3** active parents per student and **10** children per parent. Counted under a per-student lock, so parallel requests cannot race past them.
- **Accepting** — at `/[locale]/family/join`. The code travels in the URL **fragment** (`#XXXXXXXX`): read in the browser and posted, never a query parameter, never logged. A guest is sent to sign in or register and comes back with the code still in place (held in that tab only). Refusals, each with its own message: an invalid, used or revoked code ("invalid or already used" — one message for anything about the code itself); the code's own student ("your own code"); **any student account** — one holding any `StudentProfile`, a pending code or a link as a child ("a parent needs their own parent account, not a student account"; F4's sign-up intent joins this test when it exists); a platform admin; already linked; the child already has 3 parents; the parent already has 10 children; and the rate limit — **10 attempts an hour per account and per IP**, counted before any code is looked up. Account-level refusals are answered whatever the code, so a student account cannot use the page to learn which codes are live. One transaction: the invitation ACCEPTED, the link ACTIVE, audited `family.link.create` (ids only).
- **Staff and teachers may be parents.** *(Supersedes the M16 rule "refused for a phone already belonging to a teacher, staff member or platform admin".)* That refusal guarded **silent phone matches**, which no longer exist; a link now needs a secret someone handed over, and the portal is read-only. A teacher's own child at the branch is the common case. **Platform admins stay refused.**
- **Revocation** — explicit and audited (`family.link.revoke`), never automatic. By **branch staff** with `parent.link.manage`, from the student's page, with a **required reason** (kept on the link, never in the audit row — D-20); by **the parent** (Account → Family → Unlink); or by a **platform admin** (the data function exists; its screen is `05-phase-2-backlog.md`). **A student cannot remove an active parent** — a minor can't cut off their parent. Revocation is final for its code: relinking needs a new one. Reads stop on the next request. *(D-04's automatic revocation on a parent-phone change is retired — the phone is not the key.)* **D-10 stays**: a suspended/archived branch or an inactive profile disappears from the parent portal (the link itself stays).
- **Visibility.** The student's Account → Family lists their active parents (account name) and pending codes (declared name, code hint). The branch's **Parent access** card lists every active parent account — account name, how linked (the child's invitation / this branch's code / another branch's code / linked before codes), the date, and the parent the child declared when there is one, so staff notice a mismatch — and no parent email or phone beyond what the branch already holds.
- **Existing data.** The F3 migration copied every VERIFIED `ParentLink` into an ACTIVE `FamilyLink` (source `LEGACY_VERIFIED`, deduplicated per parent and child); PENDING links were not migrated. `ParentLink` is no longer read or written anywhere and is dropped after the pilot (`05-phase-2-backlog.md`).
- **Residual risk (accepted at F3).** A student can still hand a code to an adult who is **not** a student — a friend's older sibling, say. It is bounded three ways: the portal shows only that student's own data and is read-only, never more than the student's own portal; staff see every linked parent on the student's page, next to the parent the child declared, and can revoke; and the **branch-printed code, handed over in person**, is the strong path a centre can insist on. A second factor (an OTP to the declared phone) stays possible later — `05-phase-2-backlog.md` entry 12. Whether minors' data may be shown to a parent at all is still OD-2's legal review.

**Sign-up intent and the two-layer grade (delivered F4).**
- **The intent routes, it never authorises.** `User.signupIntent` (`STUDENT | PARENT | TEACHER`, nullable, set once from the sign-up metadata and read back by `resolveAppIdentity`) decides only where a person with no branch lands (`lib/auth/onboarding.ts`'s `onboardingPath`, via `landingWithoutBranch`) and which start the branch hub highlights. It is not a role; no permission, relation-resolution or scoping module reads it (asserted by `check:account`). The metadata is client-controlled, so anything but one of the three values is dropped. One refusal reads it: an account that said it is a **student** counts as a student account for F3's parent-code rule (`isStudentAccount`) even before it has a profile — otherwise a fresh "student" could accept a classmate's code.
- **Grade has two layers.** The student's **account grade** (`User.gradeId`, a platform catalog grade, theirs, editable any time on Account → Study details) and the **branch's grade on file** (`StudentProfile.gradeId`, the branch's own record). The account grade **seeds a new branch profile** (only a grade that branch offers — SEC-49) and **pre-selects Discover's filter**; it **never overwrites an existing profile** and changing it moves no branch record. Staff see the difference on the student's page (**Account says: <grade>**, with **Use account grade** — `student.manage`, audited `student.grade.account`) and on the list (the **Grade differs from account** filter). The two may differ; nothing reconciles them silently.
- **A declared parent seeds contact data, never a link.** The parent a student named in "Invite a parent" (their latest PENDING or ACCEPTED invitation; a cancelled one declares nobody) is copied into a *new* branch profile's parent name and phone as that branch's own record. It matches, links and refuses nothing (D-02); a link still needs a code.
- **D-11 (a) is unchanged.** A student completes their own profile once; staff edits stay allowed. A profile seeded with both a grade and a parent phone is already complete, so the form is simply not needed.
- **Promotion** (§4.1 item 4) is a branch-record change only, with its own batch, 14-day undo and audit.

**Teacher ratings (delivered M17).** After attending sessions, a student sees a **skippable** login pop-up inviting them to rate those sessions **1–5**, covering the **last 7 days**. What is published is an **average out of 5 only** — shown on class/session browsing (since F5 also on the public Explore pages, to guests, §4.7), **never the count**, because a count is what turns a rating into a popularity contest and lets a teacher (or a centre) infer who rated them from a small sample. Visible to **students, centres and the teacher**; the teacher can **never see who rated them**. The rating **follows the teacher across centres** — it is an attribute of the person, like their identity, not of a membership. `SessionRating`/`SessionRatingSkip` (`prisma/schema.prisma`) carry no `centerId` at all — the aggregate is platform-wide by construction, not by convention — and `lib/db/ratings.ts` exports only aggregate reads (`teacherRatingAverage`/`teacherRatingAverages`, `{ average }`, never a count) plus the write path; no function anywhere lists a raw `SessionRating` row by `teacherId`, which is the only way a rater's identity could ever reach a teacher-facing caller. A skip is persisted server-side (`SessionRatingSkip`), not in browser storage, so "costs nothing" holds across devices and future logins, not just the current tab — closing the pop-up itself (as opposed to using its per-session Skip button) persists nothing and never blocks navigation either way. See `03-build-order.md`'s M17 entry for the full delivery note and `npm run check:ratings` for the gate.

**Data visibility window (delivered M19).** By default, **no centre-side role (OWNER/MANAGER/RECEPTIONIST/ACCOUNTANT) may view data older than 1 calendar month** — analytics, money, old sessions, attendance history. Platform admin bypasses it. It is **per-centre configurable** in `CenterSettings.dataVisibilityDays` (default 30) — editable both from the centre's own `/settings` screen and, as an override, from a platform admin's `/admin/centers/[id]`. Expressed as a **rolling day count ending today**, not "since the 1st of this calendar month": an anchored window would jump backwards by up to 30 days at the start of every new month, which isn't what "how far back can this role see" means, and a day count is what lets widening it (or a platform admin's bypass) take effect on the very next request with nothing to recompute. Four constraints are part of the decision, not implementation detail:
- **It is a read restriction and never a deletion.** Every snapshot row stays exactly where it is. Nothing is pruned, archived away, or made unrecoverable — widening the window restores full visibility instantly, because nothing was lost.
- **It is enforced in the data layer, not the UI.** A direct URL or API call must not bypass it, mirroring the shape the receptionist profit-denial already has (§7 criterion 9): the denial is a scoped query and a loader-level refusal, not a hidden button. **Delivered (M19), moved into the scoped helpers (SYS, SEC-62 option (a), user decision):** `scoped(ctx)` (`lib/db/scoped.ts`) injects the floor **beside `centerId`** into every session, attendee, attendance-change, payment and expense read — `findById`, `findDetailById`, `search`, `count`, `listForDay`, the roster lookups, the receipt's change log and the absence streak (`attendees.absenceStreak`) — for the four centre-side roles (`lib/db/visibility.ts`'s `centreReadFloor`; never for TEACHER/STUDENT/PARENT, never for a platform admin). So an out-of-window session, attendee, payment or expense read **by id** is `null` exactly like another centre's id, and lists and counts stop at the floor. The one opt-out is **`scopedIgnoringVisibilityWindow(ctx, reason)`**, with `reason` `"integrity"` (a writer's own guard that must see the whole history — the student/teacher/room/expense-category delete blockers), `"settlement"` or `"audit"` (the carve-outs) — `npm run check:visibility` refuses any other use. Sessions/Analytics/Expenses still clamp their own date filter too, `refunds.list` stays windowed by `refundedAt`, and writes are covered separately (every session older than its day is closed — SEC-08).
- **What centre staff see differently since SEC-62 (SYS).** Every page reading through the helpers above: the **session detail and its print view** (an out-of-window id was already refused by a page check; it is now refused by the helper), the **sessions list and dashboard** (already range-clamped — unchanged in practice), the **student detail page** — **absence streaks now count back no further than the window** (a student absent six times, four of them before the floor, shows "absent 2 times in a row"), the **session receipt's** per-student streaks (same cut) and **"Changes during session"** (empty for a session outside the window — only reachable through the carved-out audit trail), and the **expenses list** (already clamped). Delete guards are unchanged: they read the whole history through the `"integrity"` opt-out, so an old record still blocks a delete. Not windowed, deliberately: a class's period session **count** on the classes list and class page (a planning figure, not history), settlements and the audit trail.
- **Settlement / payout records are carved out** and stay visible. Otherwise a teacher can never verify they were paid, which defeats the entire point of having the record. **Delivered:** `scoped(ctx).settlements.list`/`auditLogs.list` apply no date filter at all, regardless of the centre's window.
- **Audit logs are carved out.** An audit trail a centre cannot read past last month is not an audit trail.
- **Refund records are *not* carved out** — a refund is money moving, not a payout record, so `scoped(ctx).refunds.list` is windowed exactly like everything else.

Gated by `npm run check:visibility` (`scripts/visibility-check.ts`).

**Centre lifecycle (delivered M19).** `Center.active` (a boolean) is replaced by **`ONBOARDING / ACTIVE / GRACE / SUSPENDED / ARCHIVED`**. **`Center.plan` is removed entirely** — the column, the editor, the Server Action, and every reference in code and docs. It was free text with no behavior behind it, and leaving it in place implies a billing system that does not exist. **No module entitlements**: one product, configured, never gated per centre (§8). **Delivered:** ONBOARDING/ACTIVE/GRACE all permit sign-in (`lib/db/platform.ts`'s `ACCESSIBLE_LIFECYCLE_STATES`, the exact filter `getUserCenterRelations()` — `lib/auth/tenant.ts` — gates on, replacing the old `center: { active: true }`); SUSPENDED/ARCHIVED both refuse it, exactly as the old `active: false` did. Transitions follow a stated table (`LIFECYCLE_TRANSITIONS`), not free-form: **ARCHIVED is terminal** (closing a centre is final — a resumed relationship is a new Center, never a reactivation), and **every non-terminal state can jump straight to SUSPENDED or ARCHIVED** (an admin must always be able to shut a problematic centre down immediately, without forcing it through intermediate states); recovery back to ACTIVE is otherwise only possible from ONBOARDING (finishing setup), GRACE (resolved before a hard suspension) and SUSPENDED (reinstated) — never from ARCHIVED. `transitionCenterLifecycle` re-validates this table server-side regardless of what `/admin/centers/[id]`'s own form offers. A freshly admin-provisioned center now starts **ONBOARDING**, not ACTIVE (nothing has been configured yet), migrated existing centres map `active: true → ACTIVE` / `active: false → SUSPENDED` (the confirmed mapping — the boolean's two real states, preserved exactly).

**UX & data integrity (delivered M18).** A cluster of small decisions that are individually minor and collectively the difference between a demo and a tool:
- **Visual ID-card layout editor** — drag, resize, add from a palette, remove with ×. **A centre never sees JSON.** The stored `cardLayout` shape only ever grows optional keys (R9: text style, branch text, card colours — §5.1); an older layout is still valid and renders exactly as before. **Delivered:** `app/[locale]/(center)/settings/card/card-form.tsx` renders the live card face (`lib/id-card.ts`'s `renderIdCardSvg`, client-side, with placeholder sample data) with a drag handle per present element (pointer events, logical `insetInlineStart`/`top`, snapped to a 2% grid, clamped 0–100) — moving one is a real drag on the preview. Resize is the properties strip's width/font-size numeric field rather than a corner handle: four of the seven elements (`centerName`/`studentName`/`grade`/`studentCode`) have no `width` in the data model at all (`lib/id-card.ts`'s `CardElement`), only `fontSize`, so a single shared numeric control per element type covers all seven uniformly instead of a handle with nothing to write to on most of them. "Remove" deletes the element from state (serialized as an explicit `null` in the stored JSON — `resolveCardLayout`, `lib/id-card.ts`, now treats a `null` key as "omit," distinct from "absent = use the built-in default"); the palette (`lib/card-layout.ts`'s `CARD_ELEMENT_KEYS`) re-adds a removed one at its default position. Below `md`, the drag surface is replaced by a stacked list with numeric x/y/width-or-fontSize inputs per element, per §11.6. The generated JSON is written only to a hidden form field at submit — `saveCardLayoutAction`/`cardLayoutSchema` are byte-for-byte unchanged, they simply never render to a textarea anymore.
- **Phone validation, 11–15 digits, one shared normalizer.** `+20100…`, `20100…` and `0100…` all normalize to `01…`, through **one function** used by validation, duplicate-matching **and** search. Three implementations of this rule is three different answers to "is this the same person." **Delivered:** `lib/phone.ts`'s `normalizePhone` is now the sole implementation — the near-identical copy that used to live in `lib/identity.ts` is deleted (that module now imports it), the byte-for-byte duplicate zod schema in `lib/validation/sessions.ts` collapsed into a shared `lib/validation/phone-schema.ts` (`optionalPhone`; its unused `requiredPhone` twin was removed at SYS), and `lib/validation/auth.ts`'s registration schema — the one call site that previously validated shape with its own bare regex and never actually normalized, so `User.phone` could be written in a non-canonical form and a raw `prisma.user.findUnique({ where: { phone } })` duplicate check could miss an existing owner stored differently — now goes through the same schema too. `npm run check:people` asserts this is the *only* file defining phone-normalization logic (a grep sweep for a second `function normalizePhone` or an inline reimplementation) and that every `normalizePhone` import resolves to `lib/phone.ts`, not just that the output happens to match today.
- **All search inputs become live type-ahead dropdowns.** **Delivered:** `components/center/type-ahead-search.tsx` — a 300ms debounce, a 2-character minimum query length (silent below it, no panel), and results bounded to 8, matching Reception's pre-existing `take: 8`. Full keyboard support (↑/↓/Enter/Escape) with one deliberate exception: Enter only intercepts when a suggestion is actually highlighted, so Reception's hardware barcode scanner (types a code fast, presses Enter) still reaches the underlying plain `<form>` GET submit untouched — the QR/scan path bypasses the dropdown entirely, exactly as designed. Wired into every search input found: Students, Teachers, Reception, a teacher's own student roster, a teacher's own session search, and three "pick a candidate" pickers (a teacher's block-list, a session's add-attendee panel, a class roster's enroll panel) — the latter three reuse the exact same bounded/debounced component but a selected suggestion re-navigates to the same screen with `?q=<exact code>` rather than to a different page, so the existing server-rendered candidate-and-action UI (already permissioned and audited) needed no changes at all. The teacher session list's own date filter is deliberately **not** the shared component below — it is a forward-looking "day/week/month from today" window (upcoming sessions, spec §4.2 item 2), the opposite of the shared filter's backward-looking definition, and forcing it in would have inverted the screen's whole purpose.
- **All date filters become the same component**: Day / Week (today −7) / Month (1st → today) buttons, plus a specific-date picker, a range picker, an Apply, and a reset back to today's default. **Delivered:** `components/shared/date-filter.tsx` + `lib/scheduling.ts`'s `resolveSharedDateFilter`/`lastNDaysUtc`/`monthToDateUtc` (deliberately distinct from the pre-existing `weekRangeUtc`/`monthRangeUtc`, which are real calendar-week/month windows still used by the teacher dashboard's KPIs) and `lib/validation/date-filter.ts`'s `dateFilterSchema`. Replaces the ad-hoc filters on Analytics, Expenses and Sessions (`components/shared/date-range-filters.tsx` and Sessions' bespoke day/week/month select are both deleted). Analytics/Expenses previously also offered "year" and "all-time" segments that neither this section's original wording nor §4.1 item 5's ever actually specified — dropped in favor of the range picker, which subsumes a year; there is no "all-time" equivalent, and the data-visibility window (M19) is the intended mechanism for "how far back can this role see," not an unbounded query. The default range moved from "month" to "day" on Analytics/Expenses for consistency with Sessions and with "reset to today's default."
- **Soft-delete / deactivate wherever removal could corrupt history or analytics**; hard delete only where nothing references the row. **The 404 on student delete is a bug and gets fixed.** **Delivered:** an audit of every delete path (students, teachers, classes, rooms, expense categories/expenses, catalog selections, class schedules, holidays, blocks) found the soft-delete/blocker pattern already correctly in place everywhere history could be corrupted — `studentDeleteBlockers`/`teacherDeleteBlockers`/`classDeleteBlockers` (`lib/db/students.ts`, `lib/db/classes.ts`) refuse a hard delete while attendance/payments/classes/sessions/enrollments exist, and every one of those entities already has a `setXActiveAction` escape hatch. The actual 404's root cause was narrower and different from history-corruption: `deleteStudentAction` (and, the same bug, `deleteTeacherAction`/`deleteClassAction`) never redirected after a successful delete, and the delete control lives on that very record's own detail page (`/students/[id]`) — Next's automatic post-Server-Action refresh of the *current* route re-fetched the now-deleted row and rendered `notFound()`, while the list page's own revalidation was correct but irrelevant to the page the user was actually still looking at. Fixed by redirecting to the list (`ROUTES.centerStudents`/`centerTeachers`/`centerClasses`) on success, in all three places the same shape existed — not a one-screen patch.
- **Self-registration creates a student with a full profile page** (§4.3 item 4), not a stub. **Delivered:** see §4.3 item 4 below.
- **Receptionist phone lookup during registration reuses M3's duplicate-match panel** — **not** a raw "phone → full record" endpoint. It returns only the minimum needed to confirm identity, requires an **explicit link action**, is **rate-limited**, and **never exposes another centre's private fields**. A lookup that hands back a full record on a guessed phone number is a people-enumeration API with a friendly name. **Delivered:** `PhoneLookupField` (`components/center/phone-lookup-field.tsx`), a compact phone input sitting above the add-student/add-teacher forms, calling a new `lookupPersonByPhoneAction` (`students/actions.ts`/`teachers/actions.ts`) that is the *exact same* `resolveContact`/`describeMatch` pair the full form's own submit already ran — never a second, richer lookup. Rate-limited — **since SEC-2a** in a shared Postgres store (`lib/rate-limit.ts`, `RateLimitBucket`), 20 lookups a minute per staff member and 60 per centre, enforced inside `resolveContact` itself so the add-student, add-attendee, add-teacher and new-teacher-in-a-class submits are limited exactly like this lookup (SEC-11; the M18 in-process window gave every serverless instance its own allowance and covered only two of five paths) — and returns a `MatchCandidate` — the same minimum-fields shape `MatchPanel` already renders (name + which field matched, never another centre's stored contact). Finding a match never links anything by itself: "Use this person" only pre-fills the name/contact fields the receptionist still has to submit the rest of the form with. **SEC-2a (D-02, D-08 (b)):** a phone alone now only ever finds someone already registered here (it is not a link key), and a person known only outside this centre's organisation is described without a name.

**Security decisions (SEC-2a).** The SEC-1 audit's decisions this milestone settled (`07-security-audit.md` §6; the rest stay in OD-11). Each is enforced on the server, in the module that owns it:
- **D-01 — a sign-up never claims a staff-created person by itself.** A login whose email equals a person a centre created opens a PENDING `AccountClaim`; the login has no app user (it sees `/account-pending`) until staff at a centre that knows the person approve it **in person** on `/approvals` (`approvals.manage`, audited). Approving links the login; declining detaches the email from the record so the claimant becomes a new person. Invitations link only through their token — bound to the invited email, single use, expiring, role taken from the invitation — and, under `REQUIRE_EMAIL_CONFIRMATION=true`, only for a confirmed email. Every email-based link needs `email_confirmed_at` when that flag is on; production refuses to start without it, or while Supabase auto-confirms.
- **D-02 (a) — an unverified phone is never an identity key.** Sign-up stores no phone and answers no "phone in use"; staff can attach a record to an existing person only through that person's global email (`lib/db/identity.ts`'s `isLinkableMatch`); a contact another person holds is never copied onto a new `User`. A phone or another centre's local record can still *refuse* (an already-registered student here; a staff or administrator phone in the inline new-teacher flow) — never *link*.
- **F2 — `User.contactPhone` is not an identity (D-02 (a)).** Account settings stores a person's self-declared phone on `User.contactPhone`: **not unique**, normalized through `lib/phone.ts`, and **never read** by any matching, linking or refusal function (parent access needs a code since F3 — there is no origination left) (`lib/db/identity.ts`, `lib/auth/identity-link.ts`, `lib/db/parents.ts`, `lib/identity.ts`, `lib/db/account-claims.ts` — asserted by `npm run check:account`; `check:people` proves the add-person lookup finds nobody by it). It is **not** `User.phone`, which stays staff-typed and unique: a self-typed value there would let anyone squat a number. An email change from Account settings never opens a claim either — a staff-created person's email is refused with "ask that branch"; claiming stays sign-up's path, approved in person.
- **D-03 — answered at F3** (OD-6 decided: a one-time code; "Parent role & portal" above). Its SEC-2a stop-gap, (d) "staff parent verification is off", is gone with the Verify button. **D-04 (a) — retired at F3**: a parent-phone change no longer revokes anything, because a phone is no longer the key; only explicit, audited revocation ends a link. **D-10 (a)** — stays: a suspended/archived centre or a deactivated child disappears from the parent portal.
- **D-08 (b) — every name-revealing lookup is rate-limited** in the shared store, and a person known only outside the organisation is described without a name.
- **D-09 (a)** — only an OWNER reactivates a staff membership; a MANAGER may still deactivate. **D-22 (a)** — revoking an invitation is OWNER-only, like creating one; an owner who stops being one takes their pending invitations with them.
- **D-11 (a)** — a student completes their own profile **once**; staff edits stay allowed. *(F4: a profile seeded from the account with a grade and a parent phone is complete already; the rule itself is unchanged.)*
- **D-19 (a) — deny-all for the Data API and Storage**: RLS on, zero policies, no grants to `anon`/`authenticated`, private buckets, Storage through the server's service-role client only.
- **D-21 (a)** — the seeded platform admin has its own `SEED_ADMIN_PASSWORD`. **D-23 (a)** — the student page counts relations at other branches of the **same organisation** only.
- **D-25 (b)** — centre logos are files in the private `logos` bucket, served through a signed URL (`/api/logos/[centerId]`), never a URL the server fetches. **D-27 (b)** — student photos are capped at about 1 MB and shrunk in the browser before upload; every upload is typed by its bytes (PNG/JPEG/WebP only). **D-28** — photo changes are audited (`student.photo.update`/`student.photo.remove`).

**Security decisions (SEC-2b).** The money, concurrency and anti-fraud decisions of the SEC-1 audit (`07-security-audit.md` §6); D-18, D-20's retention half (OD-2) and OD-6 stay open in OD-11 *(OD-6 decided at F3)*. Each is enforced in the data layer by direct call, not only in a form:
- **Ledger invariants are the database's too.** At most one non-voided payment per roster row (a partial unique index; the insert answers `alreadyPaid` instead of a second row), void and refund never both on one row (a CHECK), and void/refund lock the payment and re-read it before acting (SEC-05, SEC-12). Concurrent enrolments take one locked seat claim (SEC-13).
- **D-05 (c) — a settlement claims payments.** One live claim per payment (database-enforced), written in the creating transaction; creation is serialized per teacher; transitions are conditional on the status (SEC-06). This **resolves OD-8**.
- **D-06 (a) — nothing that takes money off the books is invisible.** A centre audit screen (`/audit`, `audit.view`, centre-scoped) lists voids, switches to Absent, refunds, settlement transitions and price/cut changes — the trail is carved out of the visibility window, as audit logs always were — plus present-but-unpaid check-ins (attendance, so inside the window). The receipt counts and names voided payments, refunds and unpaid attendees (SEC-07, SEC-19).
- **D-07 (c)** — cancel and reschedule are refused while active payments exist (a **refunded** payment does not block: its money is already back with the student — an interpretation confirmed at SEC-2b); cancelled and rescheduled sessions close at the end of their day (status kept, no absences); void and refund refuse them (SEC-08).
- **D-12** — a non-OWNER cannot approve or pay a settlement **they created** (the rule is the creator, not the beneficiary); an OWNER may, and the audit row says `selfApproved` (SEC-18).
- **D-13** — see "Session lifecycle" above: a status change that voids a payment needs a reason.
- **D-14 (b)** — each session freezes the centre's timezone at creation (`Session.timezone`, set and kept by a trigger); its lifecycle and its "today" read it, so a timezone edit moves nothing already created (SEC-21). New sessions follow the new zone, and the edit itself is on the audit screen.
- **D-15 (c)** — a FIXED centre cut above the price is refused wherever a cut is configured (class, one-time session, a session's override) and whenever a price is lowered (the one rule, `lib/money.ts`'s `centerCutError`); `splitShare`'s clamp stays as the backstop for older rows (SEC-22).
- **D-16 (c)** — a period settlement runs to today at the latest and spans at most 366 days; a DRAFT can be cancelled, releasing its claims (SEC-23).
- **D-17 (b)** — every money aggregate is a 64-bit SQL sum, and a **price is capped at 100,000 EGP** (`MAX_PRICE_PIASTRES`). Why that number: a real session price is tens to a few thousand EGP, so it leaves ~30× headroom while keeping one payment under 0.5 % of the `integer` ceiling every money column uses; expenses keep the 10,000,000 EGP form cap (a year's rent is real). A settlement total beyond `integer` is refused, never thrown (SEC-24).
- **D-20 (audit content)** — an audit row carries ids, amounts, counts, statuses and dates: never a person's name or contact and never text someone typed. The reason lives on the record (payment, refund, change-log row, expense, block) and the audit screen reads it there. Existing rows are kept as they are; the writer refuses a forbidden key at runtime and a gate sweeps the source. **Exempt:** `platform.catalog.*` rows, whose `nameAr`/`nameEn` are the platform's reference catalog, not a centre's people or free text (decided at SEC-2b). Retention and erasure are still OD-2 (SEC-29).
- **D-24** — an expense may be backdated within the centre's visibility window, never before it or into the future; an expense is **voided** (who, when, reason), never deleted; every expense and category change is audited (SEC-51). Reschedule and NEW_SESSION approval refuse a past date too.
- **D-26 (b)** — a one-time session priced at 0 is allowed after an explicit "I understand this session is free"; the session and its receipt are flagged (SEC-58).
- **The audit log is append-only** (SEC-60): a trigger refuses any UPDATE but a foreign key's own `ON DELETE SET NULL`, and any DELETE outside an opted-in maintenance transaction that only test cleanup uses; money actions write their audit row inside the money transaction.

**Security decisions (SEC-2c).** D-18, decided with the values below; OD-2 (retention) and OD-6 (parent verification) stay open in OD-11 *(OD-6 decided at F3)*. Enforced on the server, by direct call:
- **D-18 — self-service limits, per account and per client IP.** Through the student portal one account may hold at most **30 PENDING reservations** and, when instant-enrolling, at most **30 ACTIVE enrolments** across every centre (`SELF_SERVICE_CAPS`, `lib/db/reservations.ts` — the 31st is refused `reservationLimit`/`enrollmentLimit`; the 30 is the audit's own gate value, several times what a real student holds). The caps are counted for the caller's own identity and serialized per account, so parallel requests cannot race past them; staff enrolments are not limited by them. Reserving or enrolling is also rate-limited — **30 an hour per account, 300 an hour per client IP** — and the teacher directory's "request to teach here" **10 a day per account, 30 a day per IP** (`lib/rate-limit.ts`). The IP limits are generous on purpose: a centre's Wi-Fi or a mobile carrier's shared address is one IP. **Instant enrolment needs no separately verified account**: production refuses to start without confirmed emails (§2.1-A), which already covers it; on dev, where *Confirm email* stays off until OD-1, it would only block testing. **CAPTCHA** stays an M20 item (it needs the domain).
- **One pending teach-here request per (requester, centre)** — a second is `alreadyRequested` — and the request is refused on the server to anyone who already teaches somewhere (`alreadyTeaching`; the directory page's redirect is not the boundary). Each Approvals queue shows one page of **50** with a count of the rest (SEC-25).
- **A typed `%` or `_` is never a wildcard** (SEC-61). A search ignores them (no name, code or phone contains them); a duplicate name is judged by the one name key — trimmed, inner spaces collapsed, case ignored — so `Cash_` and `Cash1` are different payment-method names while `cash` and `  Cash ` are the same (`lib/like.ts`).
- **A student completing their profile chooses from the grades the centre offers**, under the centre's own names — the same rule as the receptionist's form (SEC-49).

**Two security fixes (M12).**
- **Teacher detail leak.** A centre Owner or Manager viewing a teacher **must not see which other centres that teacher works at.** The teacher's portability is theirs, not their employer's, and this is the same boundary `05-phase-2-backlog.md` entry 2 refuses to cross for scheduling.
- **Role-change session invalidation.** Changing a user's role **must invalidate or re-resolve their session immediately**. A demoted user keeping their old rights until a cookie expires is a permission system with a grace period nobody agreed to.

**Excused removed (R1 — reverses the M10 per-class toggle).** Attendance has exactly **three** statuses: **PRESENT, LATE, ABSENT**. The fourth, "Excused", is gone from the whole system — the enum value, `ClassGroup.allowExcused` and its Classes-screen toggle, the roster button, the server-side refusal path, and every count in receipts, analytics, the print view and the teacher/student/parent portals. The reason: an excused student still did not attend and still paid nothing (§5 "No debt"), so for every number this product computes — money, attendance rate, the absence streak — "excused" behaved exactly like "absent" while adding a fourth button to the busiest control in the app and a per-class setting nobody needed to configure. The migration converted any existing excused row to ABSENT (seed/demo data only — no production data existed). **Absence streaks are unchanged in effect:** `consecutiveAbsenceCount` always counted only ABSENT rows and stopped at any other mark, so an excused session used to *break* a streak; with three statuses, PRESENT/LATE break it and ABSENT extends it. `ClassGroup.attendanceRequired` was dropped in the same change — it was stored, shown on the class form, the teacher's new-class request and the Approvals card, and **read by no behaviour at all**. Old `ChangeRequest` payloads that still carry the key are tolerated (readers ignore it). Automatic late/absent marking and session closing are **R2**, not part of this decision. Gated by `npm run check:payment-methods`.

**Payment methods configurable per centre, label frozen on payment (R1).** The hardcoded `PaymentMethod` enum (Cash / InstaPay / Wallet / Visa) is replaced by **`CenterPaymentMethod`** rows — one centre-entered `name`, like `Room.name` (a person-facing label, not a bilingual catalog entry). A new centre is created with **Cash, InstaPay and Vodafone Cash**; the migration gave every existing centre Cash / InstaPay / Wallet / Visa so each historical payment kept a row to point at. A `Payment` stores **`paymentMethodId`** *and* **`methodLabelSnapshot`**, the method's name **frozen at record time** — the same principle as the money snapshots (CLAUDE.md rule 2): renaming a method later never relabels a recorded payment, and history always displays the snapshot. Three rules, all server-side in `lib/db/payment-methods.ts`:
- **At least one active method, always.** Deactivating or deleting the last active one is refused (`lastActiveMethod`); the check locks the centre's method rows so two concurrent deactivations cannot together leave none.
- **Referenced → deactivate, never delete** (the M18 convention). Delete hard-deletes only a method no payment references; otherwise it deactivates instead, and the FK (`RESTRICT`) backs that up. A deactivated method disappears from every picker; history still shows its snapshot label.
- **`recordPayment` resolves the method inside its own transaction, filtered by `centerId` AND `active`.** Another centre's method id or an inactive one is refused (`invalidMethod`) whatever the client sent. `lib/money.ts` is untouched — a method carries no money.

Managed at **Settings → Payment methods**, gated by the same `center.settings.edit` action as rooms (no new matrix action); create / rename / activate / deactivate / delete each write an `AuditLog` row. Gated by `npm run check:payment-methods`.

**Session lifecycle — a closed session is a final record (R2; reverses M5's "attendance freely editable" once a session is closed).** M5 let attendance be corrected at any time, forever. R2 keeps that only while a session is **live** and makes a closed session immutable:
- **Closed means closed.** Once `Session.closedAt` is set, the session accepts **no** attendance change, no new attendance, no payment, no void, no refund, no cancel, no reschedule and no cut override — refused by the data layer on a direct call, not merely hidden (`lib/db/session-lifecycle.ts`'s `ensureSessionOpenOrAutoClose`, called first by every write path). **There is no reopen and no delete of a closed session** — no code path anywhere sets `closedAt` back, and nothing deletes a closed session. *(Revised R4: the class-sessions engine now deletes **pristine** upcoming sessions — never closed, never started, nothing recorded — when a class's slots, period or status change, and a class that never ran may be deleted with its untouched sessions; its delete-guard re-asserts `closedAt: null` in the `WHERE` itself. A closed session is still never deleted, §5.1 "Resync on edit". R5 adds one more delete — a pristine, future manual or one-time session, by staff — under the same predicate, so a closed session still never qualifies, §5.1 "Manual and one-time sessions".)* Closing sets the stored `status` to `COMPLETED`, so stored and displayed status agree.
- **End session (manual).** Staff with `session.close` (OWNER/MANAGER/RECEPTIONIST by default, §3) end a session from its detail page, behind a confirmation that says it cannot be undone. Refused before the session starts, and on a cancelled, rescheduled or already-closed one. Audited as `session.close`.
- **Automatic close at end of day.** A session nobody ended closes at the **end of its calendar day in the centre's timezone** (`CenterSettings.timezone`). There is no cron: the **next read or write that touches it** closes it — `closeMode: AUTO`, `closedAt` = local midnight — and a write that triggered it is refused. The page says so: *"closed automatically at the end of the day because it was not closed manually."* The automatic close writes its own `session.close` audit row with no actor.
- **Automatic Late.** A check-in decides its own status: within the class's late threshold (the centre's default if the class has none) of the start it is **Present**; from the minute after, **Late**. No check-in surface offers a status picker.
- **Automatic Absent.** Closing a session (either way) gives every **active, enrolled** student with no roster row an **Absent** row, recorded by the system — exactly once (closing twice, or two closes racing, creates no duplicate). A student never enrolled and never checked in gets nothing; an enrolment made after the session's day does not count.
- **Switching a paid student to Absent voids their payment.** While a session is live, changing a student who holds an active payment from Present/Late to Absent **voids that payment in the same transaction** — a void, not a refund (§5 "Void vs. refund"): the money is simply not counted, in the receipt or in analytics. **The reason is required** *(SEC-2b, D-13 — this reverses R2's "optional": a void with no reason was an untraceable way to take money off the books, SEC-20)*; zod, the Server Action and the data layer each refuse the change without one. A status change that voids nothing keeps the reason optional. The roster says so plainly before the click, and asks for confirmation. It needs `payment.void` as well as `attendance.correct`. Absent → Present/Late creates no payment; staff record one normally. A status change never creates or recomputes money.
- **Every live status change is logged** in `SessionAttendanceChange` (student, from → to, when, who, optional reason, the voided payment if any) and shown at the end of the receipt — on screen and printed — as **"Changes during session"**; `AuditLog` keeps the audit trail (`attendance.correct`, plus `payment.void` when a payment was voided).
- **Settlements need closed sessions.** A session settlement is refused until the session is closed; a period settlement counts only payments of sessions already closed, and says so on its form. A void or refund after the fact adjusts an unpaid settlement only if that settlement had actually counted the payment (§5 "Settlement totals"). A still-live session left out of a period is picked up by a later settlement over the same days once it has closed — each payment is claimed once (SEC-2b, D-05; formerly OD-8).

Gated by `npm run check:session-lifecycle`.

**Joinable rooms / room sets (R3).** A centre declares, per room, which of its other rooms it **can be combined with** — chosen in that room's **Add room / Edit room dialog** (Settings → Rooms; there is no separate combinations area), saved with the room's name and capacity as one diff in one transaction — a `RoomLink`, symmetric (it shows on both rooms' dialogs and in the list's "Combines with" column), stored once per pair, same centre only, never a room with itself. A class or a session then uses **one primary room plus any extra rooms, each linked to the primary**: a **star, not a transitive closure** — with Room 1–Room 2 and Room 2–Room 3 linked, Room 1 + Room 3 is not allowed unless Room 1–Room 3 is linked too (`lib/rooms.ts`'s `isValidCombination`, the one owner of the rule). The set's **effective capacity is the sum of its rooms' capacities** (`effectiveCapacity`); a room with capacity **0** means "not configured" and makes the whole set uncapped (an unknown seat count cannot be summed into a limit). **While a session runs, every room of its set is busy** — a session in Room 2 alone clashes with one on Room 1 + Room 2, and vice versa. A class's sessions inherit the class's set (R4: and follow a change to it, §5.1 "Resync on edit"); a single session may use a different valid set (reschedule, or "Rooms" on the session) without touching its class. Unlinking a pair, or deactivating/deleting a room, is refused while an **active class** or a **non-closed future session** uses that combination, and the refusal says how many **and names them** (the classes; the sessions by day and time — the first five of each) and saves nothing, not even the room's new name. A link to a room that has since been deactivated is kept (a removable chip) but a new link to an inactive room is refused. Links and unlinks are audited (`room.link`/`room.unlink`). No new permission: `center.settings.edit` gates links, `class.manage`/`session.manage` the sets.

**Class capacity removed (R3; reverses M15's "min(class capacity, room capacity)").** `ClassGroup.capacity` is dropped. A class's seat limit is **only** its room set's summed capacity (`lib/capacity.ts`'s `enrollmentCap(roomSetCapacity)`), checked by every enrolment path (`reserveOrEnroll`, `confirmReservation`, the staff `enrollStudentAction`, both approvals queues). A class with no room is uncapped; **new and edited classes must have a primary room** (zod + form) — existing rows with none stay valid until next edited. Lowering a room's capacity below a class's roster **removes no one**; it only refuses new enrolments, with a message naming the fix (a bigger room, or combine another room). Attendance stays **uncapped**, unchanged. A session's own room set never changes its class's enrolment cap — enrolment belongs to the class — it only changes which rooms that session keeps busy and the seat count it shows. The teacher's new-class request forms no longer ask for capacity; old request payloads that carry it are read and approved unchanged.

**Double-booking needs explicit confirmation under WARN, and is refused under DENY (R3).** Every slot-writing action — a class's weekly slots, a class's teacher/room-set change, reschedule, a session's room change, the session generator, NEW_SESSION approval — takes a `confirmConflicts` flag. With conflicts (room **or** teacher, overlap = `start < otherEnd && end > otherStart`, so back-to-back is free; cancelled sessions and the original slot of a rescheduled session occupy nothing; closed sessions do): **DENY** refuses, flag or not; **WARN** refuses **with the conflict list** unless the flag is set, and with it saves and writes a `schedule.conflict.confirm` `AuditLog` row listing every confirmed conflict. The refusal always carries the list — never a generic error — and a direct action call cannot skip it. The forms preview conflicts live (`checkSlotConflictsAction`, advisory only) and show them in `SlotConflictNotice` with an "I understand, create anyway" checkbox the submit waits for. This replaces the pre-R3 WARN behaviour of saving silently-flagged double-bookings. Gated by `npm run check:rooms`. *(R3 also had the generator create non-conflicting occurrences and hold conflicting ones back; R4 removed the generator, and a class's whole period is now one decision — "Whole-range conflicts are one decision" below. R4 also made `confirmConflicts` **required** on every data-layer slot writer: the omitted-flag script path is gone.)*

**Class periods and centre terms (R4; replaces the rolling-window generator).** A class has a **period** — `ClassGroup.startDate`/`endDate`, date-only, inclusive, stored as UTC-midnight day markers exactly like `Session.date`. The class form sets it in one of two ways: **choose a term** (one of the centre's active `CenterTerm` presets, Settings → Terms) or **custom dates**. A term only *fills* the dates: they are **copied** onto the class, there is no foreign key, and renaming, redating, deactivating or deleting a term never moves a class (so a term delete is always a hard delete). Terms may overlap ("Full year" and "Semester 1" do), are unique per centre by name case-insensitively, and follow the same period rule as a class: the end on or after the start, a span of at most **400 days** (`lib/scheduling.ts`'s `classPeriodError` — one rule for zod, the data layer and terms). A centre term is a *preset*, not the `AcademicYear`/`Term` entity `05-phase-2-backlog.md` entry 11 still describes — nothing else (enrolment, billing, analytics) hangs off it.

- **Sessions exist for the whole period.** Creating a class creates, in the **same transaction** as the class and its weekly slots, one session per matching `ClassSchedule` weekday from `max(startDate, today in the centre's timezone)` through `endDate`, skipping the holiday calendar, each carrying the class's room set (R3) and a frozen `priceSnapshot`. **No session is ever created in the past** — nor today's slot whose start has already passed: a session that never really happened would otherwise be closed at the end of the day with every enrolled student marked Absent (R2). `lib/db/class-sessions.ts` is the only module that creates, re-fits or removes a class's sessions; `@@unique([classGroupId, date, startTime])` stays as its idempotency backstop, so any re-run with nothing changed creates and deletes nothing.
- **The create dialog has no slot rows yet** (R6 re-lays it out), so from the UI a new class starts with no sessions and each slot added on the class page creates its whole period's sessions; the data layer (`createClassWithSessions`) takes the slots with the class and is what the seed and the gate use.

**The session generator is removed (R4).** The "Generate sessions" buttons (on `/classes` and a class's page), the rolling 42-day window, `app/api/cron/generate-sessions`, `CRON_SECRET` and the planned Vercel cron entry are gone (§2.1.C). There was no generation-window setting to remove — the window was a code constant. The holiday calendar stays and is still skipped whenever sessions are created. Nothing in the product runs on a schedule any more (the R2 end-of-day close was already lazy).

**Whole-range conflicts are one decision (R4).** Every session a class write would create or re-room — across the whole period — is checked against the centre's dated occupancy as **one** list, under R3's contract: **WARN** with conflicts and no `confirmConflicts` → refused with the **full** list and **nothing written** (not even the class); WARN with the flag → everything written and one `schedule.conflict.confirm` audit row listing every confirmed conflict; **DENY** → refused whatever the flag. There is no partial creation and no "held back" state. Weekly slots are no longer compared against weekly slots: with every active class's sessions materialized, the dated sessions are the whole truth — and they know that two classes on the same weekday slot with non-overlapping periods do not clash. The forms preview exactly this list (`checkSlotConflictsAction` → `previewClassSessions`, the same computation the save runs), and one "I understand" covers the whole range. `confirmConflicts` is a **required** parameter on every data-layer slot writer (`rescheduleSession`, `updateSessionRooms`, `resolveSessionRequest`, `createClassWithSessions`, `updateClassWithSessions`, `writeClassSlot`, `reactivateClass`, `materializeClassSessions`, `resyncClassSessions`) — no default, no "missing means save".

**Resync on edit: pristine sessions follow, the rest are kept and reported (R4; resolves OD-9).** Editing a class's weekly slots, period, teacher or room set **resyncs its future sessions** (not yet started, in the centre's timezone) in the same transaction as the edit. A session is **pristine** only if ALL hold: SCHEDULED, not closed, no attendees, no payments, no settlement, no ratings, no per-session share override, no description, not rescheduled from or to, its teacher **and** room set still equal the class's values *before* the edit, and — R5 — it was not made by hand (`isManual`) (`sessionDisqualifiers` — one definition for resync, deactivation, holidays and the class page). Pristine sessions that no longer match the class are deleted; pristine ones that still match take the new teacher and room set; missing dates are created. **Anything not pristine is left exactly as it is** and reported — on the save ("3 upcoming sessions were kept because they already have records or custom changes") and on the class page, which lists them for staff to cancel or reschedule by hand. Shortening the end date removes only pristine sessions after it; extending it adds sessions. Deletes re-assert pristineness in their own `WHERE`, so a check-in landing mid-resync is never deleted under it. This answers **OD-9** ("should a class's room-set change follow its already-generated sessions?"): yes — its untouched upcoming sessions follow, under the confirmation contract; sessions with records or custom changes never move on their own.

**A class price edit reprices its open sessions (SYS, user-confirmed default).** Editing a class's **price** reprices the class's own sessions that are dated **today or later** (the centre's day), **not closed**, not cancelled, not a rescheduled original, and hold **no payment at all** (voided ones included) — extra (manual) sessions of the class too, since their price was the class's. A session that already holds any payment **keeps its price**, and so does one whose own FIXED cut override would exceed the new price (D-15's one money rule). **Recorded payments are never touched** — CLAUDE.md rule 2 is about payments: each froze its own `priceSnapshot`, `centerShareSnapshot` and `teacherShareSnapshot` and keeps them. Before this decision a session froze the class price when it was created, so raising a class's price left every already-materialized session (a whole term's worth, since R4) charging the old one — the opposite of what a centre means by "the price is now 150". The edit is audited on its `classGroup.update` row with the counts (`after.reprice`: `repriced`, `keptWithPayments`, `keptCutAbovePrice`), and the save notice says how many upcoming sessions took the new price and how many kept their old one. **The centre cut needs no equivalent change**: a payment already reads the cut (the session's override, else the class's current cut) at the instant it is recorded. One owner: `lib/db/class-sessions.ts`'s `repriceClassSessions`, inside the class edit's transaction — it locks the candidate sessions and re-reads the payment fact after the lock, and `recordPayment` reads the session price under its own locks (`lockAttendeeRow`), so a payment racing a reprice either lands first (and keeps that session at the old price) or reads the new one. Gated by `npm run check:class-periods` (section 10).

**Deactivate, reactivate, delete (R4).** A **deactivated** class disappears from every forward-looking surface — class pickers, student Discover, reservation and enrolment flows (including both approvals queues and NEW_SESSION approval), today's and upcoming session lists (reception, the dashboard, the teacher's and the student's/parent's upcoming sessions) and conflict detection — enforced at the data layer (`OPEN_CLASS_SESSION`, `active: true` filters), while its history (closed sessions, attendance, payments, ratings, settlements, analytics, receipts, student attendance history) stays exactly as visible as before.
- **Deactivate** — one transaction: `active = false`, its pristine future sessions deleted, every other future session **cancelled** through the existing `cancelSession` rules (attendance and payments never touched). Sessions that already started or closed are not touched. Enrolments stay ACTIVE, so reactivating restores the class's roster and regenerates its pristine sessions — but a session deactivation **cancelled** (it had records) stays cancelled. Since SYS the list's Deactivate asks first, saying so. Audited (`classGroup.deactivate`, with the counts).
- **Reactivate** — only while the period has not ended (otherwise refused: extend the end date first); it regenerates the sessions from today through `endDate` under the full confirmation contract, and a refusal leaves the class inactive. Audited.
- **Delete** — only for a class that **never ran**: no session started or closed, none with attendees, payments, a settlement, ratings or a reschedule link, and no enrolments or reservations of any status (`classDeleteBlockers`). Then its pristine future sessions and weekly slots go with it. Otherwise it is refused **by direct call**, and the class page names what stops it and offers Deactivate instead. Audited.

**Holidays after the fact (R4).** Adding a holiday also deletes that day's **pristine** sessions of every active class, in the same transaction; sessions with records or custom changes are kept and counted for staff to cancel by hand. Removing a holiday does not recreate sessions — that is **OD-10** (§2.2). Gated by `npm run check:class-periods`.

**Manual and one-time sessions (R5).** Staff add a session by hand from the Sessions tab — **"New session"**, one entry point with two modes (a segmented control), gated by the existing `session.manage` matrix action (no new role check; teachers still ask through the M10 `NEW_SESSION` request). Both modes are written by `lib/db/class-sessions.ts` (`createManualSession`, `createOneOffSession`), in one transaction with their extra rooms, a `session.create` audit row (`mode: extra | oneOff`) and — when confirmed — the `schedule.conflict.confirm` row.
- **An extra session on a class ("For a class").** Pick an **active** class; its teacher, room set and the time of its slot on that weekday are the defaults, and the teacher may be overridden (a substitute — still an active teacher of this branch). **Price and centre cut are the class's, exactly as for a generated session**: `priceSnapshot` is frozen from the class at creation, and the cut is read from the class at payment time — R5 adds no per-session price field. Its enrolled students are its roster and are marked Absent at close like any class session (R2). Refused if the class already has a session at that exact date and start (`duplicateSlot`).
- **A one-time session ("One-time session").** Belongs to **no class** (`Session.classGroupId` null). Its own **title** (required, ≤ 80 characters), optional **subject** and **grade** (catalog entries this branch has selected and keeps active, labelled through the live-join display-name rule), **teacher**, **room set** (a required primary plus linked extras, R3), date and time, **price** (EGP → piastres through `lib/money.ts`'s parser) and **centre cut** (FIXED or PERCENTAGE, defaulting to `CenterSettings.defaultShareType`/`defaultShareValue`). Everyone attending is a **drop-in** — nobody is enrolled, so nobody is marked absent at close and there is no absence streak. Late threshold = `CenterSettings.defaultLateThreshold`. A one-time session **carries its own cut**: `recordPayment` freezes it from the session's own `centerShareType`/`centerShareValue` and **refuses** (`missingCut`) if either is missing — money is never guessed at; `lib/money.ts` is untouched. The cut may be changed while the session is open (a recorded payment never moves) but never cleared (`cutRequired`). The invariant — no class ⇒ title, teacher, price and both cut fields set — is enforced in `lib/db/sessions.ts` (`oneOffSessionShapeError`). Discover and reservations never offer one (there is no class to enrol in).
- **No backdating, ever.** The date must be today or later **in the centre's timezone**; a time earlier today is allowed. Refused by the data layer on a direct call (`pastDate`), not only by the form.
- **Holidays do not block** a manual or one-time session; the form shows a non-blocking notice when the date is on the holiday calendar.
- **Conflicts** follow R3's contract: room set **and** teacher, `confirmConflicts` required, WARN refuses with the list until confirmed, DENY refuses. A manual session is checked against every booking that day — its own class's sessions included — and two one-time sessions see each other.
- **`isManual` protects them from the engine.** A session made by hand — an extra session, a one-time session, or an approved `NEW_SESSION` request (`resolveSessionRequest` now sets it) — carries `isManual = true`, and `isManual` is part of the pristine predicate: **no resync, slot move, period change, end-date shortening, holiday insertion or class edit ever deletes or rewrites it**, and the class page does not list it as "kept". Deactivating its class treats it by the normal rule — deleted if otherwise pristine, cancelled if it has records or a different teacher/room set. A holiday added later counts it with the kept sessions so staff can cancel it by hand.
- **Delete.** Staff may delete a manual or one-time session only while it is **pristine and in the future**: not started (centre time), SCHEDULED, not closed, no attendee, payment, settlement or rating, no reschedule link, and — on a class session — no cut override. Otherwise only **Cancel** (the existing rules). Refused by direct call (`deleteManualSession`, under a row lock, the "untouched" predicate re-asserted in the delete's own `WHERE`); audited as `session.delete`. **A closed session is never deletable.**

Gated by `npm run check:one-off-sessions`.

**Creating a class in one step, a new teacher inline, searchable pickers, one time control (R6).** A UI + orchestration revision over features that already existed; no schema change.
- **One transaction, one engine.** Creating a class writes the class, its extra rooms, its **weekly rows** (`ClassSchedule`) and **every session of its period** in ONE transaction through the existing engine (`lib/db/class-sessions.ts` → `resyncClassSessions`); there is no second implementation of session creation. A new class needs **at least one row**; two rows on the same weekday must not overlap (half-open, so back-to-back is fine) — the one rule is `lib/scheduling.ts`'s `weeklySlotsError`, used by the zod schema (`classSlotsSchema`) and by the data layer by direct call. The whole range stays **one** conflict decision (R4) under R3's required `confirmConflicts`: the live preview (`checkSlotConflictsAction`'s new `newClass` kind, the engine's own `computeSync`) lists every clash across the period, WARN refuses with the list until the one tick is given, DENY refuses, and a confirmed write audits `schedule.conflict.confirm`. Editing an existing class is unchanged (R4's resync and kept-sessions report); its weekly slots keep their own editor on the class page.
- **A new teacher inline is created atomically.** In the New class dialog the Teacher section offers **Select teacher** and **New teacher**. New teacher shows the Add teacher form's fields and runs ONE action, `createClassWithNewTeacherAction` → `createClassWithNewTeacher`, which in one transaction creates the teacher (`lib/db/teacher-membership.ts`'s `addTeacherMembership` — the one teacher-creation path, which the Add teacher dialog also calls) and then the class + rows + sessions. **Any** error — validation, a phone awaiting confirmation, a refusal, a DENY or unconfirmed-WARN conflict, an engine failure — rolls the whole transaction back: **no orphan `User`, `Membership` or audit row, ever.** The answer says which half refused ("The teacher could not be created: …" / "The class could not be created: …") and the form keeps everything typed.
- **Identity rules are unchanged (CLAUDE.md rule 4).** A phone/email that already belongs to a person comes back as a **match** and nothing is written until staff press **Use this person**; then a **new `Membership`** is attached to the existing `User` (never a second `User`). A person who **already teaches here** is not recreated — the form offers to select them. A phone that belongs to a **platform administrator, or to a staff member (OWNER / MANAGER / RECEPTIONIST / ACCOUNTANT) of this branch, is refused** in this flow, before the match is even offered, so the class dialog cannot be a back door to a second role. *(Decision taken in R6, for review: the Add teacher dialog itself is not redesigned and still lets a staff member be linked as a teacher after its match panel; only the inline flow refuses.)*
- **Permissions.** The combined action needs **both** `teacher.manage` and `class.manage`; the data-layer function takes the caller's permission check and refuses by direct call if either is missing, before anything is read or written. Audit rows for both entities (`membership.create` with `via: class.create`, `classGroup.create`) are written in the same transaction.
- **Searchable pickers.** The teacher picker in every class and session dialog (and the class picker in New session) is the shared searchable combobox: type to filter by name **and** phone (the phone through `lib/phone.ts`, any format), keyboard-navigable, with a "no results" state and a clear button. The list is the centre's active teachers, scoped by `centerId` on the server; the client only filters. The room picker is unchanged.
- **One time control, stored as before.** Times remain **24-hour `"HH:mm"` strings** in the database; every start/end field in the product (class rows, New session, Reschedule, the schedule builder, the teacher portal's requests) is the shared `TimePicker`, which accepts `4`, `4pm`, `16:30`, `4:30 pm`, Arabic-Indic digits and ص / م, refuses anything else with an inline error (never coercing), and suggests the end when a start is chosen. One parser (`lib/time-input.ts`), one display formatter (`lib/format.ts`).
- **Consistent actions.** The session detail's Reschedule · Edit rooms · Cancel · Delete are one action bar (same height, grouped, destructive in colour only, wrapping cleanly at 375px); Reschedule, Edit rooms and the confirmations open the shared dialog shell.

Gated by `npm run check:class-creation`.

**Reception desk reworked (R7).** UI + orchestration over existing features; **no schema change, no new permission** (it reuses `reception.use`, `attendance.record`, `payment.record`, `session.close`). The full decision is §5.1 "Reception check-in — session-first, scan-then-confirm". What changed in behaviour, not just layout: the reception check-in now **refuses a blocked student** (before R7 only the roster's add-student paths did — a receptionist could check a blocked student in), **re-validates that the session is today's and still open**, and answers a concurrent duplicate scan from a second desk as "already checked in" instead of an error page; "today" on the desk is the centre's day, not the UTC day (R7b extends that to every screen — §5.1). Gated by `npm run check:reception`.

**ID-card styling (R9).** The card editor gained styling and lost two bugs. **No schema change** — everything lives inside the existing `CenterSettings.cardLayout` JSON, every new key optional, "absent" meaning today's look (shape: `01-data-model.md`; the editor: `04-design-system.md` §11.6). (1) **Text style, per text element** (branch name, student name, grade, student code): size, **weight** (Normal / Bold), **alignment** (Start / Center / End — *logical*, so Start is the right edge on an Arabic card), **colour** and **font**. Alignment needs a box to align within, so a text element now has an optional **box width** (a percentage of the card, defaulting to the span up to the next thing on its row); a Start-aligned text needs no box, which is why every older layout renders exactly as before. (2) **Fonts are a closed list of three** — the card font (Cairo, the only web font the app loads), a system sans and a system serif — chosen because they carry Arabic and Latin glyphs; nothing new is downloaded, and the stored value is a *key*, never a CSS string. (3) **Custom branch text** — an optional string (max 60) on the branch-name element; blank prints the centre's real name, which is also the editor's placeholder. It is one string, the same in both locales: a deliberate override, not a translation. (4) **Card colours** — the background (default: the navy gradient), an optional **header band** (30% of the card height, behind the logo and branch name; its colour defaults to the theme colour), and the **bottom line** (default: the theme colour). Uploaded logos are never recoloured. Each has swatches (the first is the theme colour), a colour input and a reset. (5) **Contrast is a warning, never a gate** — a text whose colour falls below WCAG AA (4.5:1; 3:1 for large text) on what it sits on (the header band when the text is inside it, otherwise the background — the worse gradient stop) is listed under the preview; saving is never blocked. (6) **One renderer.** The editor's preview, the print view and the stored file are all `renderIdCardSvg()`; nothing else draws a card. (7) **Strict on write, tolerant on read** — `cardLayoutSchema` refuses unknown keys, a colour that is not `#RRGGBB`, an unlisted font or alignment, an oversized text and out-of-range sizes, and stores no raw CSS; `resolveCardLayout` drops anything it does not recognise. (8) **The QR payload and its parser are untouched** (the locked decision above). *Interpretation recorded:* "accent/header colour" is read as an optional header band, because the card had no other accent surface; with the band off the card is exactly the pre-R9 card. Gated by `npm run check:card-layout`.

**Users & Roles lists centre staff only (R9).** `/settings/staff` shows, invites and re-roles **Owner, Manager, Receptionist and Accountant** — the four `CENTER_STAFF_ROLES`. **Teachers are managed only on the Teachers page.** This is a data-layer rule, not a hidden column: the screen's reads (`memberships.listStaffWithUser`, `invitations.listStaff`) pin the role set, the invite and role dropdowns do not offer TEACHER, and `createInvitationAction` / `changeMemberRoleAction` refuse a TEACHER role by direct call (as does re-roling or activating/deactivating an existing teacher through this screen). The **permissions matrix keeps its Teacher column** — it controls what teachers may do, which is a different question from who they are. Existing TEACHER memberships and invitations are untouched: they simply are not listed here (a pending TEACHER invitation can still be accepted from its link). Gated by `npm run check:card-layout`.

## 7. Acceptance criteria (test with real scenarios, not button clicks)

These are the QA gates. If these pass, Phase 1 is trustworthy.

1. **Shared teacher, two centers:** Center A and Center B share teacher T. T's portal shows a correct combined schedule; **zero** Center-A data leaks into Center B and vice versa.
2. **Shared student, two centers:** One student identity, two separate enrollment/payment histories, no cross-leak.
3. **Money snapshot:** Record a payment; change the class's center-cut; confirm the old payment's numbers are unchanged and the new session uses the new cut.
4. **Fixed vs percentage cut:** A class with `FIXED 15 EGP` and a class with `PERCENTAGE 15%` both compute center/teacher shares correctly on a 120 EGP session.
5. **Drop-in:** Add a non-enrolled student to a session once; attendance + payment recorded with no enrollment created; they don't appear as enrolled next session.
6. **Capacity:** A full class blocks further enrollment per rule.
7. **Conflict:** Two classes can't book the same room at the same time — including any room of a combined room set (R3); a teacher can't be double-booked. Under DENY refused; under WARN refused with the conflict list until explicitly confirmed, which is audited (R3, `npm run check:rooms`).
8. **Attendance correction:** Only permitted roles can change a recorded status; the change is audited.
9. **Receptionist denied profit:** A receptionist cannot view center profit by UI or by direct URL/API.
10. **Tenant isolation by URL/API:** A Center-X user cannot read a Center-Y record by manipulating an ID in the URL or API call — **denied**.
11. **Cancelled session:** Roster, schedules, and any financial/attendance effects update correctly; change is audited.
12. **Duplicate registration:** Registering an existing phone/email triggers the match/merge workflow, not a duplicate person.
13. **Consecutive absence:** After marking a student absent 3 sessions in a row, the session receipt and profile show "absent 3 times in a row."
14. **Performance:** High-volume attendance entry during a rush stays responsive.
15. **RTL:** Every screen renders correctly in Arabic RTL and English LTR.

**Criteria added by M11–M19** (each gated by the `check:*` script named in `03-build-order.md`):

16. **Reception scan shows the photo (delivered M18):** scanning a card (or selecting a search result) at Reception displays the student's photo — the anti-impersonation control §5.1 "Check-in & the QR payload" names. See §7.1 for the fix.
17. **Cancelled session refuses money and attendance (delivered M15, `npm run check:enrollment`):** recording attendance or a payment on a `CANCELLED` session — or an already-**rescheduled** one — is refused server-side, by direct call to `lib/db/attendance.ts`/`lib/db/payments.ts`, not merely hidden.
18. **Branch isolation is still centre isolation:** with an organization holding two branches, a user scoped to Branch A cannot read a Branch B record by URL/API; the org roll-up returns exactly the sum of the two per-branch figures.
19. **Owner-only granting:** a MANAGER cannot change the permission matrix, assign a role, or widen a member's branch access — by UI or by direct action call.
20. **Role change invalidates the session:** a demoted user's next request resolves the new role, with no window where the old rights still work.
21. **Teacher's other centres stay hidden:** a centre Owner/Manager viewing a teacher sees nothing about that teacher's memberships elsewhere, by UI or by API.
22. **Refund arithmetic (delivered M14, `npm run check:settlements`):** refunding a payment reduces collected revenue and that payment's centre and teacher shares by exactly its amounts, leaves the original row's money fields untouched, and creates no balance anywhere.
23. **Settlement totals derive from frozen snapshots, and are correct by status (delivered M14, `npm run check:settlements`):** a settlement's total equals the sum of the frozen `teacherShareSnapshot` values in its scope, stays correct after the class's cut changes, live-adjusts when a payment in a still-unpaid (DRAFT/APPROVED) settlement's scope is refunded, and never changes once the settlement is PAID (§5 "Settlement totals: frozen at creation, live-adjusted while unpaid, immutable once PAID").
24. **Cooling-off holds (delivered M15, `npm run check:enrollment`):** a rejected student re-requesting the same class within 7 days is refused, and told why.
25. **Capacity split (delivered M15, `npm run check:enrollment`; the cap is the room set's summed capacity since R3, `npm run check:rooms`):** enrolment past the cap is refused (naming whichever fix actually applies) while marking attendance past that same cap succeeds — proven in the same test run.
26. **Reschedule needs the whole window (delivered M15, `npm run check:enrollment`):** a target slot whose room is free at the start but busy before the end is refused.
27. **Rating anonymity (delivered M17, `npm run check:ratings`):** the teacher-facing aggregate exposes an average only — no rater identity and no count — through the API as well as the UI, proven by a static sweep of `lib/db/ratings.ts`'s own exports plus a direct call to `teacherRatingAverage`/`teacherRatingAverages`, not just a UI check.
28. **Visibility window is a data-layer denial (delivered M19, `npm run check:visibility`; in the scoped helpers since SYS/SEC-62):** a centre role cannot read out-of-window analytics/sessions/attendance/payments/expenses by direct URL or API — asserted for OWNER, MANAGER, RECEPTIONIST and ACCOUNTANT through the real `scoped()` helpers; settlement and audit rows in the same range remain readable; nothing is deleted.
29. **A closed session is final (delivered R2, `npm run check:session-lifecycle`):** a closed session refuses attendance, payment, void, refund, cancel, reschedule and cut override by direct call; an unclosed session whose day ended closes automatically on its next touch and its enrolled no-shows become Absent exactly once; a late check-in is stored Late without anyone choosing it; a live Present→Absent on a paid student voids the payment atomically and logs the change.
30. **A class period is the calendar (delivered R4, `npm run check:class-periods`):** creating a class for 9 Oct 2026 – 1 Apr 2027 with two weekly slots creates exactly the matching dates from today, none in the past and none on a holiday, on the class's room set; a whole-range conflict is refused with nothing written until confirmed (WARN) or outright (DENY); editing the class resyncs its pristine upcoming sessions and reports the kept ones, and a re-run changes nothing; a deactivated class has no upcoming sessions and is in no picker or upcoming list while its history stays in analytics; a class that ran, or has enrolments, cannot be deleted by direct call.

### 7.1 Verified gaps (static check at M10 — closed at M15 and M18)

Two of the criteria above were checked against the code as it stood at M10 and **failed then**. Criterion 17 closed at **M15**; criterion 16 closed at **M18**.

- **Criterion 17 — closed at M15.** `cancelSession` used to flip `Session.status` to `CANCELLED` with nothing downstream re-reading it — `setAttendanceAction`, `addExistingAttendeeAction`, `addNewAttendeeAction`, `checkInAction` and `recordPayment` each loaded the session but never checked its status, and the UI only disabled the Cancel button while the roster below it still rendered live controls. `lib/db/attendance.ts`'s `createAttendance`/`updateAttendanceStatus` and `lib/db/payments.ts`'s `recordPayment` now refuse both — a `SessionClosedError` thrown from one choke point (extended in the same pass to cover an already-**rescheduled** session too, since M15 also changed `rescheduleSession` to create a new row rather than mutate the original in place) — and the session detail page renders the roster read-only whenever `deriveSessionDisplayStatus` reports `CANCELLED` or `RESCHEDULED`. `npm run check:enrollment` asserts the direct-call refusal, not just the UI.
- **Criterion 16 — closed at M18.** `StudentProfile.photoUrl` existed but the Reception page built its `selectedStudent` as `{ id, name, code }` only, for both the QR-payload branch and the search-result branch, and nothing under `app/[locale]/(center)/reception/` referenced `photoUrl` or rendered an avatar at all — so the control §5.1 names as **the** anti-impersonation measure behind the static-QR decision was not on screen. Fixed: `reception/page.tsx` now resolves a short-lived **signed URL** (`lib/db/storage.ts`'s `signedUrlFor`, 10-minute TTL — deliberately not the ID card's data-URI approach, since this is a live render with nothing that needs to outlive the request) for `selectedStudent.photoUrl` when Storage is configured, for both the QR-scan and search-result paths, and passes it to `CheckInForm` (`app/[locale]/(center)/reception/checkin-form.tsx`), which renders it as a round avatar beside the check-in prompt — or a plain user-icon placeholder when no photo is on file. The QR payload decision is *justified* by the photo check, and that justification is no longer aspirational.

## 8. Product governance (the anti-scope-creep shield)

Every center request is sorted into exactly one bucket **before** anything is promised:

- **Configurable behavior** → "Yes, you can turn that on in settings." (Preferred answer.)
- **Roadmap / Phase 2** → "That's coming in a later phase."
- **Custom, separately scoped** → "That's a custom add-on we'd price separately."

Never fork the codebase per center. The feeling of "their own system" comes from **branding + configuration**, not custom code. (This is the script for the owner meetings.)

## 9. Glossary

> **Read the first two entries together.** The DB vocabulary and the UI vocabulary deliberately differ, and the mapping is the single most confusable thing in these docs. When a doc names a **model** (`Center`, `Organization`) it means the database. When it names a **screen label** ("Branch", "Centre") it means what a user reads. The i18n layer is the only place the two meet (`02-architecture.md` §8); a full DB rename is `05-phase-2-backlog.md` entry 18.

- **`Organization`** (DB) = **"Center"** (UI) = the paying customer. Holds one or more branches. Not a tenant — carries no `center_id` and isolates nothing.
- **`Center`** (DB) = **"Branch"** (UI) = the tenant, and one physical location. **`center_id` is the sole isolation key**, unchanged by the org layer.
- **`Branch`** (the retired model) = the old location sub-entity under a tenant. **Dropped at M11**, along with `Room.branchId` and `Session.branchId` — rooms and sessions belong to the centre directly. Do not confuse it with the UI word "Branch", which now means `Center`.
- **Membership** = a user's role-scoped relationship to a center (staff/teacher/accountant). An **Owner's** membership is org-level and resolves to every branch; every other staff membership names one branch unless the Owner grants more.
- **Enrollment** = a student's link to a specific class. Hard-capped by the capacity of the class's room set (R3); attendance is not.
- **Room set** (R3) = a primary room plus any extra rooms linked to it (`RoomLink`), used together by a class or a session; its capacity is the rooms' sum.
- **Session** = one dated instance of a class — or, since R5, a **one-time session** that belongs to no class.
- **Extra session** (R5) = a session added by hand to a class (`isManual`), outside its weekly slots; the class's price, cut and roster apply.
- **One-time session** (R5) = a session with no class (`classGroupId` null): its own title, price and centre cut; everyone attending is a drop-in.
- **Class period** (R4) = a class's start and end date; its sessions exist for every matching weekly slot inside it, from today on.
- **Term** (R4) = a centre's named preset of two dates ("Semester 1") that fills a class period; the dates are copied, never linked. Not an academic-year entity (`05-phase-2-backlog.md` entry 11).
- **Weekly row** (R6) = one weekday + start + end entered in the New class dialog; each becomes a `ClassSchedule` row and, through the engine, a session every matching week of the class period.
- **Pristine session** (R4) = an upcoming session nothing has touched — no attendance, money, rating, settlement, override, description or reschedule, still on its class's teacher and rooms, and (R5) not made by hand. Only pristine sessions follow a class edit.
- **Attendee** = a student marked on a session's roster (enrolled or drop-in).
- **Center cut / share** = the **centre's** portion of a session's collected amount — `PERCENTAGE` of it, or a `FIXED` piastre amount of it. Never framed teacher-side (§5.1).
- **Settlement** = a teacher's payout record, `DRAFT → APPROVED → PAID`, derived from snapshotted shares and never recomputed.
- **Void** = a payment that should never have been recorded. **Refund** = a correct payment given back in cash. Different mechanisms, different analytics effects (§5).
- **Catalog entry** = a platform-owned subject / grade / education system, with an Arabic and an English name, that centres pick from (and rename for themselves, per language). Only a platform admin adds or changes one.
- **Visibility window** = the read-only horizon (1 calendar month by default) past which a centre-side role cannot read data. A restriction, never a deletion.
