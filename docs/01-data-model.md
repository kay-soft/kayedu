# KayEdu — Data Model (Phase 1)

> The **why** behind the schema. The **what** lives in `/prisma/schema.prisma`. Read this before touching the schema, and update both together.

---

## 1. Four design principles (memorize these)

**1. Identity is global; everything else is scoped.**
A `User` is one person, once, platform-wide. Their relationship to a center is a separate `Membership` (for staff/teachers) or `Enrollment` (for a student in a class). Attendance, payments, and analytics attach to the **scoped** record, never to the raw `User`. This is what makes "one identity across many centers" work without duplicates.

**2. Every tenant-scoped row carries `centerId`.**
Not database-per-center — one database, and `centerId` is on every table that belongs to a center. It's indexed, and it's the key that isolation is enforced on (app layer + Postgres RLS as backstop). Global tables (`User`, `Center`, `Organization`, the academic catalog, platform tables) are the only ones without it. **The organization layer added at M11 does not change this**: `Organization` is global, `Center` stays the tenant, and `center_id` remains the *sole* isolation key. An org-level roll-up is a union of per-centre scoped queries summed in memory — never a `where` spanning centres in the database.

**3. Money is append-only and snapshotted.**
A `Payment` row **freezes** the price, the center's share, and the teacher's share at the moment it's recorded. Historical money is **never** recomputed from current settings. Corrections create new, audited records — they don't overwrite. This single rule is why centers will trust the numbers.

**4. The roster is decoupled from enrollment.**
A `SessionAttendee` can exist **with** an enrollment (regular student) or **without** one (drop-in / one-time). Attendance and payment therefore never *require* an enrollment. This keeps the pay-per-session, drop-in-friendly reality of Egyptian centers modelled correctly.

## 2. Entity map by layer

### Identity layer (global — no `centerId`)
- **User** — the person. Auth via Supabase; profile fields here (name, phone, altPhone, email, avatar, locale, `isPlatformAdmin`). **SEC-2a:** `emailVerifiedAt` mirrors Supabase's `email_confirmed_at` on every sync (null for a person a centre created who has never signed in); with `REQUIRE_EMAIL_CONFIRMATION=true` an email-based link needs it. `phone` is only ever a **staff-typed** contact seeded once — sign-up never writes it, and it is never a link key (D-02). A contact another person already holds is never copied onto a new `User` (`createPerson`), so nobody's global contact is squatted. **F2:** `contactPhone` (nullable, **not unique**) is the person's own self-declared phone, set on Account settings and normalized through `lib/phone.ts`; it is **never an identity key** — no matching, linking, parent-origination or refusal function reads it (`check:account`), and it is never copied into `phone`. `locale` (`ar | en`) is the **preferred language**: sign-in redirects into it (`signInAction`), and Account settings edits it. Account settings writes only `firstName`/`lastName`/`contactPhone`/`locale` on the caller's own row — never a `Membership`/`StudentProfile` local record (§6) — and an email change reaches `email` only through `resolveAppIdentity`'s sync, audited `account.email.change` in the same transaction (ids only, D-20). **F4:** `signupIntent` (`STUDENT | PARENT | TEACHER`, nullable — null for every account that existed before F4) is what the person said they were joining as at sign-up; it rides in the Supabase sign-up metadata, is stored once by `resolveAppIdentity`, and **only routes onboarding** (`lib/auth/onboarding.ts`) — not a role, read by no permission, relation or scoping code. One refusal reads it: a STUDENT-intent account counts as a student account for F3's parent-code rule (`isStudentAccount`). `gradeId` (nullable FK to `CatalogGrade`, no `centerId`) is the student's **own statement of their current grade**, edited on Account → Study details; it seeds a *new* `StudentProfile` (when the branch offers that grade), pre-selects Discover's grade filter, and is **never** written back to or from a branch record (two-layer grade, docs/00 §5.1). **U6:** `teacherHistoryDays` (`Int`, default **0 = all history**; 1–3650 otherwise) is how far back the person's **own teacher portal** shows, set on Account → "History shown in my teacher portal" (only offered, and only accepted, for a person with an active TEACHER membership). The teacher's preference alone — no centre-side read consults it, and it never widens or narrows a branch's window (§7).
- **AccountClaim** *(SEC-2a, D-01)* — a sign-up's PENDING claim on a person a centre created: `authId` (the Supabase login), `email` (normalized), `targetUserId` (cascade), `status` (`PENDING | APPROVED | REJECTED`), `resolvedAt`/`resolvedBy`/`resolvedAtCenterId`. Unique on `(authId, targetUserId)`. Global like `User` — no `centerId`; the staff list and both decisions are scoped by requiring the claimed person to hold a relation **at the acting centre** (`lib/db/account-claims.ts`). Written only by `lib/auth/identity-link.ts`'s `resolveAppIdentity`, which gives the login **no app `User`** while the claim waits. Approving sets the target's `authId` (conditionally, in one transaction, audited `account.claim.approve`); rejecting detaches the email from the still-unlinked target so the claimant's next request makes them a new person (audited `account.claim.reject`).

### Organization layer
- **Organization** *(M11)* — **the paying customer**, and a **global** table: no `centerId`, isolates nothing, and is deliberately not a tenant. Holds the billing-relationship identity (name, slug, contact) and owns one or more `Center` rows. **`maxBranches`** *(F1)* — `Int`, ≥ 1 (a CHECK constraint), default 1: how many branches the organization may have, **set by a platform admin only** (audited `platform.organization.limit.update`, no centre). **Counted branches are its non-ARCHIVED, non-deleted centres** (U5: a soft-deleted branch frees its slot — `COUNTED_BRANCHES`, `lib/db/platform.ts`). **Only a platform admin adds a branch** (U5, decided 29 Oct with Kamal — Settings → Branches and `organization.branch.create` are gone). The F1 migration (`20261026100000_f1_branch_limits`) backfilled `max(1, current non-ARCHIVED branch count)`. Every branch-adding path locks the organization row (`SELECT … FOR UPDATE`), recounts and refuses `branchLimitReached` at the limit; lowering the limit below the current count only blocks new branches. (Replaces "No limit on branches", `00-master-product-spec.md` §5.1 "Branch architecture".) In the UI this reads as **"Center"** (`00-master-product-spec.md` §9 glossary) — the DB name and the screen label differ on purpose, resolved in i18n only (`02-architecture.md` §8); the full rename is `05-phase-2-backlog.md` entry 18.
- **Center** — **the tenant, and one branch**. `slug` (for subdomain/branding), `name`, `logoPath` (SEC-2a, D-25 (b): a key in the private `logos` bucket, replacing the free `logoUrl` the server used to fetch — SEC-53; shown through `/api/logos/[centerId]`'s short-lived signed URL), theme color, and — as of **M11** — **`organizationId`**. `center_id` remains **the sole isolation key**; adding the org layer changes nothing in `lib/db/scoped.ts`, `getTenantContext()` or the isolation gates, which is the entire reason it is modelled additively rather than as a rename. In the UI this reads as **"Branch"**. **`deletedAt` / `deletedBy` / `restorableUntil`** *(U5, all nullable)* — a platform admin's **soft delete**: `restorableUntil` = `deletedAt` + 30 days, and a CHECK keeps `deletedAt` and `restorableUntil` both set or both null. A deleted branch is excluded wherever a branch is resolved, listed or counted — `ACCESSIBLE_CENTER` (`lib/db/platform.ts`, an accessible lifecycle state **and** `deletedAt: null`) is the one filter tenant resolution, branch grants, the switcher and hub, Discover, the directories and every portal spread, and `COUNTED_BRANCHES` adds the same condition for the branch limit. Nothing is hard-deleted (purge is `05-phase-2-backlog.md` entry 33, waiting on OD-2); the delete never changes `lifecycleState`.
- **BranchPause** *(U5)* — a platform admin's pause of one branch: `centerId`, `startDate`, `endDate` (UTC-midnight day markers, inclusive; a CHECK keeps `endDate >= startDate` and the span ≤ 90 days), `reason?` (kept here, never in the audit row — D-20), `createdBy`, `createdAt`, `endedEarlyAt?`, `endedEarlyBy?`. At most one **current or future** pause per branch (`endedEarlyAt` null and `endDate >=` the branch's today), checked under the `Center` row lock (`lib/db/branch-admin.ts`); it ends by itself after `endDate` — there is no cron, "current" is computed on every read (`lib/db/branch-pauses.ts`). It is **not** a tenant-isolation row for anything but its own branch: it carries `centerId` and is read per branch. Written only by a platform admin.
  - **`lifecycleState`** *(delivered M19)* — `ONBOARDING | ACTIVE | GRACE | SUSPENDED | ARCHIVED`, **replacing the `active` boolean**. `ACCESSIBLE_LIFECYCLE_STATES` (`lib/db/platform.ts`) — ONBOARDING/ACTIVE/GRACE — is the set that may sign in and operate, the exact filter `getUserCenterRelations()` (`lib/auth/tenant.ts`) uses in place of the old `center: { active: true }`; SUSPENDED/ARCHIVED both refuse it. `platformCenterList` reports it directly; `setCenterActive` is gone, replaced by `transitionCenterLifecycle`, validated against a stated transition table (`LIFECYCLE_TRANSITIONS`) rather than accepting any state — ARCHIVED is terminal, every non-terminal state can jump straight to SUSPENDED/ARCHIVED, and only ONBOARDING/GRACE/SUSPENDED recover back to ACTIVE. The M19 migration backfilled existing rows `active: true → ACTIVE` / `active: false → SUSPENDED`; a freshly admin-provisioned center now starts ONBOARDING instead.
  - **`plan` is removed entirely** *(delivered M19)* — the column, `updateCenterPlan`, `updateCenterPlanAction`, the `/admin/centers/[id]` editor, the `check:admin` assertion, and every doc reference. It was free text with no behavior behind it, and leaving it implies a billing system that does not exist. **No module entitlements** (`00-master-product-spec.md` §5.1).
- **~~Branch~~** — **retired at M11.** The old `Branch` model was a location sub-entity *under* a tenant; the tenant itself is now the location, so it has no job left. `Room.branchId` and `Session.branchId` are dropped and both belong to the centre directly. Note the vocabulary trap: the retired **model** `Branch` is not the UI word "Branch", which now means `Center`.
- **CenterSettings** — one row per center: default center-cut mode/value, teacher-timeout days (`null` = disabled, never `0`), card-layout JSON (**shape, R9** — every key optional, absent = the built-in look: `version`, `background` (`"gradient-navy"` or `#RRGGBB`), `accent` / `footer` (`#RRGGBB`, absent = the centre's theme colour), `headerBand` (boolean), and `elements`, a map of `logo` / `centerName` / `photo` / `studentName` / `grade` / `studentCode` / `qr` to either `null` (removed from the card) or `{ x, y, width? }` for the three images and `{ x, y, width?, fontSize?, weight?, color?, align?, family? }` for the four texts — `x`/`y`/`width` are percentages of the card, `x` a *logical start* offset; `color` is `#RRGGBB`, `align` is `start | center | end`, `family` is a key of the closed font list (`cairo | system | serif`, never a CSS string); `centerName` alone also takes `text` (max 60 chars, blank = the centre's real name). Validated strictly on write by `cardLayoutSchema`, read tolerantly by `resolveCardLayout` — `lib/card-layout.ts`, `lib/id-card.ts`), timezone, late-threshold default, **`scheduleConflictPolicy`** (`WARN` default | `DENY` — whether a teacher/room double-booking may be saved **after explicit confirmation**, audited (R3; before R3 WARN saved it silently flagged), or is refused outright, docs/02 §11), **`teacherEditDeadlineHours`** (M10, `null` = disabled = editable any time — hours after a session's date a teacher may still edit its description, `02-architecture.md` §6), and — as of **U6** — **`centerDataVisibilityDays`** (1–365, default 365) and **`teacherDataVisibilityDays`** (1–30, default 30), the two read horizons of §7 below, both adjustable by the centre and by a platform admin. **`dataVisibilityDays`** (the single M19 window, default 30) is **deprecated**: backfilled into the two new fields, read by nothing but the branch-copy carry-over, dropped after the pilot (backlog). The two **permission-grant toggles** (`receptionistCanViewProfit`, `receptionistCanCorrectAttendance`) are **removed at M12**, replaced by the stored permission matrix below; `permissionGrantsFromSettings()` goes with them. Configured from the Settings screens (M2/M4); the row is upserted, so a center provisioned without one is still configurable.
- **Membership** — `userId × centerId × role` for **Owner / Manager / Receptionist / Accountant / Teacher** (`ACCOUNTANT` added at M12 — five enum values, eight resolved roles, see `00-master-product-spec.md` §3). `active`, invite metadata, **`isTrustedTeacher`** (M10, defaults `true` — gates the teacher portal's "request new class/session" forms, `02-architecture.md` §6), and a **center-local name + contact record** (`firstName`/`lastName`/`email`/`phone`/`altPhone`, see §6). The unused `canSeeEarnings` flag is dropped at M12 — the matrix is where a per-role capability lives now, and a column nothing reads is a column that misleads.
  - **Owner scope is org-level** *(M11)*. **Decided:** the schema is untouched — `Membership.centerId` stays required, exactly as before — and org-level reach is a **widening computed in `getUserCenterRelations()`** (`lib/auth/tenant.ts`), not a nullable-`centerId` row. An Owner's real `Membership` still names one branch (their "home" branch); at read time, for every `OWNER` membership, `getUserCenterRelations()` additionally resolves a *synthetic* per-branch relation for every sibling `Center` under the same `organizationId` (`lib/db/organizations.ts`'s `organizationBranches`), carrying a per-branch view of the same membership row (same `id`, `centerId` swapped to the sibling). `buildContext()`/`getTenantContext()` still just read `relation.center.id` as the `centerId` to scope on, so a sibling relation scopes exactly like a real membership would — **`lib/db/scoped.ts` needed zero changes**. This was picked over the nullable-`centerId` alternative because it keeps every existing Owner-at-their-own-branch code path (staff lists, `@@unique([userId, centerId, role])`, `lastOwner` checks) provably byte-for-byte unchanged; the trade-off is that an Owner does **not** yet appear in a *sibling* branch's own `/settings/staff` list (no real row there) — a real per-branch grant surface is `MembershipBranchGrant` (M12), and closing this specific gap belongs with it. Manager / Receptionist / Accountant memberships name **exactly one** centre (real rows, unchanged). **Teacher memberships are unchanged** — a teacher belongs to centres, one row per centre, exactly as today.
- **MembershipBranchGrant** *(M12)* — the Owner-granted exception: one row per extra `centerId` a branch-scoped member may also reach. Only an OWNER may write one, and every write is audited. Resolution is additive and never subtractive — a grant widens the set of centres a membership resolves to, it can never remove the member's own.
- **Invitation** — pending email invite: `centerId`, email, role, token, status, expiry.

### Permissions layer *(M12)*
- **PermissionGrant** — the stored, action-level matrix that replaces the hardcoded `Record<TenantRole, Permission[]>` plus the two `CenterSettings` booleans: `centerId × role × action × allowed`. **Deny by default** — an action with no row is denied, so a permission newly added to the codebase is denied to everyone until an Owner grants it. Only **OWNER** may write these rows; the matrix screen submits its whole grid at once, written in one transaction and audited as a single `permission.matrix.update` row (before/after the full set of changed rows), not one `AuditLog` row per cell. The matrix can only widen a role **within what the platform allows that role**: a hardcoded *grantable* ceiling still exists in code (a TEACHER can never be granted `center.profit.view`, an OWNER can never be stripped of ownership actions), so a misconfigured centre cannot invent a privilege escalation. See `02-architecture.md` §6 for the resolution order.

### Academic catalog layer *(M13, delivered — platform-owned, NO `centerId`)*
> The three entities below **moved out of the tenant** at M13. They are global, platform-authored reference data; a centre no longer authors its own rows, it **picks** from the catalog. **R8:** only a platform admin writes a catalog row (`lib/db/catalog-admin.ts`, which re-checks `isPlatformAdmin` on every call and audits each write); centres no longer propose entries — a centre that needs one contacts the platform. This is what makes "IGCSE Physics" mean the same thing at every centre — and what let Discover stop matching classes on subject *names* across centres (docs/02 §14; `lib/db/discover.ts`'s `discoverClassesForCenter` takes a real `{ subjectId, gradeId }` `where` now).
- **CatalogEducationSystem** — `nameAr` + `nameEn`, and a **`defaultFixedCenterShare`** (piastres, e.g. American 40 EGP, IGCSE 50 EGP): the default a class inherits when its cut is set to `FIXED`, overridable per class and per session. It is consulted **only at configuration time** — a class's own `centerShareValue` copies it once when the class is created — and never at payment time, so changing it never moves an existing class, let alone a recorded payment (§3). Only a platform admin edits this field, directly at `/admin/catalog` — a centre never writes to the canonical row.
- **CatalogGrade** — `nameAr` + `nameEn` + education-system link.
- **CatalogSubject** — `nameAr` + `nameEn`, **grade-independent since U3**: a subject exists once, its names unique across the whole catalog. `gradeId` is a **deprecated** column — nullable, unread, never written, no FK or index — kept only so the build deployed before U3 kept working until the new code shipped (expand-only); dropping it is `05-phase-2-backlog.md` entry 32.
- **CatalogSubjectGrade** *(U3)* — `subjectId` + `gradeId` (composite primary key, so a pair exists once) + `createdAt`: "this subject is taught in this grade", any education system. Global like the rest of the catalog (no `centerId`, RLS on), written only by `lib/db/catalog-admin.ts`. `ON DELETE CASCADE` from the subject (deleting a subject takes its links), `RESTRICT` from the grade (a grade with links is not deleted). A link is not removed while an **active** class anywhere uses the pair.
- *Rules for all three (R8).* Both names are required (trimmed, 1–80 characters) and unique, case-insensitively, English and Arabic each — within the **same parent** for systems and grades, and **across all subjects** for subjects (U3). `active` is the platform's deactivate flag: a deactivated entry leaves every picker, Discover filter and the centre "add" list but keeps resolving in classes, sessions, history and analytics. **Hard delete only if nothing references the row** — no `CenterCatalogSelection`, `ClassGroup`, `StudentProfile`, one-time `Session`, or child entry (a system's grades; a grade's subject links — a subject's own links never block it) (the relations are optional, so Prisma's default `SET NULL` would orphan a class silently; `lib/db/catalog-admin.ts` counts the references itself and refuses with the counts). Every write writes an `AuditLog` row `platform.catalog.create | update | deactivate | reactivate | delete` with before/after and no `centerId`.
- **CenterCatalogSelection** — a centre's pick of a catalog entry, and the **only** thing a centre may edit about it: its own **display name, one per language** — `displayNameAr` and `displayNameEn`, both optional, null/blank = use the catalog's own name in that language — and (for an education system only) its own **base price**. (R8 replaced the single free-text name M13 had with these two; the migration backfilled each old value into `displayNameAr` if it contains an Arabic-script character, else `displayNameEn`. No production data existed.) `kind` plus three nullable FKs (`educationSystemId`/`gradeId`/`subjectId`, exactly one set per row) say which catalog table it points at — an application-layer invariant, the same shape `StudentBlock.refId` already uses in this schema, rather than a cross-column CHECK constraint. It is `centerId`-scoped; the catalog entry it points at is not. Can be deactivated (a centre-side toggle) or deselected (hard-removed, refused while a class/session/student still references the underlying catalog id). **U3:** a centre picks a subject **once** (not once per grade); a **(grade, subject) pair is offered** at a centre when both picks are active, neither entry is deactivated by the platform, and `CatalogSubjectGrade` links them (`lib/db/catalog.ts` `isPairOffered`). A grade's deselect is no longer blocked by the centre's subject picks (a subject is not "under" a grade); its classes and students still block it. *Migration `20261030150000_u3_subject_grade_links`* merged the per-grade duplicates: subjects grouped by their normalized (English, Arabic) names, the oldest of each group kept, every member's old grade turned into a link, every `ClassGroup`/`Session`/`CenterCatalogSelection`/`ChangeRequest.payload` reference repointed, a centre's duplicate selections merged into one (active if any was; each display name the most recently updated non-empty one), the duplicates deleted. `AuditLog` rows keep the ids they were written with (append-only).
> **Every catalog entry carries both an Arabic and an English name** and renders in the active locale. **Person names do not work this way** — a person has one name per relationship (§6), not one per locale. A name is not a translatable string, and modelling it as one produces two drifting records of the same human.
> **The display-name overrides are live everywhere, not just on `/settings/catalog` (M13, bilingual since R8).** No schema field anywhere freezes a catalog entry's name the way `Payment.priceSnapshot` freezes money — every read of a subject/grade/education-system is a live join, so a centre's rename belongs on all of them, not only the screen where it picks and renames. `lib/db/classes.ts`'s `classListSelect`/`classDetailInclude`, `lib/db/sessions.ts`'s `sessionListSelect`/`sessionDetailInclude`, `lib/db/students.ts`'s `studentListSelect`, `lib/db/discover.ts`'s `discoverClassSelect`, and the relevant `lib/db/scoped.ts`/`lib/db/student-portal.ts`/`lib/db/teacher-portal.ts` includes are all functions of `centerId` that add a nested `selections: { where: { centerId } }` lookup (selecting `CATALOG_OVERRIDE_SELECT` — the two override columns); `lib/catalog.ts`'s `catalogLabel`/`catalogLabelWithSelection` is the **one resolver** that reads it back (Arabic UI: `displayNameAr` else `nameAr`; English UI: `displayNameEn` else `nameEn` — an override never crosses languages, `02-architecture.md` §8). The student-portal reservations read, the pending-ratings pop-up in the student layout and the ID card all go through it too. The one read that's genuinely cross-centre in a single query — `lib/db/student-portal.ts`'s `listReservationsForStudent` (a student's own reservations span every centre they've applied to) — can't push a per-row `centerId` into a nested include, so it batch-resolves the distinct (centre, catalog id) pairs actually present in one extra query instead. The only deliberately canonical-only reads are ephemeral, non-persistent text: schedule conflict labels built inside the data layer (`lib/db/slot-conflicts.ts`'s occupancy loader and `lib/db/approvals.ts`'s `resolveSessionRequest`; SYS removed the unused `classDisplayName`, and the R4 generator and `toExistingScheduleSlots` went with R4), and the platform-admin catalog screen (`/admin/catalog`, which manages the canonical rows themselves, not a view through any one centre's lens).

### Config layer (all `centerId`-scoped)
- **Room** — belongs to the **centre directly** (M11 drops `branchId`); name/number + capacity. Capacity is the **hard cap on enrolment** and deliberately **not** a cap on attendance (`00-master-product-spec.md` §5.1 "Capacity"). **Since R3** the cap is the summed capacity of the class's **room set** — its primary room plus every extra room combined with it — via `lib/rooms.ts`'s `effectiveCapacity` and `lib/capacity.ts`'s `enrollmentCap(roomSetCapacity)`; `0` on any room of the set means "not configured" and leaves the set uncapped, and a class with no room is uncapped. (M15's `enrollmentCap(classGroup.capacity, room.capacity)` min-of-two rule is reversed: `ClassGroup.capacity` no longer exists.) `reserveOrEnroll`, `confirmReservation` and the centre-staff `enrollStudentAction` all read it through `lib/db/room-sets.ts`'s `loadClassRoomSet`/`classRoomSetFrom`. `SessionAttendee`/`createAttendance` carries no capacity check at all — attendance is never gated.
- **RoomLink** *(R3)* — two rooms of one centre that can be combined into one bigger room: `centerId` (indexed, cascade), `roomAId`, `roomBId` (both FK to `Room`, cascade), `createdAt`. **Stored once per pair, normalized so `roomAId < roomBId`** (ids compared as strings) and unique on `(roomAId, roomBId)` — symmetric by construction, with a database `CHECK (roomAId < roomBId)` as backstop (which also rules out a self-link). Same centre only: the only writer, `lib/db/room-sets.ts` (`linkRooms`/`unlinkRooms`/`setRoomLinks`/`saveRoomWithLinks`), resolves both rooms inside the link's own `centerId`, so a cross-centre link is "room not found". Unlinking is refused while an active class or a non-closed future session uses the pair (`combinationUsage`). A link is a **star edge, not transitive** — see `lib/rooms.ts`'s `isValidCombination`. Deleting a room cascades its links (a room still referenced by any class/session, as primary or extra, is never deleted — §6).
- **ClassGroupRoom** *(R3)* — one **extra** room of a class: `centerId`, `classGroupId`, `roomId` (all cascade), unique on `(classGroupId, roomId)`, indexed `(centerId, roomId)`. `ClassGroup.roomId` stays the **primary**; every extra must be linked to it (validated by `resolveRoomSet` on every write). Written only by `lib/db/room-sets.ts`'s `writeClassExtraRooms`.
- **ClassGroup** — the class: teacher, subject, grade, educationSystem (**catalog references** as of M13 — `subjectId`/`gradeId`/`educationSystemId` now point at `CatalogSubject`/`CatalogGrade`/`CatalogEducationSystem` directly, the same columns reused via an id-preserving migration so no existing class needed a value change), room (the **primary** room — required on every new or edited class since R3; extra rooms are `ClassGroupRoom` rows), price, **centerShareType (FIXED|PERCENTAGE) + centerShareValue** (a `FIXED` value is **the piastre amount the centre takes**, defaulted from the education system's `defaultFixedCenterShare` at configuration time and freely overridable — `00-master-product-spec.md` §5.1 "Center cut"), `lateThresholdMinutes`, `acceptsNewStudents`, `requiresConfirmation`, **`startDate` + `endDate`** *(R4 — the class's **period**, required, date-only UTC-midnight markers like `Session.date`; typed or **copied** from a `CenterTerm` preset with no FK back to it; its sessions exist for every matching weekly slot inside it from today on — `lib/db/class-sessions.ts`)*, `active` *(R4: inactive = no forward-looking sessions and gone from every forward reader, history intact — `00-master-product-spec.md` §5.1 "Deactivate, reactivate, delete")*. *(R1 dropped two flags: the M10 per-class excused toggle, along with the status itself, and an attendance-required flag no behaviour ever read — `00-master-product-spec.md` §5.1 "Excused removed". **R3 dropped `capacity`** — the seat limit is the room set's — reversing M15's min(class, room).)* One room set per class — not one per slot (see the `ClassSchedule` note below).
  - **F6 — joining options.** `sessionBookingMode` (`SessionBookingMode`: `OFF | INSTANT | APPROVAL`, default `OFF` — every class that predates F6 is OFF and behaves exactly as before) decides whether one session can be booked online by a student who is not enrolled, and whether that booking is confirmed at once or waits in the approvals queues; `maxBookingSeats` (`Int?`, null = no extra cap; a CHECK keeps it ≥ 1) caps the CONFIRMED bookings per session on top of the seat limit. Both are edited in the class dialog's **Joining** section beside `acceptsNewStudents` and `requiresConfirmation`, and audited with the rest of `classGroup.create` / `classGroup.update`.
- **CenterTerm** *(R4)* — a centre's term **preset**: `centerId` (indexed, cascade), `name` (one centre-entered string, like `Room.name`), `startDate`, `endDate` (date-only markers), `active`, timestamps. Unique per centre by name **case-insensitively**, enforced by `lib/db/terms.ts` (the only writer — it locks the centre row so two concurrent creates cannot both pass) rather than a database index; the period follows the same rule as a class's (`lib/scheduling.ts`'s `classPeriodError`). Terms may overlap. **Nothing references a term**: the class form copies its dates onto `ClassGroup.startDate`/`endDate`, so editing a term moves no class and a delete is always a hard delete. Read through `scoped(ctx).terms` (`list`, `listActive`, `findById`); covered by the Data API lockdown like every `public` table (SEC-2a). Not the `AcademicYear`/`Term` entity of `05-phase-2-backlog.md` entry 11 — nothing else hangs off it.
- **CenterPaymentMethod** *(R1)* — the centre's own payment methods: `name` (one centre-entered string, like `Room.name` — a label people type, not a bilingual catalog entry), `active`. A new centre is created with **Cash / InstaPay / Vodafone Cash** (`lib/db/payment-methods.ts`'s `DEFAULT_PAYMENT_METHOD_NAMES`, used by `createCenterWithSettings` and the seed). Two invariants, both enforced in `lib/db/payment-methods.ts` rather than per screen: **at least one active method per centre, always** (deactivating or deleting the last active one is refused, under a row lock so concurrent deactivations can't race past it), and **a method any `Payment` references is deactivated, never deleted** (the §6 master-data convention; the FK is `RESTRICT` as a backstop). Pickers list active methods only, oldest first, so a centre's first method is the preselected one. See §3 for how a payment freezes the label.
- **ClassSchedule** — recurring slot(s) for a class: dayOfWeek, startTime, endTime. (A class can have several.) No `roomId` of its own: the class's room set (`ClassGroup.roomId` + its `ClassGroupRoom` extras, R3) is what every one of its sessions occupies, and it's what the class detail page shows in its read-only context panel (docs/04 §9, revised from the original per-slot-room mockup). **R4:** adding, moving or removing a slot resyncs the class's future sessions over its whole period (`lib/db/class-sessions.ts`'s `writeClassSlot`), and conflicts are checked on those dated sessions — weekly slots are no longer compared with each other.

### People-in-center layer
- **StudentProfile** — a student's per-center record: `userId × centerId`, grade, a **center-local name + contact record** (`firstName`/`lastName`/`email`/`phone`/`altPhone` — see §6), parent name/phone/altPhone, `studentCode` (the ID-card number, unique per center, **system-assigned** — see §6), `photoUrl`, `profileCompletedAt` *(nullable, delivered M18)* — null on a self-registered student's auto-seeded stub, stamped at creation for a receptionist-added one (already whole) or once a self-registered student completes `/student/profile`'s one-time form (spec §4.3 item 4); a read-restriction gate in the `(student)` layout keys on it, active. (Per-center so centers own their data and grade taxonomy is center-local.) The **photo lives here, not on `User.avatarUrl`**: a picture a center took for its own ID card is that center's data, is stored under `avatars/{centerId}/…`, and must not follow the person to another center. `User.avatarUrl` stays the person's own global avatar. **F4 — two-layer grade:** `gradeId` here is the grade **this branch has on file**; the student's own is `User.gradeId`, and the two may differ (staff see "Account says: <grade>" and may adopt it with **Use account grade**, audited `student.grade.account`). A *new* profile (`ensureStudentProfile`) is seeded with the account grade (if the branch offers it) and the parent the student declared in F3's "Invite a parent" (name and phone, as this branch's own record — never a link); with both a grade and a parent phone `profileCompletedAt` is stamped at creation, so the one-time form is skipped. An existing profile is never re-seeded or overwritten by the account.
- **GradePromotionBatch / GradePromotionItem** *(delivered F4)* — one confirmed bulk promotion at one branch, and its undo ledger. The batch: `centerId` (the sole isolation key, cascade with the centre), `fromGradeId`/`toGradeId` (FKs to `CatalogGrade`, restrict; a CHECK keeps them different), `createdBy`/`createdAt`, `undoneAt`/`undoneBy` (plain user ids, no FK; a CHECK says both or neither). One item per student **actually moved**: `batchId`, `studentProfileId` (cascade), `previousGradeId` (the From grade, kept per row so undo does not rely on the header alone); unique on `(batchId, studentProfileId)`. Written **only** by `lib/db/promotion.ts`'s `confirmGradePromotion` — in one transaction with the `StudentProfile.gradeId` updates (rows locked `FOR UPDATE`, re-checked active and still in the From grade) and one `student.grade.promote` audit row (batch id and counts, ids only) — and changed only by `undoGradePromotion`: the **latest not-yet-undone** batch, within 14 days (`lib/promotion.ts`), reverting only items whose profile still sits in the batch's To grade, audited `student.grade.promote.undo`. Read through `scoped(ctx).gradePromotions` (`recent`, `latestOpen`). **Not windowed** by the data-visibility window (it holds no session or money data and the undo window is its own). It touches no enrolment, class, session, payment, other branch or `User.gradeId`; the catalog hard-delete guard counts it (`students` usage).
- **StudentCodeCounter** — `centerId` (PK), `next`. One row per center; the race-free source of the next `studentCode` (§6). Not a business entity a screen shows — a plumbing table for `lib/db/students.ts`.
- **Enrollment** — `studentProfile × classGroup`: status (ACTIVE/REMOVED/BLOCKED), enrolledAt. Unique on `(studentProfileId, classGroupId)` — the row is reused across its lifecycle rather than recreated: REMOVED frees the seat, BLOCKED means a `StudentBlock` (scope CLASS) currently sits on top of what was an active enrollment, and un-blocking restores it to ACTIVE rather than creating a fresh row (M4, `app/[locale]/(center)/classes/actions.ts`). **U8 - `leftByStudentAt` (nullable):** set only when the *student* ended the enrolment themselves ("Leave class", `leaveClass` in `lib/db/reservations.ts`); the row is then REMOVED exactly as a staff removal leaves it, and this timestamp is what tells the two apart ("Left <class> on <date>, by the student" on the centre's student page). Cleared whenever the pair is reactivated (a rejoin, a staff re-enrol, `setStatus` to anything but REMOVED), together with `enrolledAt` being reset to the moment they came back - so a rejoining student is never marked Absent for sessions that closed while they were out.
- **StudentBlock** — a teacher or class blocking a student: `centerId`, scope (TEACHER|CLASS), refId, blockedUserId, reason. Unique on `(centerId, scope, refId, blockedUserId)` — blocking the same student twice is a bug — and indexed on `(centerId, scope, refId)` because "is this student blocked here?" is a hot lookup on the enrol/add path. A block is **per center**: a teacher shared by two centers who blocks a student at one has not blocked them at the other. Scope CLASS (`refId` = a `ClassGroup` id, M4) is enforced at enrollment time exactly like scope TEACHER already was at M3 — the same `studentBlocks.isBlocked()` helper, just a different scope/refId pair.

### Session & attendance layer (all `centerId`-scoped)
- **Session** — one dated instance: classGroup, teacher, room (the **primary** room; extra rooms are `SessionRoom` rows, R3), date, start/end, status (SCHEDULED/LIVE/COMPLETED/CANCELLED), `priceSnapshot`, description. **`branchId` is dropped at M11** — a session belongs to its centre. **`rescheduledToId`** *(delivered M15)* — a self-reference (`Session? @relation("SessionReschedule", ...)`, unique), written **immediately** by `lib/db/sessions.ts`'s `rescheduleSession`, which now **creates a new `Session` row** at the target date/time in the same transaction rather than mutating the original in place — the original keeps its own date/time and whatever attendance/payments it already carries, and is closed to any *new* ones (`lib/db/attendance.ts`/`lib/db/payments.ts`'s `SessionClosedError`, reason `"sessionRescheduled"` — the same choke point that refuses a `CANCELLED` session, extended in the same milestone). `deriveSessionDisplayStatus` reports a session carrying this as `RESCHEDULED`, ahead of both the stored `status` and the clock. `startTime`/`endTime` already existed here and on `ClassSchedule` before M15, so the "room must be free for the **entire** start→end window" check needed no new fields — `lib/scheduling.ts`'s `timeRangesOverlap` already compared the whole window, not just the start instant; M15 added the first direct test of that (`npm run check:enrollment`), not a code fix. **`centerShareType`/`centerShareValue`** *(M13, both nullable)* — a session's own centre-cut override (`00-master-product-spec.md` §5.1 "Center cut"): null on both (every session's state until explicitly overridden) means inherit the class's own cut; `lib/db/payments.ts`'s `recordPayment` reads the session's override first, falling back to the class, at the exact instant a payment is frozen — never rewrites an already-recorded payment. Unique on `(classGroupId, date, startTime)` **among sessions not rescheduled away** — the idempotency backstop of the class-sessions engine (R4, `lib/db/class-sessions.ts`, which replaced the M4 rolling-window generator): a `createMany({ skipDuplicates: true })` against it never creates a second row for a slot that already has one, so re-running any class write with nothing changed creates nothing. **U2:** the uniqueness is a **partial unique index**, `Session_classGroupId_date_startTime_live_key … WHERE "rescheduledToId" IS NULL` (migration `20261030120000_u2_session_slot_partial_unique`): a moved original no longer holds its slot, so its replacement can be rescheduled back there; a CANCELLED session (and every other status) still holds it. Prisma 6 cannot declare a partial index, so it is hand-written SQL and the schema carries a plain `@@index` on the same columns (docs/02 §11 has the migration rule). No Prisma call uses a compound-unique key on these columns; the writers that put a session on a class's slot (`rescheduleSession`, `createManualSession`, `resolveSessionRequest`) read the slot first with `slotTakenError` (`lib/db/slot-conflicts.ts`, `rescheduledToId: null` — `duplicateSlot`, or `duplicateSlotCancelled` when the blocker is cancelled) and keep mapping a racing P2002 to `duplicateSlot`. The engine's own taken-key read still counts every session, moved and cancelled ones included, so it never recreates either. **R4:** a session is created from its class's period (never in the past, never on a holiday) and, while **pristine** — nothing recorded on it, nothing customised, still on its class's teacher and room set — it follows its class's edits (deleted, re-roomed or re-taught); once anything touches it, it stays exactly as it is. **`timezone`** *(SEC-2b, D-14)* — the centre's timezone frozen at creation by a trigger and never changed afterwards; the session's lifecycle reads it (§8). **`pauseId`** *(U5, nullable, `ON DELETE SET NULL`)* — the `BranchPause` that cancelled this session (through `cancelSession`, which also stamps `updatedAt` with the pause's own `createdAt`). "End pause now" restores only sessions still tagged with it, still CANCELLED and with `updatedAt` no later than that stamp ("untouched since"), and clears the tag on each one it restores.
  - **R5 — manual and one-time sessions.** **`classGroupId` is nullable**: null means a **one-time session** that belongs to no class (the FK and its cascade are unchanged; the `(classGroupId, date, startTime)` unique stays and still works, because Postgres treats NULLs as distinct — any number of one-time sessions may share a slot, a class still cannot hold two). Four new columns: **`title`** (`String?`, ≤ 80 — a one-time session's own name), **`subjectId`**/**`gradeId`** (`String?`, FKs to `CatalogSubject`/`CatalogGrade`, `SET NULL`, exactly like `ClassGroup`'s — a one-time session's optional catalog entries, labelled through the centre's selection like every other catalog read) and **`isManual`** (`Boolean @default(false)` — made by hand: an extra session on a class, a one-time session, or an approved `NEW_SESSION` request; existing rows were migrated `false`). **Invariant, "the kind says which fields apply"** (the `Settlement`/`CenterCatalogSelection` style, application-layer): **`classGroupId` null ⇒ `title`, `teacherId`, `priceSnapshot` and BOTH `centerShareType` and `centerShareValue` are set** — on a one-time session those two are not an override but its only cut. Enforced in `lib/db/sessions.ts` (`oneOffSessionShapeError`, checked by the creator; `updateSessionShareOverride` refuses to clear them, `cutRequired`), asserted by `npm run check:one-off-sessions`. On a class session `title`/`subjectId`/`gradeId` are unused (its name is its class's). **`isManual` is part of the pristine predicate** (`lib/db/class-sessions.ts`'s `sessionDisqualifiers` → `"manual"`, and `STILL_PRISTINE` pins `isManual: false`): no resync, end-date change, holiday insertion or class edit deletes or rewrites a manual session; deactivating its class deletes it only if it is otherwise pristine, else cancels it. Every reader names a session through **`lib/session-label.ts`** (`sessionDisplayName`/`sessionLabelParts`/`sessionKind`) — the single owner of "class subject · grade, else title (· subject · grade)" — so a null class never throws or prints "undefined". Migration `20261015090000_r5_manual_one_off_sessions` (no production data existed).
- **SessionRoom** *(R3)* — one **extra** room of one session: `centerId`, `sessionId`, `roomId` (all cascade), unique on `(sessionId, roomId)`, indexed `(centerId, roomId)`. **Copied from the class's `ClassGroupRoom` rows by the class-sessions engine (R4)** (and by NEW_SESSION approval and reschedule, which copies the original's set unless another valid one is chosen; R5: written for the room set picked on a manual or one-time session at creation); a session may also change its own set ("Rooms" on the session, `lib/db/sessions.ts`'s `updateSessionRooms`) — which never changes its class or the class's enrolment cap. **While the session runs, every room of its set is busy**: `lib/db/slot-conflicts.ts`'s `loadSessionOccupancy` is the one loader of "who occupies what" (a CANCELLED session and the original slot of a rescheduled one occupy nothing; a closed one does). Written only by `lib/db/room-sets.ts`'s `writeSessionExtraRooms`.
- **Session close fields** *(R2)* — **`closedAt`** (when the session was closed), **`closedBy`** (the closing user's id, `null` for an automatic close) and **`closeMode`** (`SessionCloseMode`: `MANUAL` = staff pressed "End session", `AUTO` = its calendar day ended in the centre's timezone and the next touch closed it, stamping local midnight). A set `closedAt` makes the session an immutable record: `lib/db/session-lifecycle.ts`'s `ensureSessionOpenOrAutoClose` — the one closure guard every attendance/money/lifecycle write calls first — refuses everything after it, and closing also stores `status: COMPLETED` so the stored and displayed status agree (`deriveSessionDisplayStatus`: RESCHEDULED > CANCELLED > COMPLETED when closed or the day is over > SCHEDULED before start > LIVE, which now lasts until the session is ended or its day ends). Nothing ever clears `closedAt` — there is no reopen. Existing past sessions were not backfilled: the lazy rule closes them on their next touch. CANCELLED and rescheduled sessions never close.
- **SessionAttendanceChange** *(R2)* — one live-session attendance status change: `centerId` (indexed, cascade), `sessionId`, `studentProfileId`, `fromStatus`/`toStatus`, `voidedPaymentId?` (set when the change was Present/Late → Absent on a paid student and voided that payment in the same transaction, or (T5) when a plain void on a live session reset the student), `refundedPaymentId?` *(T5 — the refunded payment whose refund reset the student on a live session, so the log reads as a refund and not as a void; nullable, `SetNull` like `voidedPaymentId`)*, `reason?` (optional), `changedBy`, `changedAt`. Append-only. Written only by `lib/db/attendance-change.ts`'s `applyAttendanceChange`, the one writer behind `changeAttendanceStatus`, the void/refund reset (`resetAttendanceAfterReversal`) and the re-check-in (`recheckInAttendee`). It runs in the same transaction as the change, any void or refund, and the `attendance.correct` / `payment.void` / `payment.refund` audit rows. It is the **receipt's** data source ("Changes during session"); `AuditLog` stays the audit trail. Read through `scoped(ctx).attendanceChanges` / `listSessionAttendanceChanges`, always `centerId`-scoped.
- **Holiday** — a center's own holiday calendar (M4): `centerId`, `date`, an optional `name`. Unique on `(centerId, date)`. Not itself a business screen a role opens daily — it's the input the class-sessions engine (`lib/db/class-sessions.ts`, R4) skips dates against, edited from a small panel on `/classes` (docs/02 §11). Adding a holiday also deletes that day's pristine sessions in the same transaction (never a manual or one-time session — those are counted as kept, R5); removing one restores nothing (OD-10).
- **SessionAttendee** — roster row: session, `studentProfileId?` (null-safe for pure drop-ins), `enrollmentId?` (null for drop-ins), `attendanceStatus` (PRESENT/LATE/ABSENT — exactly three as of R1), `isDropIn`, recordedBy, recordedAt. A first-time mark is `attendance.record`; changing an already-marked row is `attendance.correct` and is audited (M5, spec §5 "Attendance", `lib/db/attendance.ts`). One row per `(sessionId, studentProfileId)` — reused across corrections, like `Enrollment`, never recreated. Can carry more than one `Payment` over its history (see below). **R2:** a check-in row's status is decided by `createAttendance` itself (Present within the class's late threshold of the start, Late after — `lib/scheduling.ts`'s `checkInStatus`, in the centre's timezone), inserted by one statement that is atomic with the closure check; corrections happen only while the session is live and each writes a `SessionAttendanceChange`. **T5:** a void or refund on a live session resets a Present/Late row to ABSENT ("Not arrived"), and that same row can be checked in again (`recheckInAttendee`). The row is never deleted, because its payments cascade from it. A drop-in's ABSENT row is never an absence (`lib/attendance-rules.ts`'s `EXCLUDE_DROP_IN_NO_SHOWS`, applied by every absence and history reader). **ABSENT rows for enrolled no-shows are written by the close** (`materializeAbsences`: `isDropIn: false`, `enrollmentId` set, `recordedBy: "system"`, idempotent against the `(sessionId, studentProfileId)` unique index).
- **Payment** — the ledger row (see §3): session, sessionAttendee, studentProfile, amount, `paymentMethodId` + **`methodLabelSnapshot`** (R1 — the centre's method and its name frozen at record time), **priceSnapshot, centerShareSnapshot, teacherShareSnapshot**, receiptRef, `voided`/`voidReason`/`voidedAt`/`voidedBy`, recordedBy, recordedAt, and — as of **delivered M14** — a plain `refunded` boolean marker paired with its optional `Refund` row (see the Finance-adjacent layer). Void and refund are **different states with different analytics effects** and must never be collapsed into one flag. `sessionAttendeeId` is a plain indexed foreign key, **not** database-unique (revised at M5) — a void never deletes its row, and "void, then optionally write a corrected Payment" (§3) writes a *second* row against the same `SessionAttendee`, not a replacement. `lib/db/payments.ts`'s `recordPayment` is what enforces "at most one **active** (non-voided) payment per attendee at a time" instead, since the database no longer can. `teacherId` (M6) is a **denormalized snapshot** of `session.teacherId`, written once by `recordPayment` alongside the money snapshots — it exists purely so the Analytics by-teacher breakdown (`lib/db/analytics.ts`'s `revenueByTeacher`) can `groupBy` in a single query (Prisma cannot `groupBy` on a related model's column). It is **not** one of the "sacred" money snapshots §3 forbids recomputing — it's a reference, like `recordedBy`, not an amount.

### Finance-adjacent layer
- **Refund** *(delivered M14)* — `centerId`, the `paymentId` it reverses (unique — at most one refund per payment), a denormalized `teacherId` (from `payment.teacherId`, the same "reference, not a money field" reason `Payment.teacherId` itself is denormalized — it lets `revenueByTeacher` `groupBy` on `Refund` in one query), `amount`/`centerShareReversed`/`teacherShareReversed`, `reason`, `refundedBy`, `refundedAt`. **The original `Payment` row is preserved untouched** — no money field on it is ever written — and `Payment.refunded` (a plain boolean) is what a reader checks without a join. **Whole-payment refunds only**: `amount`/`centerShareReversed`/`teacherShareReversed` are always exactly the reversed payment's own `amount`/`centerShareSnapshot`/`teacherShareSnapshot` — Phase 1 has no partial-refund shape, matching spec §4.1 item 12's "mark a recorded payment REFUNDED" rather than a proration model nothing asked for. **Cash-back only: no student balance is created anywhere**, which is why there is no balance column here and no ledger to net against (`00-master-product-spec.md` §2 "Student debt" is unchanged). A voided payment can never be refunded, and a refunded payment can never be refunded twice — `lib/db/refunds.ts`'s `refundPayment` refuses both. Analytics (`lib/db/analytics.ts`'s `revenueTotals`/`revenueByTeacher`) **subtracts** a refund from collected revenue **and** from that payment's centre and teacher shares — the reversed payment itself is not voided, so it still contributes to the raw aggregate; the `Refund` row is what nets it back out for the same date range/teacher. This is the one place a refund differs sharply from a void, which is simply not counted because it was never real revenue. Permissioned (`payment.refund`) and audited (`payment.refund` — plus a `settlement.adjust` row for every DRAFT/APPROVED settlement it live-adjusts, see the `Settlement` bullet below). See the void-vs-refund table in `00-master-product-spec.md` §5.
- **Settlement** *(delivered M14, promoted from "summary, not source of truth" to a real record)* — **R2:** creation requires closed sessions (a session settlement refuses a live session; a period settlement counts only payments of sessions closed by then, closing any whose day already ended first), and **`closedSessionsOnly`** (default `true`; backfilled `false` on rows that predate R2) records which counting rule produced `totalAmount`, so a later void or refund adjusts an unpaid settlement only if it had actually counted that payment (`adjustUnpaidSettlementsForReversal`, shared by refunds and voids). A teacher's payout: `centerId`, `teacherId`, scope (a single `sessionId`, **or** a period `periodFrom`/`periodTo` — exactly one shape populated per row, the same "kind says which fields apply" invariant `CenterCatalogSelection.kind` already uses in this schema), `totalAmount`, `status` (`DRAFT | APPROVED | PAID`), the transition actor/timestamps (`createdBy`, `approvedBy`/`approvedAt`, `paidBy`/`paidAt`). **No partially-paid state** — a settlement is fully paid or it is not, because a partial state reintroduces exactly the "how much is still owed" bookkeeping the no-debt rule refuses. **Totals derive from the frozen `teacherShareSnapshot` values of non-voided AND non-refunded payments in scope, computed once at creation** — a class's centre-cut config changing afterward never moves it. **A later refund is handled by status (M14 follow-up, decided in `00-master-product-spec.md` §5 "Settlement totals"):** while `DRAFT`/`APPROVED` — the payout hasn't left the centre yet — `lib/db/refunds.ts`'s `refundPayment` finds every such settlement in the refunded payment's scope and subtracts its `teacherShareReversed` from `totalAmount` in the same transaction, audited as `settlement.adjust`; once `PAID`, the total is **never** touched — the money is already out, and the loss is handled outside this record. This was chosen over refusing the refund outright (nothing here can cancel a DRAFT settlement, so a legitimate refund would be stranded) or merely blocking the settlement's next transition without fixing the number (leaves a wrong total visible to the teacher indefinitely). `lib/db/settlements.ts` also refuses to let the same money be claimed twice at creation: `createSessionSettlement` refuses a session that already has a settlement (`sessionAlreadySettled`), and `createPeriodSettlement` refuses a date range overlapping the same teacher's existing scope (`overlappingSettlement`) — overlap is per teacher, so two different teachers may share the exact same period. The `Payment` rows remain the source of truth, and this record is the *decision* about them, not a second copy of the money. Both shapes are first-class because real centres do both: a centre paying cash right after one session marks that session's teacher share paid (from the session detail page itself), and a centre settling monthly rolls a period up (`/settlements`). Every transition is permissioned (`settlement.manage`) and audited (`settlement.create`/`settlement.approve`/`settlement.pay`). **Carved out of the data-visibility window** (§7) — a teacher who cannot read a four-month-old settlement cannot verify they were paid, which makes the record worthless. **SEC-2b (D-05, D-12, D-16):** a settlement **claims** the payments it counts — see **SettlementClaim** — and its `totalAmount` always equals the sum of its live claims' `teacherShare`; `status` gains **CANCELLED** (a DRAFT only, with `cancelledBy`/`cancelledAt`), which releases its claims; approve/pay are conditional updates on the expected status, and a non-OWNER may not approve or pay a settlement they created.
- **SettlementClaim** *(SEC-2b, D-05 (c) — closes OD-8 and SEC-06)* — `centerId`, `settlementId`, `paymentId`, `teacherShare` (the payment's frozen `teacherShareSnapshot` at claim time), `releasedAt`, `createdAt`. A payment holds **at most one live claim** (`releasedAt` null) — a partial unique index, `SettlementClaim_one_live_per_payment`, raw SQL in the migration — and the claims are written in the same transaction that creates the settlement, after a per-(centre, teacher) advisory lock. Cancelling a DRAFT, or a later void/refund adjusting an unpaid settlement, stamps `releasedAt`; a claim is never deleted. Existing settlements were backfilled with the payments their totals had counted (none was counted twice).
- **ExpenseCategory** / **Expense** — center expenses with category, amount, date. `ExpenseCategory.active` (M6) follows the same "deactivate rather than hard-delete while referenced" convention as the other master-data entities in §6. **SEC-2b (D-24):** an `Expense` is **voided, never deleted** — `voided`, `voidReason`, `voidedAt`, `voidedBy` — and every total skips a voided one (`lib/db/analytics.ts`); its date may be backdated within the centre's visibility window, never before it or into the future (`expenseDateError`, `lib/db/visibility.ts`). Create, void and every category change are audited.

### People layer, continued *(M16, M17, F3 delivered)*
- **FamilyLink** *(delivered F3 — OD-6 decided)* — a parent ↔ child relation between **two global `User`s**: `parentUserId`, `studentUserId`, `status` (`ACTIVE | REVOKED`, default ACTIVE), `source` (`STUDENT_INVITE | CENTER_CODE | LEGACY_VERIFIED`), `invitationId` (the accepted `FamilyInvitation`, unique; null for a legacy link), `createdAt`, `revokedAt`/`revokedBy`/`revokedReason`. Unique on `(parentUserId, studentUserId)`; a CHECK forbids linking a person to themself. It carries **no `centerId`** — a cross-cutting identity relation, like `SessionRating` — so it can exist before the child joins any branch; it has no `scoped()` entry because it isolates nothing by itself. **Every read through it is a tenant read through the child's own profile**: the parent portal reads each ACTIVE link's child through that child's **active** `StudentProfile`s at **accessible** centres (`lib/db/parents.ts`'s `activeChildLinks`, the only read a parent-portal page builds on — D-10), with the student portal's centre-scoped functions; staff read and revoke links only for a student with a profile at their own branch (`familyAccessForStudent`, `revokeFamilyLink` — another branch's profile id is `notFound`). Created **only** by accepting a code (`acceptFamilyCode`: one transaction — a conditional PENDING → ACCEPTED on the invitation, the link ACTIVE, `family.link.create` audited ids-only). Ended **only** by explicit revocation (`family.link.revoke`): the branch with a required reason (on the record, never in the audit row — D-20), the parent, or a platform admin — never the student. Revocation is final for its code; relinking with a new code re-activates the same row (the unique pair), and the earlier revocation stays in the audit trail.
- **FamilyInvitation** *(delivered F3)* — one parent code: `studentUserId`, `codeHash` (**sha256 of the code — the plaintext is never stored**; unique; a CHECK accepts only a 64-hex digest), `codeHint` (its last two symbols, CHECK length 2), `source` (`STUDENT_INVITE | CENTER_CODE`), `issuingCenterId` (the branch that printed it; null for a student's own invitation; `ON DELETE SET NULL`), `createdBy`, `createdAt`, the student's **declared** parent — `declaredParentFirstName`/`LastName`/`Phone` (the phone normalized by `lib/phone.ts`; never an identity key, never matched on) — `status` (`PENDING | ACCEPTED | REVOKED`), `acceptedBy`/`acceptedAt`, `revokedAt`. No expiry. **At most one PENDING `CENTER_CODE` per (student, branch)** — a partial unique index in the migration, so regenerating (which revokes the previous one in the same transaction) cannot leave two. A student's **slots** — ACTIVE links plus PENDING invitations of any source — are capped at 3, counted under a per-student advisory lock (`lib/db/parents.ts`). Global like `FamilyLink`; a branch reads only the codes it issued.
- **ParentLink** *(delivered M16 — **deprecated at F3**, not read or written anywhere)* — the old phone-matched parent↔child row. The F3 migration (`20261026110000_f3_family_links`) copied every VERIFIED row into a `FamilyLink` (`LEGACY_VERIFIED`, the parent and the profile's `userId`, deduplicated, earliest verification as the date); PENDING rows were not migrated. The table stays untouched until it is dropped after the pilot (`05-phase-2-backlog.md`). What it was: `parentUserId` (the parent's global `User`), `studentProfileId` (the child), a denormalized `centerId`, `status` (`PENDING | VERIFIED | REVOKED`), `matchedPhone`, `verifiedAt`/`verifiedBy`, `revokedAt`/`revokedReason`; unique on `(parentUserId, studentProfileId)`. Origination by a phone match and the (disabled) staff verify seam are both gone (OD-6, decided at F3 — `00-master-product-spec.md` §5.1 "Parent role & portal").
- **SessionRating** *(delivered M17)* — `studentUserId` (the global `User` — a rating is the student's own act, the same identity the login pop-up authenticates against, not a centre-local `StudentProfile`), `sessionId`, the rated `teacherId` (denormalized from `session.teacherId` at rating time, the same reason `Payment.teacherId` is denormalized — the aggregate is one indexed `aggregate`/`groupBy` rather than a join through sessions), `score` 1–5. Unique on `(studentUserId, sessionId)` — one rating per student per session, never re-rated. Deliberately carries **no `centerId`**: the published aggregate is platform-wide by design (see below), so there is nothing here for `lib/db/scoped.ts` to scope — `lib/db/ratings.ts` takes `teacherId` directly, the same "cross-cutting read, not a `scoped()` entry" shape `Settlement`/`Refund` already use for `centerId`. **The rater's identity is stored and never exposed** — not to the teacher, not to the centre, not through any read path: `lib/db/ratings.ts` exports only `teacherRatingAverage`/`teacherRatingAverages` (`{ average }`, never a count, structurally — not just hidden in a response the caller trims) plus the write functions; no function anywhere lists raw rows by `teacherId`, which is what a teacher would need to work out who rated them. The rating **follows the teacher across centres** — keyed on the global `teacherId`, not on a membership — because it describes the person, like their identity, not their relationship with one employer; `npm run check:ratings` asserts the same `teacherId` produces the same combined average regardless of which centre's session it was earned at.
- **SessionRatingSkip** *(delivered M17)* — `studentUserId`, `sessionId`, unique on the pair. The persistence behind "skipping costs nothing": the login pop-up's candidate query (`attendedSessionsToRate`) excludes a session with a row here exactly like it excludes an already-rated one, so an explicit skip never re-surfaces that session — on this device, on any other, at this login or a future one. A dedicated table rather than a sentinel `score` value, so `SessionRating`'s own `avg`/`groupBy` never needs to filter a placeholder out.

### Workflow layer
- **Reservation** — student's request to join a class: status (PENDING/CONFIRMED/REJECTED/CANCELLED). **Delivered at M8** (`lib/db/reservations.ts`). `studentId` references the global `User`, not a `StudentProfile` — deliberately, since a PENDING request can exist before the student has any local record at that center at all; the `StudentProfile` is created only when a seat is actually claimed (instantly, or on confirmation), via `ensureStudentProfile()` — the same "seed once from `User`, then independently editable" shape as `createPerson()`/`seedLocalName()` (§6), just triggered by the student themselves rather than staff. Unique on `(classGroupId, studentId)` with no `centerId`/`status` in that key, so — like `Enrollment` — the row is reused across its lifecycle rather than recreated: a REJECTED/CANCELLED request, re-requested later, resets the same row to PENDING instead of inserting a second one (which the constraint would refuse). **The reused row is also what makes the 7-day cooling-off cheap (delivered M15)**: `rejectedAt` (a new column, stamped by `rejectReservation`) on this same row is the whole mechanism — `lib/capacity.ts`'s `isInCooldown`/`cooldownUntil` reads it back in `reserveOrEnroll`, refusing a re-request inside 7 days of it with the UI stating the retry date plainly rather than failing silently (`00-master-product-spec.md` §5.1 "Approvals & enrolment"). Both `StudentBlock` scopes are re-checked at request **and** at approval time, so a block placed between the two refuses the approval. `confirmReservation`/`rejectReservation` (center/teacher-side) and `cancelReservation` (student's own, pinned to their `studentId`) are real and gated by `npm run check:student-portal`, `npm run check:approvals` and (M15's new cases) `npm run check:enrollment`; as of the **Approvals** milestone they have a real UI caller (`/approvals`, `app/[locale]/(center)/approvals/actions.ts`), closing the gap noted at M6/M7/M8 (`00-master-product-spec.md` §4.1 item 9) — and as of **M15**, a second real UI caller at `/teacher/approvals` (`app/[locale]/(teacher)/teacher/approvals/actions.ts`), the teacher's own narrower queue over the same rows.
- **SessionBooking** *(F6)* — a student's request to attend **one session** of a class without enrolling: `centerId` (indexed, cascade), `sessionId` (cascade), `studentId` (the global `User`, like `Reservation` — a PENDING booking can exist before any local record; indexed), `status` (`PENDING | CONFIRMED | REJECTED | CANCELLED`), `requestedAt`, `resolvedAt?`/`resolvedBy?`, `cancelledAt?`/`cancelReason?` (`STUDENT | SESSION_CANCELLED | SESSION_RESCHEDULED | STAFF`; a CHECK ties a reason to CANCELLED and to nothing else), and `sessionAttendeeId?` (`@unique`, `SET NULL`) — the roster row a check-in turned it into. Unique on `(sessionId, studentId)`, so a cancelled or rejected booking is **reused** on re-booking, never a second row. The `StudentProfile` is made (`ensureStudentProfile`) only when the booking is CONFIRMED. **It records no money**: the student pays at the desk, where `createAttendance` links `sessionAttendeeId` in the same statement as the roster row, and the row is an ordinary drop-in (`isDropIn: true`, no enrolment) — so a booked no-show writes nothing at close (absences stay enrolled-only, R2). A CONFIRMED booking takes one of the session's seats: seats = the class's seat limit; used = active enrolments + CONFIRMED bookings + walk-ins (Present/Late drop-ins no booking links). Written only by `lib/db/session-bookings.ts`; read through `scoped(ctx).sessionBookings` and the student's own identity-scoped `listBookingsForStudent`. RLS on, zero policies (SEC-2a). Migration `20261027150000_f6_session_bookings`.
- **ChangeRequest** — teacher's request to add a class/session at a center: type, payload JSON, status, resolvedBy. Feeds the Approvals screen. As of **M7**, the write path and a teacher's own "my requests" list are real (`scoped(ctx).changeRequests` in `lib/db/scoped.ts`, written from `/teacher/classes`). Two payload shapes exist: `NEW_CLASS` (subject/grade/timing/attendance settings, since M7 — it also carried `capacity` until R3 removed the field; old payloads keep the key and every reader ignores it) and, as of **M10**, `NEW_SESSION` (`classGroupId`/date/startTime/endTime/note, written from `/teacher/sessions`). As of the **Approvals** milestone, a request no longer sits `PENDING` forever: `lib/db/approvals.ts`'s `resolveChangeRequest` flips a `NEW_CLASS` request to `APPROVED`/`DECLINED` (checked for `PENDING` first — an already-resolved request cannot be re-resolved), called from `/approvals`. Accepting a `NEW_CLASS` request is a status flip only, **not** a `ClassGroup` creation — see the decision record at `00-master-product-spec.md` §4.1 item 9. A `NEW_SESSION` request is different (M10): it names an **existing** `ClassGroup`, which already has a decided price, center-cut and room — every field a `NEW_CLASS` request is still missing — so `lib/db/approvals.ts`'s `resolveSessionRequest` immediately creates the `Session` on approval, re-running the same teacher/room conflict check every slot write uses (`findSessionConflicts`; R4: refused as `classNotFound` for a deactivated class) and respecting the center's own `scheduleConflictPolicy` exactly like `rescheduleSession` does (WARN refuses with the conflict list until the approver confirms, then creates it and audits the confirmation — R3; DENY refuses as `conflict`) — no money, room, or scheduling decision left to guess at, so there is no reason to defer. `payload` stays untyped `Json`, genuinely read back by the Approvals screen (subject/grade/class names resolved separately since the payload only carries ids) rather than by nothing.

### Platform / trust layer
- **AuditLog** — `centerId?`, actorUserId, action, entityType, entityId, before/after JSON, createdAt. Written for financial, permission, and attendance-correction changes. `centerId` is nullable specifically for platform-level actions that belong to no single tenant (`lib/db/audit.ts`'s `AuditInput.centerId` was `string | null` from the start, docs/02 §5, for exactly this case) — as of **M9**, `platform.center.create`/`platform.center.activate`/`platform.center.suspend`/`platform.center.plan.update` all carry a real `centerId` (the tenant acted on), while `platform.support.access` — written on every visit to that tenant's admin detail page, the "controlled privileged support access" the spec calls for (§4.4) — also carries the viewed center's id, never null, so a center's own audit trail shows every time a super admin looked at its data.

## 3. The financial ledger — the part to get perfectly right

**The flow of one paid attendance:**

1. A `Session` is created from a `ClassGroup` (R4: for its whole period, when the class is created or its schedule edited; R5: or by hand as an extra session, which copies the class price the same way). At creation it copies the class price into `session.priceSnapshot`. **SYS (user-confirmed):** editing the class's price later reprices the class's sessions dated today or later that are **not closed and hold no payment** (`repriceClassSessions`, audited with the counts); a session with any payment keeps its price, and a recorded payment never changes (`00-master-product-spec.md` §5.1 "A class price edit reprices its open sessions"). There is no per-session price editor.
2. At the desk, the student is marked on the roster → a `SessionAttendee` row (Present/Late, `isDropIn` true or false).
3. Payment is confirmed → a `Payment` row is created, and **at that instant** we compute and freeze:
   - `amount` = what was collected (normally = session price).
   - `centerShareType`/`centerShareValue` = the session's own override (M13) if it has one, else the class's current cut. **A one-time session (R5, no class) has only its own two fields** — they are its cut, its `priceSnapshot` was typed at creation, and if either cut field is missing the payment is **refused** (`missingCut`), never defaulted.
   - `centerShareSnapshot` = `centerShareType == FIXED ? centerShareValue : round(amount * centerShareValue / 100)`.
   - `teacherShareSnapshot` = `amount − centerShareSnapshot`.
   - `priceSnapshot` = the session price at that moment.
   - `paymentMethodId` + `methodLabelSnapshot` (R1) = the chosen `CenterPaymentMethod`, resolved **inside the same transaction** filtered by `centerId` **and** `active` (another centre's id or an inactive one is refused as `invalidMethod`), and that method's `name` copied verbatim.
4. These three snapshots are **immutable**. Analytics and settlements read them directly; they never recompute from the class config. `methodLabelSnapshot` follows the same rule for the label: renaming or deactivating a method never relabels a recorded payment, and every display of a recorded payment reads the snapshot, never the method's current name. The method carries no money — `lib/money.ts` never sees it.

**Why snapshots, concretely:** teacher raises their price / center changes its cut in March. February's already-recorded payments must still show February's split, or a teacher will (rightly) dispute the books. Recomputing live is the classic bug that loses a client. Snapshot = the books are always internally consistent and auditable.

**Corrections & refunds:** never `UPDATE` a `Payment`'s money fields. Instead mark it `voided` (with a **required** reason + `AuditLog`) and, if needed, write a corrected `Payment`. History stays intact. This is why `Payment.sessionAttendeeId` is **not** a plain unique column (revised at M5, `lib/db/payments.ts`): a void keeps its row and a correction adds a second `Payment` against the same `SessionAttendee`. "At most one **active** payment per attendee" is, since SEC-2b, **the database's rule as well as `recordPayment()`'s**: a partial unique index `Payment_one_active_per_attendee` on `(sessionAttendeeId) WHERE voided = false AND refunded = false` *(T5 — it was `WHERE voided = false`; a refund now frees the slot as a void does, so a student reset by a refund pays again with a new row; the invariant is the same in kind: at most one payment per attendee that is neither voided nor refunded)*, which `recordPayment` inserts against with `ON CONFLICT ("sessionAttendeeId") WHERE "voided" = false AND "refunded" = false DO NOTHING` (the predicate must match the index exactly, or Postgres rejects the statement; `check:session-lifecycle` and `check:security` assert it against the migration) (a lost race answers `alreadyPaid`), behind the roster-row lock and a fresh re-read after it (SEC-05 — the old check read its answer from a snapshot taken before the lock). A CHECK, `Payment_not_voided_and_refunded`, keeps void and refund exclusive; both lock the payment row and re-read it before acting (SEC-12).

**Void-on-absent (R2):** while a session is live, switching a student with an active payment from Present/Late to Absent voids that payment **inside the same transaction** as the status change and its `SessionAttendanceChange` row (`lib/db/attendance.ts`'s `changeAttendanceStatus`; **the reason is required** for such a change since SEC-2b, D-13). It is an ordinary void — `voided` + reason, money fields untouched, excluded from every total — never a refund, and if the void fails the status does not move. Moving back to Present/Late creates no payment. A closed session refuses every void and refund (`lib/db/session-lifecycle.ts`), which is what lets a settlement built from closed sessions stay correct. A refunded payment can no longer be voided too (it would be subtracted twice).

**Void/refund resets attendance on a live session (T5):** the reverse direction of the rule above. `voidPayment` and `refundPayment` take the session's shared lock, then **the attendee row's lock** (`lockAttendeeRow`), then the payment row's lock. That is the order `changeAttendanceStatus` and `recordPayment` already use, so there is no deadlock cycle. After the flag flips, the same transaction resets a Present/Late attendee to ABSENT with one change row (`voidedPaymentId` or `refundedPaymentId`) and an `attendance.correct` audit row. Two voids of one payment, a void racing a refund, or a void racing a re-check-in or a second payment all serialize on the attendee row, so exactly one wins. Money fields, the `Refund` row and settlement claims are untouched, and the re-payment is a new `Payment` with fresh snapshots. `historicalBackfill` (scripts) skips the reset.

**No debt:** there is no balance table. If a student didn't pay, there's simply no `Payment` row — they're an unpaid/absent attendee. Nothing owes anything. Concretely (M5): a payment can only ever be recorded for a **PRESENT/LATE** `SessionAttendee` — "attend = pay, or not counted" (spec §2) is enforced in `recordPayment()`, not just hinted at in the UI.

**Rounding rule:** percentage cuts round to the nearest piastre (`Math.round`); document any change here because it affects totals.

**Consecutive-absence counting (M5, spec §7 acceptance criterion 13):** `lib/db/attendance.ts`'s `consecutiveAbsenceCount()` walks a student's `SessionAttendee` history for one `classGroupId`, most-recent-first, counting `ABSENT` rows until the streak breaks — capped at 50 rows. Any non-ABSENT mark breaks the streak; with exactly three statuses (R1) that means PRESENT or LATE. Shown today on the session receipt (`app/[locale]/(center)/sessions/[id]/session-receipt.tsx`); the spec also calls for it on the student's own profile page, which is not yet built (tracked as a gap, not silently dropped). **R2:** an enrolled student who simply did not come now gets a real ABSENT row when the session closes, so the streak counts no-shows too — not only students someone remembered to mark absent. Until a session closes (by hand, or lazily on its next touch after its day), its no-shows have no row yet.

## 4. Multi-tenant isolation strategy

**Primary defense — application layer.** Every tenant-scoped query goes through a helper that requires a resolved `centerId` from the session context and injects it into the `where`. No raw `prisma.session.findMany()` without a center scope — that's a lint/review red flag. A `getTenantContext()` resolves the current user's membership + active center on every request.

**Backstop defense — the Data API is closed (SEC-2a, D-19 (a)).** *(Corrected — this used to promise per-tenant RLS policies that never existed.)* Every table in `public` has RLS on with **zero policies**, and the Supabase Data API roles (`anon`, `authenticated`) hold no privilege on the schema, its tables, sequences or functions, now or through default privileges — a checked-in migration, asserted live by `npm run check:rls`. That closes PostgREST/GraphQL to the public anon key on every project. It is **not** a backstop for the app's own queries: Prisma connects as `postgres`, which has BYPASSRLS on Supabase, so the application layer above is the isolation boundary, full stop (`02-architecture.md` §5; a non-bypass app role with per-tenant policies is `05-phase-2-backlog.md` entry 23).

**Branch (organization) visibility — M11.** An Owner resolving to several centres, or a Manager the Owner has granted extra branches, is **not** a widening of the isolation model. Their context resolves to a **set** of `centerId`s instead of one, and every query still runs `centerId`-scoped against exactly one of them; a multi-branch view is the union of those results, computed in the application layer. This is the same shape `getTeacherContexts` established at M7 and `lib/db/discover.ts` at M8 — one context per centre, unioned by the caller, never a `where` spanning centres. Consequently `lib/db/scoped.ts`, `getTenantContext()`'s scoping behavior and `npm run check:isolation` are **unchanged** by M11, which is the whole reason the org layer is additive rather than a rename.

**Teacher visibility of other centres — the leak M12 closes.** A centre Owner or Manager viewing a teacher **must not see which other centres that teacher works at**. The teacher-detail loader must select only this centre's membership and this centre's history; a naive `include: { memberships: true }` on the global `User` leaks the whole list. The teacher's portability belongs to the teacher, and this is the same boundary `05-phase-2-backlog.md` entry 2 refuses to cross for cross-centre scheduling.

**Teacher cross-center visibility.** A teacher's portal queries span the centers they're a member of, but each center's rows are still filtered by that membership's granted visibility. Combined views are unions of permitted per-center data — never a bypass of scoping.

As of **M7** this is real: `getTeacherContexts(userId)` (`lib/auth/tenant.ts`) resolves *every* center a user has a `TEACHER` membership at — ignoring the single-center `kayedu_center` active-center cookie entirely — into one full `TenantContext` per center (its own `CenterSettings`, its own `grants`). The teacher dashboard loops over these contexts and calls `lib/db/teacher-portal.ts`'s `teacherCenterSummary(db, centerId, teacherId, …)` once per center — each call still just a `centerId`-scoped `where`, identical in shape to any single-center query — and only combines the results in memory (`combineTeacherSummaries`, a pure sum with no query of its own). The per-center pages (`/teacher/sessions`, `/teacher/students`, `/teacher/classes`) stay single-center, reading through the *active* center's context exactly like the center-staff pages do; switching which center is active reuses the existing `/select-center` cookie flow rather than adding a second switching mechanism.

**Student cross-center visibility (M8).** A student's own data is read the same identity-scoped way `getUserCenterRelations` already reads `Membership`/`StudentProfile` — by `userId`/`studentId`, not by looping a single `centerId` through every query — because a student can have a PENDING `Reservation` at a center where no `StudentProfile` exists yet (`lib/db/student-portal.ts`'s `studentBlockedRefsByCenter`/`studentReservationStatusByClass`/`studentActiveEnrollmentClassIds`, and `getStudentContexts` in `lib/auth/tenant.ts` for the centers that *do* have a profile). This is still not a query spanning two centers' data: filtering strictly by "this exact authenticated user's own id" can only ever return rows this one person owns, across however many centers — the same category of exception `getUserCenterRelations` already established, not a new one. **Discover** (`lib/db/discover.ts`) is the one genuinely cross-center *browse*: it loops every active `Center` and runs one `scopedWhere(centerId, …)`-scoped query per center (mirroring the teacher portal's "one context per center, unioned in memory" shape exactly, just keyed by every center instead of by one teacher's memberships), then filters/paginates the combined result in the application layer — never a `where` spanning more than one center at the database layer.

**The two isolation tests that must pass** (from the spec's acceptance criteria): shared-teacher no-leak, and Center-X-can't-read-Center-Y-by-ID. Both are automated: `npm run check:isolation` (M1) for the by-ID case, `npm run check:teacher-portal` (M7, `scripts/teacher-portal-check.ts`) for the shared-teacher scenario, and `npm run check:student-portal` (M8, `scripts/student-portal-check.ts`) for the student-portal equivalent — a block placed at one center must not leak into another, and neither center may resolve the other's `Reservation`/`StudentProfile`/`Enrollment` by id — one teacher User with two `TEACHER` `Membership` rows, independently seeded sessions/payments/students at each center, asserting the combined dashboard total is exactly the sum of two independently-scoped per-center summaries and that neither center's session/student/payment/block/`ChangeRequest` rows resolve from the other center's scope.

## 6. Naming & convention notes

- Tables/models: PascalCase singular (`ClassGroup`). Enums: PascalCase. Fields: camelCase in Prisma (maps to snake_case columns via `@map` if preferred).
- Every tenant table: `centerId String` + `@@index([centerId])`, and compound indexes on hot query paths (e.g. `@@index([centerId, date])` on `Session`). **SYS** added four found by read-only `EXPLAIN` on the dev database (migration `20261019090000_sys_hot_query_indexes`, additive only): `Payment(sessionId)` (the receipt and roster — and the foreign key had none), `SessionAttendee(studentProfileId)` (a student's history and absence streak), `AuditLog(centerId, createdAt)` (the audit screen's newest-first page) and `Reservation(studentId)` (a student's own requests).
- Timestamps: `createdAt`, `updatedAt` everywhere.
- Money: store EGP as **integers in piastres** (i.e. `Int`, amount × 100) to avoid floating-point money bugs — or `Decimal`. **Decision: use `Int` piastres.** Document any display conversion in one place.
- Soft-delete the things centers care about auditing (students, teachers, classes) via `active`/`deletedAt` rather than hard delete.
- **People deletion is a relationship deletion.** Deleting a teacher removes their `Membership` at that center; deleting a student removes their `StudentProfile`. Both are refused while history exists — a teacher with classes/sessions, a student with attendance or payments — and the center is told to deactivate instead, because money and attendance are append-only (§3). The global `User` row survives, and is removed only when the person has never signed in (`authId` is null) and holds no other membership or student profile anywhere: someone this platform created who now exists nowhere. Both deletions write an `AuditLog` row, as do block and unblock.
- **Name, like contact, is center-local — nothing about a person's record is global-locked (revised again).** `StudentProfile` and `Membership` each carry their own `firstName`/`lastName` alongside `email`/`phone`/`altPhone`. When a center's record is created — registering a student, adding a teacher — the local name is **seeded** from the relevant `User`: for a brand-new person it's simply what was typed on the form (`createPerson()` in `lib/db/identity.ts`); for a person who matched an existing identity it's that person's **actual** name (`seedLocalName()` in `lib/db/identity.ts`), not whatever staff happened to type before the match was found. From that moment on the local name is editable at that center **immediately, with no lock of any kind** — a teacher shared by two centers can have a different spelling, nickname, or even a different name at each. `User.firstName`/`User.lastName` stay the platform-wide default (still required, since `User` must always have a name to exist as a person) and are never written back to by a center's edits — `localName()` in `lib/identity.ts` reads the local value and falls back to the global one only for the rare record whose local name was never seeded (a `Membership` created through the older staff-invite path, which this predates and does not touch). Fully symmetric with contact now: nothing on a `StudentProfile`/`Membership` is gated by sharing or by whether the person has signed in.
- **Duplicate-matching searches three tables, not one — but links on one key (SEC-2a).** `findPeopleByContact()` (`lib/db/identity.ts`) checks the global `User` **and** every center's local `StudentProfile`/`Membership` contact columns, because a person may have been entered somewhere with a contact that never made it onto their global `User`. Since SEC-2a only a match on the person's **global email** may be *linked* (`isLinkableMatch`; confirmed, under `REQUIRE_EMAIL_CONFIRMATION`, when it is a login's email): a phone (D-02) or another centre's local record only ever refuses — "already registered here", or a staff/administrator contact in the inline new-teacher flow. `resolveContact` returns none / matched / conflict / rateLimited, rate-limits every caller per staff member and per centre (`RateLimitBucket`, D-08), and `describeMatch` names the person only when they are known inside the viewing centre's organisation.
- **Contact details are stored normalized** — email lower-cased, Egyptian mobiles as E.164 `+20XXXXXXXXXX` (U4; `01XXXXXXXXX` before) — so the duplicate match in `lib/identity.ts` cannot be dodged by typing `+20…`, `0…` or Arabic digits. The unique columns are on `User` only; the center-local copies on `StudentProfile`/`Membership` are deliberately **not** unique-constrained — two different people at two different centers can legitimately share a contact string (a shared front-desk phone, a family email), and it is the global `User` uniqueness plus the match workflow that keeps one human one row.
- **Student codes are system-assigned, never typed.** `StudentProfile.studentCode` is claimed from a per-center `StudentCodeCounter` row with one atomic `INSERT … ON CONFLICT DO UPDATE … RETURNING`, inside the same transaction that creates the `StudentProfile` (and the new `User`, when there is one) — see `lib/db/students.ts` (`claimStudentCode`). Postgres's row lock on the counter's primary key makes concurrent claims race-free: two receptionists registering at once still get consecutive, non-colliding numbers. Running the claim and the insert in one transaction means a failure anywhere else rolls both back, so a crash never burns a number into a permanent gap. Codes start at `1001` and are a center's own numbering — the same number legitimately exists in two different centers.
- **Config master data (rooms, payment methods (R1), expense categories, and the centre's catalog selections) deactivates by default.** Payment methods go one step further: a delete on a referenced method *deactivates it instead* rather than refusing, and the last active method can be neither deactivated nor deleted (`lib/db/payment-methods.ts`). Hard delete is offered in the UI but refused while anything still references the row: these relations are optional FKs, so Postgres would `SET NULL` and silently orphan (a grade losing its subjects, a room losing its sessions) rather than fail. The settings actions count references first and tell the center to deactivate instead. *(Education systems, grades and subjects leave this list at M13 — a centre no longer owns those rows, it owns a `CenterCatalogSelection` pointing at them, and deactivating is done to the selection.)*
- **Soft-delete is the default everywhere removal could corrupt history or analytics (delivered M18).** Hard delete is reserved for rows nothing references. This is not a new principle — it is the one above, applied consistently across every entity rather than only to master data. **Audited and confirmed already correct**: every entity with downstream history (students, teachers, classes, rooms) already refuses a hard delete while attendance/payments/classes/sessions/enrollments reference it and already offers a deactivate escape hatch — the sweep found no gap to close there. **The 404 on student delete was a bug** (and the same bug existed for teachers and classes too) — not a soft-delete gap but a missing redirect: the delete control lives on the record's own detail page, so a hard delete with no redirect let Next's automatic post-action refresh of that same route re-fetch the now-gone row and 404. Fixed in all three places by redirecting to the list on success (`00-master-product-spec.md` §5.1 "UX & data integrity").
- **Phone numbers normalize through exactly one function (delivered M18; E.164 since U4).** `0100…`, `100…`, `+20100…`, `0020100…` and `20100…` — any spacing or punctuation, any of the three digit scripts — all become `+20100…`. That single normalizer (`lib/phone.ts`) is used by **validation, duplicate-matching and search alike** — three implementations of this rule would be three different answers to "is this the same person," which is precisely the question the duplicate-match workflow exists to answer. This tightens the rule already stated above ("contact details are stored normalized") into a single-implementation requirement, asserted by `npm run check:people`'s static sweep rather than eyeballed.
- **Phone numbers — the stored form (U4).** Every phone column holds only E.164 `+20` + the 10-digit national number, or null: `User.phone` (the one unique phone column), `User.altPhone`, `User.contactPhone`, `Membership.phone`/`altPhone`, `StudentProfile.phone`/`altPhone`/`parentPhone`/`parentAltPhone`, `FamilyInvitation.declaredParentPhone` and the deprecated `ParentLink.matchedPhone`. Every writer goes through `normalizePhone` — the zod schema for forms, and the writers themselves (`createPerson`, `addTeacherMembership`) for any caller that skips zod. The data migration `20261031090000_u4_phone_e164` is one `DO` block (all or nothing): it strips spaces, dashes and one leading `+`, requires `01XXXXXXXXX` or `201XXXXXXXXX` (so an E.164 value passes and a re-run is a no-op) and RAISEs naming the table, column and count otherwise; it RAISEs if two `User.phone` values would become equal; then converts and re-checks. `npm run report:phones` runs the same test SELECT-only.
- **A self-registered student's profile is a stub exactly once (delivered M18).** `StudentProfile.profileCompletedAt` (nullable) distinguishes `ensureStudentProfile`'s (M8) auto-seeded row — name/email/phone/altPhone only, no grade, no parent contact — from a whole one; a receptionist's own add-student form stamps it immediately, since that form already collects everything. The `(student)` route-group layout checks it on every request and substitutes a one-time completion form for whatever page was actually asked for until it's set (spec §4.3 item 4) — a read restriction on reaching the rest of the portal, not a schema restriction on the row itself, and never revisited once stamped. **F4:** when the account carries a grade the branch offers *and* a declared parent phone, the profile is created already whole (`profileCompletedAt` stamped by `ensureStudentProfile`) and the form never appears; otherwise the stub and the one-time form behave exactly as before.

## 7. The data-visibility windows (delivered M19, split at U6)

**The rule.** No centre-side role (OWNER/MANAGER/RECEPTIONIST/ACCOUNTANT) may read data older than its branch's window. **Since U6 each branch has two** (decided with Kamal, 29 Oct), both adjustable by the branch and by a platform admin, and both **bypassed entirely by a platform admin's own reads**:
- **`CenterSettings.centerDataVisibilityDays`** (1–365, default 365) — the centre's own analytics, money, sessions and attendance: `visibilityWindowFloor`, and the floor `scoped(ctx)` injects (`centreReadFloor`).
- **`CenterSettings.teacherDataVisibilityDays`** (1–30, default 30) — reads about one teacher: the Analytics by-teacher breakdown and every Analytics view filtered to a teacher (`teacherVisibilityWindowFloor`). Independent of the centre window.

The full read-by-read table is in `00-master-product-spec.md` §5 "Data visibility window". TEACHER/STUDENT/PARENT reads are never windowed by a branch. A teacher's own portal is limited only by their own **`User.teacherHistoryDays`** (0 = all history, the default; `teacherHistoryFloor`/`teacherPortalHistoryFloor` in `lib/db/visibility.ts`/`teacher-portal.ts`) — applied to the portal's dashboard, session list, students, student history and session detail, never to a write's integrity check and never to settlements. The caps are enforced server-side by the schemas the actions parse with; a missing field means that field's default. Existing branches were backfilled from the old `dataVisibilityDays` (clamped to each cap) by migration `20261031150000_u6_split_visibility_windows`.

**Expressed as a rolling day count, not a calendar-month anchor.** Each window counts its days back from *today* — **the centre's calendar day** (R7b: `todayInTimezone(CenterSettings.timezone)`, `02-architecture.md` §11 "One owner of today"), so the floor flips at the centre's midnight, not UTC's; between 00:00 and 03:00 Cairo time a UTC-anchored floor was a day too old — computed fresh on every request (`lib/db/visibility.ts`'s `visibilityWindowFloor`) — deliberately not "since the 1st of this calendar month," which would silently jump the visible horizon backwards by up to 30 days at the start of every new month. A rolling window also keeps the "widen it and see more instantly" property exact: the floor moves by exactly the days added, nothing else.

**Four properties that are part of the decision, not implementation detail** (`00-master-product-spec.md` §5.1):

1. **It is a read restriction and never a deletion.** Every snapshot row stays exactly where it is — nothing is pruned, archived out, or made unrecoverable. Widening the window restores full visibility instantly, because nothing was lost. This is what keeps the window compatible with §3: money is append-only, and a visibility rule that deleted anything would break that outright.
2. **It is enforced in the data layer, not the UI.** The date bound is injected by the scoped query helpers alongside `centerId` — the same seam, at the same point — so a direct URL or API call cannot reach past it. This deliberately mirrors the shape the receptionist profit-denial already has (`00-master-product-spec.md` §7 criterion 9): a loader-level refusal and a scoped query, not a hidden button. A UI-only window would be a suggestion. **Delivered at M19 per page; in the helpers since SYS (SEC-62, option (a)):** `scoped(ctx)` ANDs the floor (`centreReadFloor` — centre-side roles only) into every `Session`, `SessionAttendee`, `SessionAttendanceChange`, `Payment` and `Expense` read — by date, through the session's date for the three that hang off a session — so an out-of-window record read by id is `null` like a foreign one, and lists, counts and the absence streak stop at the floor; `refunds.list` keeps its `refundedAt` floor; the pages still clamp their date filters (`clampRangeToVisibility`). The only way past it is `scopedIgnoringVisibilityWindow(ctx, "integrity" | "settlement" | "audit")` — delete blockers and the two carve-outs (`02-architecture.md` §5).
3. **Settlement / payout records are carved out** and stay visible regardless of age. Otherwise a teacher can never verify they were paid, which makes the settlement record worthless — see the Finance-adjacent layer. **Refund records are not carved out** — a refund is money moving, not a payout, so it is windowed like everything else.
4. **Audit logs are carved out.** An audit trail a centre cannot read past last month is not an audit trail.

**What it is not.** Neither window is a retention policy, not a compliance control, and not a security boundary against a hostile insider (a centre-side user who could read last month's data can read it, write it down, and keep it). It is an operational guardrail: it keeps day-to-day screens focused on the live window and limits the blast radius of a compromised or over-curious account. Say that plainly rather than letting it be mistaken for something stronger.

Gated by `npm run check:visibility` (`scripts/visibility-check.ts`); the floor's anchor day is pinned at 00:30 and 23:30 Cairo under both offsets by `npm run check:timezone` (R7b).

## 8. Security-support tables and database rules (SEC-2a, SEC-2b)

- **RateLimitBucket** — the shared store behind `lib/rate-limit.ts`: `key` (primary key, e.g. `identityLookupPerUser:<userId>`), `windowStart`, `count`. One atomic upsert per call (a fixed window); rows older than a day are pruned opportunistically. Global and tenant-free — it holds counters, never data. Replaces the M18 in-process `Map`, which gave every serverless instance its own allowance (SEC-11, SEC-67).
- **Every new table must enable RLS in its own migration** (`ALTER TABLE "X" ENABLE ROW LEVEL SECURITY;`) — `npm run check:rls` fails otherwise. Default privileges already keep `anon`/`authenticated` from being granted anything on it.
- **SEC-2b — rules the database itself enforces** (migration `20261018090000_sec2b_money_integrity`, raw SQL Prisma's schema language cannot express; `prisma migrate diff` reports no drift):
  - `Payment_one_active_per_attendee` — partial unique on `Payment(sessionAttendeeId) WHERE voided = false AND refunded = false` (§3; the refund clause since T5, migration `20261027190000_t5_void_refund_reset_attendance`).
  - `Payment_not_voided_and_refunded` — CHECK `NOT (voided AND refunded)`.
  - `SettlementClaim_one_live_per_payment` — partial unique on `SettlementClaim(paymentId) WHERE releasedAt IS NULL` (§2 "Finance-adjacent layer").
  - `Session_freeze_timezone` — a trigger: on insert, a session with no `timezone` gets its centre's `CenterSettings.timezone` (else `Africa/Cairo`); on update the old value is kept. **`Session.timezone`** is therefore the centre's timezone *frozen at creation* (D-14): the write guard (`COALESCE(s.timezone, cs.timezone)`), Present/Late, the end-of-day close, reception's "today" and the teacher edit deadline read it, so editing the centre's timezone moves nothing already created. Existing sessions were backfilled from their centre.
  - `AuditLog_append_only` — a trigger: no UPDATE except a foreign key's own `ON DELETE SET NULL` (`centerId`/`actorUserId` going to null, nothing else changing), no DELETE unless the transaction set `kayedu.audit_maintenance = 'on'` (only the gates' fixture cleanup, `scripts/lib/audit-maintenance.ts`). TRUNCATE (the dev wipe) is unaffected. Rows carry ids, amounts, counts, statuses and dates — never a name, contact or free text (D-20; `lib/db/audit-row.ts` is the one writer and refuses such a payload; `platform.catalog.*` rows are exempt).
  - The two trigger functions are executable by no API role, and `SettlementClaim` has RLS from birth.
