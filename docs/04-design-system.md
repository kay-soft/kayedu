# KayEdu — Design System (Phase 1)

> Derived from the approved visual direction (the five reference screens: Reception Desk, Today's Sessions, Session Detail, Student Profile + ID Card, Analytics). This is the authority for look and feel. Build every screen against these tokens — do not invent new colors, radii, or spacing per screen.

---

## 1. Direction in one line

**Clean, trustworthy, data-dense SaaS** — light working canvas, white cards, a dark sidebar for anchoring, one confident blue as the brand, and color used _only_ to carry meaning (status, money, alerts). Calm enough to stare at for eight hours, sharp enough that an owner trusts it with their money.

---

## 2. Color tokens

Define these as CSS variables on `:root` in `globals.css`. The **brand** value is overridden per center at runtime (see architecture §9) — everything else stays fixed.

```css
--brand: #2563eb; /* primary blue — per-center overridable */
--brand-fg: #ffffff;

--bg-canvas: #f5f6f8; /* app background */
--bg-surface: #ffffff; /* cards, tables, panels */
--bg-sidebar: #0f172a; /* dark navy sidebar */
--bg-sidebar-hover: #1e293b;
--bg-subtle: #f8fafc; /* table header, inset rows */

--text-primary: #0f172a;
--text-secondary: #475569;
--text-muted: #5f6b7d; /* DES: was #94a3b8 — 2.56:1 on white, failed AA for every 12px label */
--text-placeholder: #64748b; /* DES: placeholders had no token and drew in --text-secondary,
                                so an empty field looked already filled in */
--text-on-dark: #e2e8f0;
--text-on-dark-muted: #94a3b8; /* DES: the muted line on the navy sidebar / auth panel (6.96:1) —
                                  the darker --text-muted would be 3.3:1 there */

--border: #e5e7eb;
--border-subtle: #f1f5f9;
--border-strong: #cbd5e1; /* the border a control takes on hover */
--border-control: #848f9f; /* DES: a text field / select at rest. On a white card its edge is
                              the only thing that marks it, so WCAG 1.4.11 asks 3:1 —
                              #e5e7eb was 1.24:1, #cbd5e1 1.48:1; this is 3.28:1 on white,
                              3.03:1 on the canvas */
--border-control-hover: #64748b; /* 4.76:1 */

/* Interaction surfaces. `--bg-subtle` is a *resting* inset (table headers,
   read-only panels), so it cannot double as the hover tint for a control
   that already sits on one. These are the two steps above it. */
--bg-hover: #f1f5f9; /* pointer over an interactive surface */
--bg-active: #e2e8f0; /* pressed */

--success: #16a34a; /* present, paid, positive trend */
--success-bg: #dcfce7;
--warning: #f59e0b; /* late, pending, attention */
--warning-bg: #fef3c7;
--danger: #dc2626; /* absent, negative trend, destructive */
--danger-bg: #fee2e2;
--info: #3b82f6; /* upcoming, neutral badge */
--info-bg: #dbeafe;

/* DES — the same four hues, one shade darker, for TEXT and icons drawn in a
   status colour (badge labels, form messages, inline status words). The fills,
   dots and borders above are unchanged. Measured on their own tint / on white: */
--success-fg: #15803d; /* 4.57 / 5.02 — was 3.00 */
--warning-fg: #b45309; /* 4.51 / 5.02 — was 1.93 */
--danger-fg: #b91c1c; /* 5.30 / 6.47 — was 3.95 */
--info-fg: #1d4ed8; /* 5.49 / 6.70 — was 3.01 */
```

**How these bind to shadcn (`app/globals.css`).** The tokens above are the source; the base-nova variables are aliases onto them, so components inherit the palette without per-screen overrides:
`--background: var(--bg-canvas)` · `--card: var(--bg-surface)` · `--muted: var(--bg-subtle)` · `--primary`/`--ring`/`--sidebar-primary`: `var(--brand)` · `--destructive: var(--danger)` · the sidebar family maps to `--bg-sidebar` / `--bg-sidebar-hover` / `--text-on-dark`. The semantic set is exposed as Tailwind utilities too: `bg-success-bg text-success`, `text-text-muted`, `bg-canvas`, `bg-surface-subtle`, `bg-surface-hover`, `bg-surface-active`, `border-border-strong`.

**Semantic color rules (non-negotiable — consistency here is what makes the app readable at a glance):**

- **Present / Paid / positive** → success green.
- **Late / Pending / warning** → amber.
- **Absent / Void / negative** → danger red.
- **Upcoming / neutral / informational** → info blue.
- **Live / in-progress** → success green with a pulsing dot.
- **Text in a status colour uses its `-fg` shade** (`text-success-fg`, `text-warning-fg`, `text-danger-fg`, `text-info-fg`) — the hue, and so the meaning, is the same; only the lightness changed so a 12px "Late" can be read (DES; `check:design` refuses `text-success` / `text-warning` / `text-danger` / `text-info` on text). Fills (`bg-success`, the live dot), tints (`bg-*-bg`) and borders keep the base token.
- Money figures are **never** colored except for trend indicators (▲ green / ▼ red).
- Subject tags may use a rotating accent palette (blue, green, purple, amber, rose) — assigned per subject, consistent app-wide.

## 3. Typography

- **Font:** Cairo (already loaded via `next/font` — covers Arabic + Latin). One family everywhere.
- **Numerals:** Arabic-Indic (٠١٢٣) in `ar`, Latin (0123) in `en`, via a shared `Intl` formatter helper. Never mix within a locale.
- **Times:** 12-hour with a meridiem — `4:00 PM` / `٤:٠٠ م`, never `16:00`. A start–end pair renders as one range through `formatTimeRange` (`4:00 – 5:30 PM`), which collapses the shared meridiem and picks the locale’s own separator rather than a hand-joined en dash. A formatted time needs no `dir="ltr"` wrapper — the string carries its own direction.
- **Wherever a session is listed, its date rides with its time.** A time alone answers “when in the day”, not “which day”. The two today-only surfaces — the dashboard’s *Today* rail and Reception — are the exception: there the date is the screen’s premise.
- **Scale:**
  | Use | Size / weight |
  |---|---|
  | Page title | 24px / 700 |
  | Section heading | 18px / 600 |
  | Card title | 16px / 600 |
  | Body | 14px / 400 |
  | Table cell | 14px / 400 |
  | Label / caption | 12px / 500, `--text-muted` |
  | KPI figure | 30–36px / 700 |
- Arabic needs slightly more line-height than Latin: use `leading-relaxed` for Arabic body copy.
- **Weights (DES):** 400 body · 500 labels and controls · 600 card/section titles and names · 700 page titles and KPI figures. Nothing else. `CardTitle` is 16px / **600** (it had shipped at 500, lighter than the 14px semibold names inside the card) and renders a heading element (`as`, default `h2`), so every card-based screen has an outline below its `h1`.
- **Figures (DES, measured).** Cairo's Latin digits are **tabular by default** (`1111` and `0000` have the same advance); its **Arabic-Indic digits are proportional and the font has no `tnum` feature for them**. So: every figure carries `tabular-nums` (correct for Latin and any fallback face, harmless for Arabic), and **a numeric column is end-aligned** (`text-end`) so Arabic figures line up by their last digit. Money in a column shows **two decimals** (`formatMoney(…, { fixed: true })`) so `EGP 728` and `EGP 622.50` do not mis-align. A figure never wraps (`whitespace-nowrap`), and a negative amount carries a real minus (`−`), never an ASCII hyphen that wraps on its own.
- **Dates name their month in both locales (DES).** `lib/format.ts` formats a date as day · short month · year — "Oct 15, 2026" / "١٥ أكتوبر ٢٠٢٦". `dateStyle: "medium"` had given English a month name but Arabic a numeric `١٥‏/١٠‏/٢٠٢٦`, which reads as either day-first or month-first; a range collapses the shared parts ("١–١٥ أكتوبر ٢٠٢٦").
- **One numbering system per locale, everywhere.** Arabic shows Arabic-Indic digits in every figure — including the counts inside translated plurals (`{count, plural, …}`), which next-intl would otherwise print in Latin digits. Counts go into messages already formatted by `lib/format.ts`.
- **Placeholders** are `--text-placeholder` (lighter than any value) and read unmistakably as examples: a **name** is prefixed "e.g." / "مثال:" (`e.g. Mona`) — a bare "Mona" in a register form read as already filled in; a **phone or email** shows its format, in Latin digits in both locales because the field is left-to-right (`01012345678`, `name@example.com`).

## 4. Shape, spacing & elevation

- **Radius:** cards & panels `12px`; buttons, inputs, badges `8px`; pills & avatars `full`.
  In Tailwind: `--radius: 0.5rem` makes `rounded-lg` = 8px (buttons/inputs/badges) and `--radius-xl` is pinned to `0.75rem` = 12px (cards). Use `rounded-lg` and `rounded-xl`; don't hand-write radii.
- **Radius by hierarchy (DES):** 12px for containers (cards, dialogs, panels), 8px for controls (buttons, fields, menus), full for pills (status badges, avatars, chips). A status badge is a **pill** — it had shipped at 8px, the same as a button, so it read as something to press.
- **Spacing scale:** 4 / 8 / 12 / 16 / 24 / 32 px. Card padding **16px below `md`, 20px from `md`** (DES: the doc said 24, the `Card` drew 16 at every width; 20 keeps the density this tool needs while giving a desktop card room). **Page rhythm:** 24px between the regions of a page; a section is its heading plus its content at 12px, so a heading belongs to what follows it rather than floating between two blocks (`PageSection`, §5).
- **Shadows:** soft and minimal — `0 1px 3px rgba(15,23,42,.06)` at rest, `0 4px 12px rgba(15,23,42,.08)` on hover/elevated. Available as the `shadow-card` / `shadow-card-hover` utilities. No heavy drop shadows.
- **Borders:** 1px `--border` at rest, `--border-strong` on hover for anything interactive. Prefer a border over a shadow for table and list separation.
- **Floating surfaces** (popover, dropdown, calendar) use `shadow-popover` — deeper than a card, because they sit *above* the page rather than in it.

**Motion.** Short, consistent, and always in answer to something the user did.

```css
--motion-fast: 120ms; /* hover, press, small state flips */
--motion-base: 160ms; /* the default for every interactive element */
--motion-slow: 200ms; /* drawers, popovers, anything that travels */
--ease-out: cubic-bezier(0.16, 1, 0.3, 1);
```

Apply them through the `transition-ui` / `transition-ui-fast` utilities rather than per-component `transition-colors`, so hover, press and focus feel identical everywhere. Nothing bounces, nothing lingers, and **nothing animates at all under `prefers-reduced-motion: reduce`** — one global rule in `globals.css`, so a component added later cannot forget it.

**Interaction states are not optional.** Every interactive element has a visible **hover**, **active**, **focus-visible** and **disabled** state. `Button` carries all four on its base class, so no variant can ship without them; everything that is not a `Button` — links, list rows, calendar days, menu items — applies the `focus-ring` utility (`focus-ring-inverse` on the dark sidebar) instead of writing its own ring. Focus rings are keyboard-only (`:focus-visible`) and always drawn from `--ring`.

**One focus ring (DES).** A **2px `--ring` outline, 2px off the element's edge**, keyboard-only — on buttons, links, rows, chips, menu items and the sidebar (where it is `--brand-fg`, `focus-ring-inverse`). Buttons had a 3px half-transparent halo, links an outline and nav items a ring with an offset — three rings for one meaning. **Text fields and selects** are the one exception: their focus is the brand **border** plus a 3px 25% halo, because a field shows focus with its caret and its edge, not a ring around it. A sticky header never covers the focused element (`scroll-padding-top` on `html` equals the 64px app bar).

**Content width.** One rule, applied by the app shell and nothing else: `--content-max: 96rem`, centred, via the `content-shell` utility. The header bar and the page body share it, so they align. A 1280px laptop is unchanged; a wide monitor gets a wider working area instead of a narrow column stranded in grey.

## 5. Core component patterns

**Sidebar** — dark (`--bg-sidebar`), fixed, 240px (`w-60`), or a **72px icon rail (`w-18`) when collapsed** (M3). Logo + center name at top, nav items with icon + label, active item highlighted with the brand color, user block + sign-out pinned at the bottom; the collapse toggle (`PanelLeftClose`/`PanelLeftOpen`) is the app bar's start-edge button from `lg` (DES, §14.3 — it had sat beside sign-out). Collapsed: labels hide (kept in the accessibility tree via `sr-only`, not unmounted) and the native `title` attribute gives a hover tooltip — no separate tooltip library for a single-line label. The preference is a plain (non-httpOnly) cookie (`lib/ui/sidebar-cookie.ts`, `kayedu_sidebar_collapsed`) written directly by the client on toggle and read server-side by each experience layout before the first paint, so there is no expand-then-snap-shut flash. Mirrors correctly in RTL: the toggle icon flips with `rtl:-scale-x-100`, and the content area's padding uses the logical `ps-*` property so it always tracks the sidebar's actual edge. **Collapses to a full-screen drawer under `lg`** regardless of the collapse preference — a full-screen sheet has no need for an icon rail — hamburger in the header, overlay + slide-in panel, Escape and overlay-tap close it, body scroll locked while open. Implemented in `components/shell/app-shell.tsx`; a single item is `components/shell/nav-item.tsx` (icon + label, the solid brand fill when active — DES dropped the start-edge tab drawn on it, §14.3 — 44px minimum height, a `collapsed` variant). Items come from `components/shell/nav.ts`, filtered by `can(role, permission)` so a receptionist never sees a link they can't open. **There is no placeholder row: a route a later milestone owns is absent from the nav until it ships** (R10a removed the `Soon` badge and the `disabled` field; `check:design` fails on either). **Sections (R10a):** consecutive items sharing a `group` sit under one small heading (`NavGroups` messages — the centre experience has *Front desk · Academics · Money*; Dashboard and Settings sit outside any group); on the icon rail, where there is no room for words, a hairline marks the same boundary. The mobile drawer carries its close button on the brand row, so the drawer opens on the centre, not on an empty strip.

**Dialog** (M3; R10b) — the standard pattern for "Add X" on every list-first entity screen (students, teachers, and every later one). *R10b: the Add student and Add teacher dialogs no longer use this bare primitive — they are the R6 `DialogShell` (§11.15) with titled sections (§11.19), like the class and session dialogs; the paragraph below describes the primitive the shell wraps, which the small settings "Add" dialogs still use directly.* A centered card (`max-w-lg`, rounded, `shadow-card-hover`) from `sm` up; **a full-screen sheet below `sm`**, per the modal→sheet rule in §6. Implemented in `components/ui/dialog.tsx` wrapping Base UI's `Dialog` primitives (already a dependency — `components/ui/button.tsx` uses the same package), exporting `Dialog`/`DialogTrigger`/`DialogContent`/`DialogHeader`/`DialogBody`/`DialogFooter`/`DialogTitle`/`DialogDescription`/`DialogClose`. Backdrop fades and the popup scales in on open using Base UI's `data-starting-style`/`data-ending-style` attributes — plain CSS transitions, no animation library. A visible close button sits at the popup's logical end corner (`end-3 top-3`) and is always present unless explicitly suppressed. **Centering (corrected at SYS):** horizontally by symmetric insets and auto margins (`inset-x-0 mx-auto` with the max width), vertically by `top-1/2 -translate-y-1/2`. The earlier `start-1/2` + `-translate-x-1/2` was *not* direction-agnostic: `start` resolves to `right` in Arabic while a translate is always physical, so every dialog sat half its width off-centre in RTL. Never pair a logical inset with a physical translate — `check:design` refuses it. The close button's label is translated (`Shared.close`). The list page composes it as a small client wrapper (e.g. `add-student-dialog.tsx`) that controls `open` state itself so the form inside can close the dialog on success (`onCreated` callback) while staying open on a duplicate-match result so staff can confirm the link. **Settings master data (R1):** `components/settings/entity-manager.tsx` takes `addVia="dialog"` to put its create form behind an "Add" button in the list card's header (`CardAction`) instead of the always-open add card above the list — used by Settings → Payment methods; rooms keep the original inline card. Rename/deactivate/delete stay inline on each row either way.

**KPI / stat card** — white surface, label (12px muted) above a large figure, trend chip below (`▲ 12.4%` in success/danger). Optional icon chip. Implemented in `components/shared/stat-card.tsx`: `trend` takes a direction plus an already-localized label, with `invertColor` for metrics where a rise is bad news (expenses, absences) so the color follows the meaning rather than the arrow; the icon sits in a neutral chip. **Every card is the same neutral surface (R10a).** The old `accent` prop painted a green/amber/red/blue top border on "Live now", "Not started", "Expenses" and the teacher KPIs — decoration borrowing the status palette — so the prop is gone (`check:design` fails if it returns). **Semantic colours are for status only** (§2): they appear on status badges, trend chips and the attendance/payment controls, never on a tile, a filter chip or a tab. A selectable chip or filter has exactly one selected state — the brand tint (`border-brand bg-brand/10 text-brand`). A card that is not clickable does not lift on hover. The figure itself is never colored. **A zero gets its own treatment** (`zero` + `zeroLabel`): the figure dims and a one-line "no activity in this range" sits under it, because a wall of bold `EGP 0` reads as a broken screen rather than as an answer.

**Data table** — subtle header background, 1px row borders, generous row height (~56px), hover highlight, status as a badge in its own column, avatar+name as a combined cell. **On mobile, tables become stacked cards** — never horizontally scroll a primary table. A column's fixed width is *table* layout, so it is scoped `md:` and up: a card column has no column width, and an unscoped `w-28` truncated money and dates inside a card that had room to spare. The configuration screens share one implementation: `components/settings/entity-manager.tsx` takes a field-descriptor list and drives the create form, the row display and an inline edit panel from it, so a new master-data screen is a page file rather than another table. Editing expands in place instead of opening a modal — one behavior on phone and on desktop.

**Status badge** — pill, 12px medium, tinted background + matching text color from the semantic set (e.g. `--success-bg` + `--success`). Live states get a pulsing dot.

**Attendance control** (M5, revised R1) — three segmented buttons, **Present / Late / Absent** (green / amber / red). R1 removed the fourth segment the M5 build had added (spec §5.1 "Excused removed"), returning to the original three-state mockup. Unselected = neutral outline; selected = the semantic tint. Large touch targets — this is used hundreds of times a day. Implemented in `components/center/attendance-control.tsx` as one `<form>` with three named submit buttons (`name="status" value="PRESENT"`, …) rather than client selection state, so a click is a single round trip with no separate "confirm" step. The status order and tints are exported (`ATTENDANCE_STATUS_ORDER`/`ATTENDANCE_STATUS_TINT`). **R2:** the control is for *corrections* only — an unmarked roster row shows a single **Check in** button instead (Present or Late is decided by the server from the arrival time), and neither Reception's check-in form nor the add-attendee panel offers a status at all; Reception shows a one-line muted note under the payment method saying the status is automatic. `interceptStatus`/`onIntercept` turn one segment into a plain button that opens a confirmation instead of submitting — the roster uses it for **Absent on a paid student**, whose row also says, in muted text, that switching to Absent voids the payment.

**Payment method selector** (M5, revised R1) — icon + label buttons in a row, wrapping, selected state uses a brand-colored ring. The options are **the centre's own active methods** (R1 — Settings → Payment methods), passed in by the page, not a hardcoded list; the centre's first (oldest) method is preselected. Because the names are centre-entered, every button shares one generic wallet icon and a long name truncates inside its button rather than widening the row. Implemented in `components/center/payment-method-selector.tsx` — client selection state (unlike the Attendance control), because the method is chosen before the surrounding form's own single submit records the payment; it submits `paymentMethodId`. A recorded payment always displays its frozen `methodLabelSnapshot`, never the method's current name.

**Receipt / money summary** (M5) — bordered panel, right-aligned figures, clear label→value rows (Total collected / Center share / Teacher share), with counts (present / late / absent — three equal columns at every width) alongside. Implemented in `app/[locale]/(center)/sessions/[id]/session-receipt.tsx`; center/teacher share rows are hidden entirely — not just visually de-emphasized — for a role without `center.profit.view` (spec §7 acceptance criterion 9). **R2:** below the counts, a **Closed** row (time in the centre's timezone + who, or "automatically, end of day"), or for a session still open a muted "not closed yet — figures can still change" line; then, only when something changed, a **"Changes during session"** list — one muted tile per change: student, *from → to*, time · who, the optional reason, and a red **Payment voided** pill when the change voided one. No empty section is ever drawn.

**ID card** — landscape credit-card proportions (85.6 × 54 mm), dark gradient surface, center logo + name, student photo, name, grade, student code, QR block, and a brand-colored band along the bottom edge. Layout positions come from `CenterSettings.cardLayout`. The built-in starting layout lives in `lib/card-layout.ts` and is laid out so no two elements collide in either direction — the M3 gate asserts it. Rendered by `lib/id-card.ts` as a single self-contained SVG on a 320 × 202 unit face: `x`/`y`/`width` are percentages of that face and `fontSize` is in card units, so one layout is correct on screen and at print DPI. `x` is a **logical start** offset — an Arabic card mirrors the whole layout, per §7 — and a missing logo or photo falls back to an initial rather than a gap. **Text anchors are logical (DES):** every `<text>` carries `direction`, and SVG's `text-anchor` follows it, so start-aligned text is `start` and end-aligned text is `end` in both directions. The renderer had flipped the anchor *as well*, which anchored every Arabic text at its far end — the branch name ran off the card and the photo overprinted the grade, on screen, in print and in the stored file (docs/09 §2.0 pattern 4). LTR output is byte-for-byte unchanged; `check:card-layout`'s RTL goldens were re-taken once for this fix. A stored card generated before it should be regenerated from the student page. The preview (`components/center/id-card-preview.tsx`), the print view (`/students/[id]/card`) and the file stored in `id-cards/` are the same string. The paper printout (`/students/[id]/paper`) is the A4 companion: registration details, parent contacts, enrolments and the same card artwork. Both print views live in the `(print)` route group — the center role gate without the app shell — and their on-screen controls are `print:hidden`.

**App bar** — the header is a real bar, not a strip of text links: `content-shell`-aligned, 64px, sticky, translucent over the canvas. It carries, from the start edge, the mobile drawer trigger and the **branch switcher** (§11.1); from the end edge, the **language toggle** and the **user menu**. Implemented across `components/shell/app-shell.tsx`, `components/shell/branch-switcher.tsx`, `components/shell/user-menu.tsx` and `components/shared/locale-toggle.tsx`. The user menu exists because below `lg` the sidebar is a drawer, and *who am I signed in as* / *sign out* must not live behind a navigation drawer. The language control is the **language toggle** (next paragraph).

**Language toggle** (`components/shared/locale-toggle.tsx`, `LocaleToggle`, R10a) — the product's one and only locale switch, and its most recognisable control. A **circular button** (44px hit area around a 36px visual) showing the code of the language you would switch *to*: **`AR` while the UI is English, `EN` while it is Arabic** — it names the destination, so it reads the same in both directions. One click goes to the **same route in the other locale, query string included** (filters, pagination, `?next=` survive), through next-intl's `Link locale=` — the existing mechanism, with no second one. It reads `useSearchParams` inside a `Suspense` whose fallback is the same button without the query, so there is never a frame with no toggle. `aria-label` and `title` carry the full target name ("Switch to Arabic" / "التبديل إلى الإنجليزية"); it has the shared `focus-ring`, a brand-tinted hover and a 95% press scale, and the global reduced-motion rule stops the transition. It is rendered by `AppShell` (so every experience — centre, teacher, student, parent, platform admin), the auth layout and the 404, and nowhere else: `check:design` fails on a second locale-switching component, on `Link locale=` anywhere but here, and on any shell that does not render it. (It replaced a two-segment `LocaleSwitcher` whose links were `href={pathname}` and so dropped the query string. The class-period and new-session modes keep the segmented-track look; the language control no longer shares it.)

**Avatar** (`components/shared/brand-avatar.tsx`) — a centre's logo when one is set, otherwise its initial on the centre's own theme colour. The sidebar, the branch switcher and the centre-selection cards all render this one component, so a branch looks the same in all three. The initial comes from `lib/initials.ts`, and the rule is one sentence (**R10b**): **the first letter of the name as it is displayed, in whichever locale it is displayed in — no word is ever skipped.** `مركز النور` shows `م`, `Nour Academy` shows `N`, `The Nile School` shows `T`, `النور` shows `ا`. (R10a had kept a rule that skipped a leading generic word — `مركز`, "Academy", "The" — so the avatar disagreed with the label beside it on every centre named that way; it is gone, and `check:design` runs the function over Arabic and Latin names to prove it.) What the function still does, because `name.charAt(0)` once did not: it works in **code points** (an astral character is kept whole, not half a surrogate pair) and it skips *characters* that are not a letter or a digit — a leading quote, bracket or invisible bidi mark — which is not skipping a word. `nameInitial` is the rule; `centerInitial` is the same function under the name the centre screens use; `personInitials` is a two-letter monogram (first letter of each name, ignoring the `"-"` single-name placeholder). Never `name.charAt(0)`. The **person avatar** (`components/shared/person-avatar.tsx`, R10b) is the same idea for a student or teacher on a detail-page header: their photo when there is one (a short-lived signed URL), otherwise `nameInitial` on the neutral subtle surface, round.

**Select** (`components/ui/select.tsx`) — the product's one dropdown, built on Base UI's `Select`. It replaces the native `<select>`: the old control styled the *closed* box but handed the open list to the browser, so the most-used control in the ERP dropped out of the design system the moment anyone clicked it, and the option list ignored the app's direction in Arabic. This renders the list itself — 44px rows, brand-tinted selection, a check on the chosen item, keyboard and type-ahead support, correct RTL alignment — and still posts a real form value from `name`, so no form's payload changed. Accepts the list either as an `options` array or as plain `<option>` children. `submitOnChange` reproduces the filter bars' "re-query on change", fired from an effect so the hidden input is written before the form serialises.

**Checkbox & switch** (`components/ui/checkbox.tsx`, `components/ui/switch.tsx`) — replace `<input type="checkbox" className="accent-…">`, which tinted the OS control but left its size, radius, focus ring and disabled treatment to the browser. A **checkbox** is a value that will be true when you save (the permission matrix, which saves on Apply); a **switch** is a setting that is on *now* (`ToggleRow` on the configuration screens). The switch's thumb travels on a logical inset, so it slides toward the end edge in both directions.

**Date control** (`components/ui/calendar.tsx`, `components/ui/date-picker.tsx`) — the app's own month grid, replacing `<input type="date">` everywhere. The browser's calendar ignores the app's locale and direction, renders Latin digits inside an Arabic screen, and looks different in every browser the desk happens to run. This one formats its month heading, weekday initials and day numbers through `lib/format.ts` (so Arabic-Indic in `ar`), opens the week on Saturday in `ar` and Sunday in `en`, does all arithmetic in UTC to match every stored date, and supports single and range selection with the span highlighted between the two ends and previewed under the pointer. Full arrow-key navigation, with left/right reversed in a right-to-left grid. `DatePicker` is the single-date form control: same 44px height as `Input`, same `"YYYY-MM-DD"` value posted, an optional inline clear for a filter with an "any date" state.

**Every floating surface is portalled to `<body>`, without exception.** `Card` sets `overflow-hidden` for its rounded corners, and almost every filter, search box and form in the product sits inside a card — so an absolutely-positioned panel gets clipped at the card's edge. Select, DatePicker, DateFilter, Dialog, Popover and the type-ahead dropdown all portal out and position in viewport coordinates. A new dropdown that positions itself with `absolute` inside the page flow is a bug waiting for the first card it lands in.

**Popover** (`components/ui/popover.tsx`) — one floating-surface pattern for the branch switcher, the user menu and the date control, opening with the same `data-starting-style`/`data-ending-style` CSS transition the dialog established. Base UI's `align="start"`/`"end"` are logical, so a popover anchored to the start edge stays there in Arabic. **`components/shell/ui-direction.tsx` wraps the app in Base UI's `DirectionProvider`** — `<html dir>` alone is not enough, and without it every popover, select and dropdown anchored to the left in Arabic.

**Empty state** (`components/shared/empty-state.tsx`) — an icon in a tinted chip, a short title naming the absence, a line explaining what *would* appear here, and, where the screen has one, the action that creates the first item. It replaced thirty-odd single dimmed sentences floating in cards, which read as a screen that failed to load rather than a screen with nothing in it yet. `tone` carries meaning: `info` for "nothing here yet", `warning` for "nothing matched what you asked for" (something is filtered, and the action is *clear the filter*), `success` for a queue that is legitimately empty, `muted` for a secondary panel.

**Loading state** (`components/shared/skeleton.tsx`) — skeletons compose into the layout the real screen uses (`SkeletonPageHeader`, `SkeletonStatRow`, `SkeletonList`, `SkeletonPage`), never a single grey bar standing in for a page. Every route group has a `loading.tsx` built from these, so nothing shifts when the data lands. The pulse is plain CSS, stopped by the global reduced-motion rule.

**Error state** (`components/shared/error-state.tsx`) — what every `error.tsx` renders. Says what happened in the interface's voice, offers the retry React's boundary already gives us, and shows the raw message **only in development** (an ORM error string can name a table, a column, or an id from another tenant). Each route group has its own boundary so the shell — sidebar, branch context, language — stays usable while one screen has failed; `app/[locale]/not-found.tsx` and `app/[locale]/error.tsx` are the backstops outside any shell.

**Button & link button** — `Button` (`components/ui/button.tsx`) carries hover/active/focus-visible/disabled on its base class. A *link* that acts as a button is `LinkButton` / `AnchorButton` (`components/shared/link-button.tsx`), same variants and sizes, default size `touch` (44px). Twenty-five screens had hand-written this as a bare `<Link>` with a copied class string — each slightly different, none with a focus ring — so the most common navigation affordance in the ERP was the one control a keyboard user could not see.

**Request card** (`components/shared/request-card.tsx`) — one pending request in an approvals queue; see §11.3.

**Page header** (`components/shared/page-header.tsx`, `PageHeader`) — how every titled screen opens: a 24px / 700 title (`text-balance`), an optional one-line description under it, and the page's actions on the **end edge** from `sm`. Below `sm` the actions drop under the title and wrap, so two buttons never squeeze the title at 375px. Actions are passed as a node (a `LinkButton`, a dialog trigger, a badge) and laid out by the header — no page hand-rolls a flex row beside its title. Settings sub-pages get theirs from the settings layout (their own title is a `SectionHeader`); signed-out and print screens are exempt. `check:design` requires it on every other page. A header-level *link* is a `LinkButton` (`ghost` for "View all", `outline` for "Open"), never a bare `text-brand hover:underline`. **Detail pages (R10b)** use three more optional slots so the four of them open identically: `back` (`{ href, label }` — a ghost 44px arrow-and-label above the title, the arrow mirrored in Arabic; navigation is not a verb, so it never sits in the action bar), `leading` (an avatar or photo beside the title) and `meta` (the row of status badges and key facts under the description — active/inactive, One-time/Extra, the student code, the period, the rooms). The verbs go in `action` as one `ActionBar` with `inHeader` (§11.15): full width and two columns on a phone, directly under the title; packed to the end edge from `sm`.

**Detail page** (R10b; `components/shared/detail-layout.tsx`, `DetailLayout` + `DetailCard`) — how the class, session, teacher and student pages share one structure. A `PageHeader` (above) with the entity's name, its status badges in `meta` and **one action bar**; then a **main** column (two thirds from `lg`) and a **side** column (one third) of cards, **one column below `lg`** in the order *main, then side, then `below`* — so the work comes first on a phone and the reference cards follow. Put what a person came to the page to do in `main` (the record, the roster, the schedule, enrolments) and facts and secondary tools in `side` (key facts, the ID card, the rating, the block list, the receipt). Every card is a `DetailCard` — title, optional one-line description, optional `action` on the header's end edge, then the body — which wraps the shared `Card`, so padding, radius and border come from the tokens and no page draws its own. **No stranded half-empty column:** a card that is a long list of its own and would make `main` several times taller than `side` goes in `below` (a full-width row under both columns); a `main` that is long on purpose (a roster) pairs with `stickySide`, which keeps the side column in view beside it (and scrolls itself if it is ever taller than the viewport); and a card with nothing to say is an `EmptyState` (compact) or is not rendered. A form that lives in a card is divided into `FormGroup`s (`components/shared/field.tsx`) — a 14px heading and a hairline, not a boxed section, since a bordered `FormSection` inside a `Card` would be a card in a card. **A destructive control is never beside Save:** the student and teacher pages end with a **danger zone** (`components/center/delete-record-card.tsx`, `DeleteRecordCard`) — a full-width, `--danger`-bordered panel under both columns, rendered only to a role holding the delete permission, with the same two-step "Delete → this cannot be undone → Delete permanently / Cancel" confirmation and the same server action as before (which still refuses a record with history). The class page keeps Delete and Deactivate in its Edit class dialog (§11.13); the session page's destructive verbs (End session, Cancel, Delete) are red buttons in the header's action bar.

**Filter row** (`components/shared/filter-bar.tsx`, `FilterBar` + `FilterField`) — the one shape every list and report filters with: a plain GET form (state in the URL, §11.7), a row of **labelled** fields that wraps rather than scrolls, every control 44px and bottom-aligned, stacked full-width below `sm`. The label is visible (12px / 500) — it is what lets a select, a date control and a reset button share a baseline, since a label-less control beside a labelled one floats half a line off. `DateFilter` draws its own label ("Date range") above its trigger so it is a field like the others. A screen with three or four selects may lay the `FilterField`s out in a grid instead of a flex row; the *field* is the shared unit. Dropdowns are the shared `Select` (or `Combobox` for a long list) — never a native `<select>` (`check:design`).

**List header** (`components/shared/list-header.tsx`, `ListHeader`) — the column-header row of a list-style table: hidden and `aria-hidden` below `md` (each stacked card labels its own cells), a hairline-bordered 12px muted row from `md`. The columns' widths stay with the page, since they must match the row cells beneath. One implementation replaced nine copies of the same class string.

**KPI grid** (`components/shared/stat-grid.tsx`) — a KPI row's column count is chosen for the number of cards in it, not left at a fixed `sm:2 / xl:4`. **Every arrangement fills its rows at 375, 768 and 1280 (R10a):** where the column count does not divide the card count, the last card *spans the remainder* rather than leaving a hole — three cards are 1 / 2 (the third spans the row) / 3 across; five cards are 1 / 2+2+1 / 3-over-2 (a six-column track) / 5 across. Above six cards there is no arrangement that divides cleanly; that is the signal to split the row by meaning, which is what Analytics does (money in / what it left behind; students / teachers). A one-card row (a receptionist's "Collected today") stays full width.

**Alert note** — amber-tinted panel with icon for operational warnings (e.g. "absent 3 sessions in a row — consider contacting the guardian").

**Form fields (mandatory, M3).** Two rules apply to every text input in the product, retroactively:
1. **A field that is genuinely, unconditionally optional gets a dimmed "(optional)"** beside its label (`Shared.optional` in `messages/*.json`) — never leave staff to guess or hit a validation error to find out. Don't apply it to a field that is only *conditionally* required (e.g. "phone or email, at least one") — a hint sentence explains that correctly where a flat "(optional)" tag would lie. `components/shared/field.tsx`'s `Field` takes an `optional` prop that renders this consistently; `components/settings/entity-fields.tsx` derives it automatically from `required`/`emptyLabel` for the five master-data screens.
2. **Every text input gets a dimmed placeholder showing the expected format** — a phone field shows `01012345678`, an email field shows `name@example.com`, a name field shows an example name prefixed "e.g." (DES, §3 — a bare name read as a filled-in value). Placeholders are translated strings (never hardcoded, CLAUDE.md rule 5) so they read naturally in both locales; keep them as literal, plausible examples, not instructions like "enter your phone."

## 6. Responsive rules (mandatory)

Every screen must work on a phone. Breakpoints: `sm 640` / `md 768` / `lg 1024` / `xl 1280`.

- **Mobile-first**: build the small layout, then enhance upward.
- Sidebar → hamburger drawer below `lg`.
- Multi-column grids → single column below `md`.
- Tables → stacked cards below `md` (label/value pairs), never a horizontal scroll for primary data.
- KPI rows → 2-up on `sm`, 1-up on very small screens, and the wide arrangement chosen for the card count (`StatGrid`, §5) — never a fixed four-wide grid that leaves an orphan row.
- Touch targets **min 44×44px**; reception/attendance controls larger still.
- Modals → full-screen sheets on mobile.
- Test at **375px** width as the floor, and at **2560px** as the ceiling: content is centred and capped at `--content-max` by the `content-shell` utility (§4), applied by the app shell only.

---

## 7. RTL rules

- Logical properties only: `ps-*/pe-*`, `ms-*/me-*`, `text-start/end`, `start-*/end-*`. **Never** `left/right`, `pl/pr`, `ml/mr`.
- Icons that imply direction (arrows, chevrons, back) must mirror in RTL; icons that don't (calendar, user, money) must not.
- Charts: axis and legend placement follow reading direction; numeric axes stay conventional.
- Every screen is reviewed in **both** `ar` and `en` before it's considered done.

## 9. Class Schedule Builder (M4 reference, revised)

**Weekly Time Slots list:** one row per slot — day dropdown, start/end time pickers, remove (×) icon at the row end. **Add slot:** a `+ Add time slot` text-button below the last row, full-width tap target on mobile.

**After a save (R4):** adding, moving or removing a slot resyncs the class's upcoming sessions, and `SessionSyncNotice` sits under the row — a green line ("12 sessions created · 11 upcoming sessions removed") and, when any were kept, an amber one ("3 upcoming sessions were kept because they already have records or custom changes"). See §11.13.

**Mobile (< md):** slot rows stack into single cards (day/time/room as label→value pairs, matching the existing table→card responsive rule in §6) rather than a row grid. Remove control and Add button stay 44px+.

## 11. New and changed surfaces (M11–M19)

Every pattern here inherits §2's tokens, §6's responsive rules and §7's RTL rules without exception. What follows is only what is *specific* to each surface — where a rule is not restated, the general one applies unchanged.

### 11.1 Branch switcher (M11)

Lives in the header, beside the centre logo, **not** in the sidebar — it changes the scope of everything below it, so it must stay visible when the sidebar collapses to a rail or a drawer (§5).

- A single control: the active branch name plus a chevron. Opens a list of the branches this user resolves to (`02-architecture.md` §4), with **"Whole Management"** pinned at the top when the user holds more than one.
- **Hidden entirely for a single-branch user.** No disabled control, no dropdown with one item — the same reasoning `/select-center` already follows for a single-centre user.
- **"Whole Management" must look different from a branch, not merely be first.** It is a scope, not a place: give it an icon and a divider below it, so nobody reads it as another branch name.
- **Roll-up is analytics-only** (`00-master-product-spec.md` §4.1). When "Whole Management" is active, operational nav items (Reception, Sessions, Approvals) are **disabled with a one-line reason** — "pick a branch to use the desk" — never silently missing. A nav item that vanishes reads as a permission problem.
- Mobile: the switcher moves into the drawer header, full-width, 44px minimum.

**Delivered** as `components/shell/branch-switcher.tsx`, in the app bar (§5). It replaced a plain "Switch branch" text link that showed no branch context at all — the one thing a switcher exists to show. The trigger *is* the context (the branch's mark plus its name); the panel is the list, with "Whole Management" pinned above a divider under a `Layers` icon so it cannot be read as one more branch name, and a check on whatever is currently in scope. Each row submits the same `selectCenterAction` the `/select-center` hub uses — the switch itself is unchanged, only where it can be reached from. Hidden entirely below two branches, per the rule above. Below `sm` the trigger collapses to the mark and chevron alone; the branch name is in the panel.

### 11.2 Permissions matrix screen (M12)

The densest screen in the product, and the one most likely to become an unreadable grid.

- **Roles as columns, actions as rows**, grouped by area (People / Classes / Money / Settings / Approvals) with sticky group headers. The role header row is sticky too — a matrix you have to scroll blind is a matrix that gets misconfigured.
- A cell is a checkbox with three visual states: **granted**, **denied**, and **not grantable** (the platform ceiling, `02-architecture.md` §6.1). Not-grantable renders as a dimmed dash with a `title` explaining why — **never an unchecked box**, which would imply an Owner could tick it.
- **OWNER-only screen.** Anyone else does not see the nav item and is redirected at the loader.
- **Below `md` the grid becomes one card per action**, listing the roles as label→value toggle rows — the standard table→card rule (§6), applied to a matrix. Do **not** horizontally scroll it; this is primary data.
- Changes save explicitly (an Apply button with a dirty-state count), never per-cell-on-click: a permission grid that writes on every tick is a grid where a mis-click is a silent privilege change.

**Delivered, with one part of this section still outstanding.** The header row and the action column are both sticky (`app/[locale]/(center)/settings/permissions/permissions-form.tsx`), inside an explicit max-height scroll box — sticky needs a scroll container, and `overflow-x: auto` alone had made the page's own scrolling the wrong one to stick against. Cells are the shared `Checkbox` (§5); not-grantable still renders as a dimmed dash, never an unchecked box. **DES:** the grid keeps **one controlled state** shown by both layouts and posts each granted cell exactly once — the two uncontrolled copies had silently dropped every revoke (docs/09 §3a F6). The Save button now carries the change count ("Save 3 changes", disabled at zero) and sticks to the foot of the page; the not-grantable cell is a plain dash with its reason as a tooltip and screen-reader text; the note explaining it sits above the grid; each checkbox's name says action *and* role. **Grouping the rows by area with sticky group headers has not shipped** — that is a content decision (which action belongs to People vs Money) rather than a presentation one, and it is the remaining gap against this section.

### 11.3 Teacher approvals (M15)

Same card queue as the centre `/approvals` screen — deliberately, since a teacher and a manager are reading the same kind of request and should not have to learn two layouts.

- One card per pending student: avatar + local name, class, requested-at, and the two actions.
- **A refusal states its reason in the card, not in a toast.** "Blocked from this class", "class is full — move it to a bigger room or combine another room with it" (R3: the cap is the room set's), "rejected 3 days ago, can re-request in 4 days" (§11.7's copy rule). A toast disappears; the reason needs to stay next to the thing it explains.
- Empty state is a real state, not a blank panel — most teachers have an empty queue most days.

**Delivered as `components/shared/request-card.tsx`, shared by `/approvals` and `/teacher/approvals`.** The centre queue carries four genuinely different asks — a teacher proposing a **new class**, a teacher asking for a one-off **session**, a student requesting a **place**, and a teacher asking to work at this branch at all (**onboarding**) — and all four used to render as the same anonymous bordered box, so a manager could not tell what kind of decision they were about to make until they read the body text.

- **The kind is the first thing the card says**: a distinct icon, a named badge, and a detail grid holding the fields that kind actually turns on (day/time/attendance/late-threshold — no capacity since R3 — for a class; date/time for a session; price for a reservation).
- `kind` is a *category, not a status*, so it takes no semantic colour (§2 reserves those). The icon and the label carry it; the badge stays neutral.
- **Onboarding is derived, not stored**: a `NEW_CLASS` request from a requester with no local `Membership` is a teacher asking to work here, which is the same database row but a different decision. It gets its own kind and an info note saying so — approving is a decision about the class, not about hiring.
- Requester, requested-on, note and the two actions are identical across kinds on purpose: those parts of the decision genuinely are the same and should not have to be re-learned per queue.
- Below `lg` the actions move under the card, full-width; from `lg` they pin to the card's end edge. **The two actions are an equal-width pair** (a two-column grid of `w-full` buttons, 256px wide from `lg`) on all four queues, so a long "Decline" is never a different size from "Approve" (R10a).
- **The empty queue** (`success` tone) names the absence, says what would land here, and links to Teachers — where class and session requests originate.

### 11.4 Parent portal (M16)

Visually the **student portal**, with exactly one addition and one subtraction.

- **Addition: the child selector**, in the header where the branch switcher sits for staff. Avatar + name per child; if a parent has one child, **the selector is hidden** and the child's name appears as plain header context.
- **Subtraction: every write control.** No enrol button, no cancel, no rating prompt. Do not render them disabled — remove them. A disabled control tells a parent the feature exists for them and is broken.
- Where a child attends more than one centre, the per-centre grouping the student portal already uses carries over unchanged.

### 11.5 Rating pop-up (M17)

A modal on login (full-screen sheet below `sm`, per §6), and the interaction most at risk of being annoying.

- One row per session from the **last 7 days**: subject + teacher + date, and a 5-star control with 44px targets. **Delivered as real stars** (`app/[locale]/(student)/rating-popup.tsx`), not numbered buttons: the run up to the pointer fills as a preview, so the score is legible before it is committed, and each star is still a single submit — a click is the whole interaction, with no separate confirm step.
- **Skip is a first-class action, not a dismissal.** A visible "Skip" button of equal weight to "Submit", plus the standard close affordance. It must never be re-shown in the same session after a skip.
- **Partial submission is allowed** — rate two of five, submit, done. Never gate submit on completeness.
- **Never show a count anywhere** — not in the prompt, not in the confirmation. Where an aggregate appears (the Discover class card, §10, and the teacher's own view), it is `4.6 ★` and nothing else. No "(23 ratings)", no distribution bar: a count is what lets a teacher infer who rated them from a small sample.

### 11.6 ID-card layout editor (delivered M18)

Replaces the raw `cardLayout` JSON textarea. **A centre never sees JSON** — that is the whole point of the change.

- **Direct manipulation on a live card preview** at true proportions (85.6 × 54 mm, matching §5's ID card): drag to move, handles to resize, an element **palette** to add from, an **×** to remove.
- Selection shows a small properties strip (font size, alignment) — not a separate panel that hides the card.
- **Snap and bounds:** elements snap to a light grid and cannot be dragged off the face. The M3 gate already asserts the default layout has no collisions; the editor should make a colliding layout hard to produce rather than merely detectable.
- **`x` stays a logical start offset** (§5, `02-architecture.md` §10) — an Arabic card mirrors the whole layout, so the editor previews in the **active locale** and says so.
- Below `md`, editing is a stacked list of elements with numeric position controls rather than a drag surface. Dragging a 320-unit card on a 375px screen is not editing.

**Delivered, with two corrections to this section's own draft assumptions.** `app/[locale]/(center)/settings/card/card-form.tsx` — drag-to-move is real pointer-based dragging on the preview, snapped to a 2% grid, clamped 0–100%, using logical `insetInlineStart`/`top` so the RTL mirror needs no special-case code. **"Resize" is the properties strip's numeric field, not a drag handle** — `lib/id-card.ts`'s `CardElement` has no `width` on four of the seven elements (`centerName`/`studentName`/`grade`/`studentCode`), only `fontSize`, so a corner-handle would have nothing to resize on most elements; one shared numeric control (width for the three image elements, font size for the rest) covers all seven the same way. **"Alignment" was not a control at M18** — nothing in `CardElement` stored one, and the text anchor was always derived from `dir`. **R9 adds it** (logical Start / Center / End inside an optional text box — see below). The palette/× map onto a real, new distinction in `resolveCardLayout`: a JSON `null` for an element key means "removed" (never rendered), separate from "absent" (still means "use the built-in default") — previously there was no way to express "removed" at all.

**R9 — what changed, and the rules it set.**

- **Drag from anywhere on an element.** The editor draws the card with the real renderer and lays an invisible target over each element's measured bounds, so a logo or a photo is grabbed by its picture and a text by its glyphs — not by a label chip. A press that travels less than **4px** is a click (it selects); past that it is a drag (it moves). Dragging uses pointer capture, snaps to the 2% grid, clamps to the face and mirrors for Arabic with no special case. A focused element also moves with the arrow keys (Shift = 5%).
- **Selection is stable.** Clicking an element selects it and opens its **properties strip**; the strip stays open until the user presses **empty card space**, presses **another element**, or hits **Escape**. Releasing a drag, clicking, blurring and hovering never close it. *(Root cause of the old flash: the card cleared the selection from its `onClick`, and after a drag the browser delivered the click to the card, not the element that had moved away.)* Rule for any future canvas editor: **never derive selection from click, blur or hover — set it on pointer-down, clear it on an explicit gesture.**
- **Properties strip (md and up)** for the selected element: *size* (width for images, font size for text), then for the four **text** elements — **text box width**, **Weight** (Normal / Bold), **Alignment** (Start / Center / End, logical — Start is the right edge on an Arabic card), **Font** (a closed list: the card font, a system sans, a system serif), **Text color**, and on the branch name a **Custom branch text** field (blank = the real name, shown as the placeholder, max 60). Remove lives in the strip's header.
- **Card colors** is its own card: **Background**, an optional **Header band** (a toggle, with its own colour) and the **Bottom line**. Every color control is the same component — the native picker, swatches (**the first swatch is the theme colour**), the hex readout (`dir="ltr"`) and a reset that *removes the key* (back to the theme colour, or the default background) rather than writing a copy. Swatches are 44×44 targets around a 24px dot. Uploaded logos are never recoloured.
- **Contrast warning, never a gate.** A text whose colour is below WCAG AA (4.5:1; 3:1 at ≥24 units or ≥18.66 bold) on what it sits on — the header band if the text is inside it, otherwise the background (the worse gradient stop) — is listed in a **warning** `FormMessage` under the preview. Saving is never blocked.
- **One render path.** The preview is `renderIdCardSvg()`, the same function print and the stored file use; the editor passes `annotate` only to get measurable wrapper groups. There is no second renderer to keep in sync.
- **Below `md`** the live preview still shows (it is the only way to see a colour change on a phone), but there is no drag surface: each element is a collapsible row (`<details>`, a 44px summary) holding the same controls as the strip plus numeric position. Drag stays desktop-only.
- **Server validation errors are shown** — a layout the schema refuses (`invalidCardLayout`) now surfaces as a message instead of failing silently.

### 11.7 Date filter (delivered M18) — one component, everywhere

Replaces every ad-hoc date filter in the product. Analytics, Expenses, Sessions and every later screen use **this** and nothing else.

- A segmented button row: **Day** · **Week** (today −7) · **Month** (1st → today), plus a **specific-date** picker and a **range** picker, an **Apply**, and a **reset to today's default**. *"Today" here is the centre's calendar day (`CenterSettings.timezone`, R7b), passed to the control as `todayIso` by the server — never the browser's or UTC's.*
- **Buttons apply immediately; the pickers wait for Apply.** A range that re-queries on the first of the two dates is a range that queries a nonsense window.
- The active selection is always readable as text next to the control ("1–6 Sep") — a highlighted segment alone is not enough once a specific date or range is in play.
- **State lives in the URL** (`02-architecture.md` §14), like pagination, so a filtered view is shareable and back-button-safe.
- Below `md` the segments stay a row (they are short) and the two pickers stack.

**Delivered** as `components/shared/date-filter.tsx`, on Analytics, Expenses and Sessions.

**Revised presentation: one control, not five.** The first delivery put a segmented row, two separate picker toggles, two native `<input type="date">` fields and a stray Reset link on four different baselines — three date affordances for one job, two of them drawn by the browser. It is now a **single trigger** reading the active selection ("Range: 1–6 Sep"), opening **one panel** that holds the presets beside one range calendar: pick a start, pick an end, the span highlights between them and previews under the pointer, and **a start with no end *is* the specific-date case**. One Apply, in the panel's footer, disabled until there is something to apply. Reset is an icon button beside the trigger, on the same baseline. **R10a:** the control draws its own visible label ("Date range") above the trigger and sits in a `FilterBar` (§5 "Filter row") beside the page's other `FilterField`s, so on Analytics the date control and the teacher select share one baseline instead of each carrying a different label treatment. The presets still apply on click; the calendar still waits for Apply.

**The URL contract is unchanged** — `range` / `date` / `from` / `to`, same schema, same parser — so a bookmarked filtered view resolves exactly as it did. Every visible control writes to the same four hidden inputs and nothing else, so there is exactly one `range` value in the query; Apply fires from an effect, after those inputs are written, and submits the page's real form so the screen's other filters ride along untouched.

**Single-date filters use the same calendar, not the same component**: `/student/schedule`, `/parent` and `/teacher/sessions` filter by one `?date=`, so they render `DatePicker` (§5) — the same month grid, the same locale and direction, an inline clear for the "any date" state. The teacher session list keeps its own forward-looking day/week/month for the reason recorded below. **One deliberate exception, not an oversight**: the teacher's own session list (`/teacher/sessions`) keeps its own bespoke day/week/month filter rather than adopting this component, because its "week"/"month" are forward-looking (today → today+6/+29, "what's coming up," spec §4.2 item 2) while this component's are backward-looking by definition (today−7 → today, 1st-of-month → today) — the two are answering different questions, and unifying them would have silently turned an upcoming-sessions view into a recent-sessions one.

### 11.8 Live search dropdown (delivered M18)

Every search input in the product becomes a type-ahead. This is the most-used interaction in the app after attendance, so the details matter more than usual.

- Results appear in a panel below the input: avatar + local name + the matched field (code / phone), **highlighting the matched substring**.
- **Minimum query length before anything fires**, debounced, and bounded to a small result count (`02-architecture.md` §14). A dropdown that loads every student to filter in the browser is the loader that section warns about, in nicer clothes.
- Three states are all real and all need a design: **loading** (a subtle inline spinner in the input, never a layout shift), **no results** (with the "add new" action inline, since at Reception that is the likely next step), and **too short** (silent — no panel at all).
- **Full keyboard support**: ↑/↓ to move, Enter to select, Escape to close. Reception uses a hardware barcode scanner, which types fast and presses Enter — the dropdown must not swallow or reorder that. **Scanner contract (R7):** a submit reads the input element's own value, cancels the pending debounce and any in-flight search, and Enter selects a suggestion **only after an arrow-key highlight** — hovering a row never arms Enter and typing clears the highlight, so a scan can never select a stale suggestion under a resting mouse.
- **The QR/scan path bypasses the dropdown entirely**: a scanned `KAYEDU|…` payload resolves straight to the selected-student panel (`lib/id-card.ts`'s `parseScannedStudentInput` — the one tolerant reader), and that panel **must show the student's photo** — it is the anti-impersonation control the static-QR decision rests on (`00-master-product-spec.md` §5.1), delivered in the same milestone (§7.1).
- Below `md`, the dropdown becomes a full-width sheet under the input, not a floating panel.

**Delivered as `components/center/type-ahead-search.tsx`: 300ms debounce, a 2-character minimum, 8 results.** Loading/no-results/too-short are all real, distinct states exactly as specified. Two details landed narrower than this section's draft: rows show **name + the matched field as plain text**, not an avatar and not a highlighted substring — no avatar image exists to show for most of these lists (teachers/students have no thumbnail beyond the ID-card photo, which reception's own selected-student panel already covers separately, §7.1), and substring-highlighting was left for a follow-up pass rather than blocking the rest of the sweep on it. The "add new" inline action in the empty state is supported by the component (an `emptyAction` slot) but not yet wired into any screen — none of the nine screens converted pass one today. Below `md` the dropdown is a `w-full` panel directly under the input; on Reception and the other single-column mobile layouts this already reads as the full-width sheet the spec calls for, so no separate mobile variant was needed.

**Fixed after the presentation pass: the panel was being clipped.** It positioned itself with `absolute` inside the form, and the form sits inside a `Card`, whose `overflow-hidden` cut the list off a few pixels below the input — on Reception, Students, Teachers, Classes, the session and class detail pages, and both teacher lists. It now renders through `createPortal` into `<body>` as a `fixed` panel measured against the input's own bounding rect, so no ancestor's `overflow` can clip it and no ancestor's `transform` can re-anchor it. `left`/`width` come from the measured rect, which is correct in both reading directions with no special case. It follows scroll (capture-phase, so nested scroll containers count) and resize, flips above the input only when there is genuinely more room there, and the outside-click handler checks the portalled panel as well as the form — otherwise every click on a result would have read as a click outside.

### 11.9 Settlements & refunds (M14)

- **Settlement status** uses the existing semantic set (§2) and adds no new colours: `DRAFT` = neutral/muted, `APPROVED` = info blue, `PAID` = success green. There is **no partially-paid state** and therefore no amber — do not invent one.
- **A refund is shown alongside its original payment, never in place of it.** The original row stays legible with a `REFUNDED` badge (danger tint, matching Void's treatment) and the refund appears as a linked child row. Replacing the original would misrepresent an append-only ledger as an editable one.
- **Void and refund must never look the same.** They are different events with different analytics effects (`00-master-product-spec.md` §5); give the badges distinct labels and keep both visible.
- Money figures stay uncoloured (§2) — the badge carries the meaning, not the number.

### 11.10 Out-of-window empty state (M19)

When a read is refused because it falls outside the data-visibility window, the screen shows a **named** empty state, not a blank chart or a zero.

- Copy pattern: *"Data older than 30 days isn't shown at this centre."* Plus, for a role that can change it, a link to `/settings/visibility`.
- **A zero is the wrong answer here** — a chart rendering 0 EGP for last quarter reads as "we earned nothing", not "you can't see this", and that is a genuinely dangerous ambiguity on a money screen.
- Uses the **Alert note** pattern (§5), info-tinted rather than amber: nothing is wrong, something is simply out of view.

## 13. What each screen owes this system

Every route in the product has, without exception:

1. A **designed empty state** for each region that can be empty — icon, title, one line of explanation, and the creating action where one exists (§5).
2. A **loading state** that matches the real layout's shape (`loading.tsx` per route group, §5).
3. An **error state** inside its own shell (`error.tsx` per route group), plus `not-found.tsx` and a locale-level backstop.
4. **Four states on every interactive element** — hover, active, focus-visible, disabled (§4).
5. **No raw browser-default control**: no unstyled `<select>`, no native `<input type="date">` chrome, no `accent-color` checkbox. The design-system components in §5 cover all three.
6. **Both locales and four widths** verified: 375px, tablet, laptop, and a wide monitor capped by `content-shell`.

A screen that does not is not finished, and this list is the checklist to run against it.

## 14. The professional pass (DES)

The review behind every change here is `docs/09-design-review.md` (screenshots of every route at 375 / 768 / 1280 / 1920 in both locales). Tokens are in §2–§4 above; this section is the component and pattern side. Where it differs from an earlier section, **this section wins** and the earlier one says so.

### 14.1 Foundations

- **Button sizes.** `default` is **44px** (`h-11 px-4 gap-2`) — it had been 32px, below the touch rule, and 47 call sites leaned on it. `sm` is 36px, for a secondary verb inside a dense desktop row only, never the only control on a phone. `icon` is 44px, `icon-sm` 36px. `LinkButton`/`AnchorButton` default `touch` is the same 44px; an empty state's "Clear filters" is `touch`, not `sm`.
- **Destructive button** text is `--danger-fg` on the 10% danger tint (it was `--danger` on the tint, 4.0 : 1).
- **Fields** (`Input`, `Textarea`, the `Select` and `Combobox` triggers, `DatePicker`, `TimePicker`) sit on **white** (`--bg-surface`) with a `--border-control` edge that darkens to `--border-control-hover` under the pointer; placeholder `--text-placeholder`. They had been filled with the grey canvas colour, which on a white card reads as disabled. Read-only fields are `bg-surface-subtle` with `--text-secondary` text, so an invitation's fixed email no longer looks editable. Every field takes its hint and error ids through `aria-describedby` (`Field` wires it), and an email/code field turns off spell-check and auto-capitalisation.
- **Card** — a 1px `--border` edge (it had been a 10% `ring` of the text colour, a second border recipe), `shadow-card`, 12px radius, padding 16 / 20 (§4). `CardTitle` 16 / 600 as a heading (§3). A card inside a card is not allowed: a panel inside a card is a `bg-surface-subtle` inset with no border, or a hairline-separated group (`FormGroup`).
- **Status badge** — a pill (`rounded-full`), 12px / 500, `px-2.5`, the tint plus the `-fg` text (§2). `dot` draws a 6px status dot before the label — the "Live" badge pulses it (reduced motion: a steady dot). A **role** or a **kind** is never a status: it uses the `neutral` badge (the select-centre role badges had used `brand`, which on the default blue read as "Upcoming").
- **Empty state** draws **no dashed box** of its own: almost every one sits inside a card, which is already the frame, and the dashed outline inside a bordered card was a card in a card. `compact` (a secondary panel inside a card) sits on a quiet `bg-surface-subtle` inset instead. Icon chip, title (14px / 600), one line of explanation, the action — unchanged.
- **Skeletons** are drawn with the same `Card` recipe (border, radius, padding) as the content they stand in for, so nothing shifts when the data lands.
- **Detail-page headers put the action bar beside the title only from `lg`** (below it, the bar sits under the title as on a phone). From `sm` a four-verb bar had left the session title a 130px column at 768 — three lines, with every meta badge stacked. A list page's single header action still sits beside the title from `sm`.
- **`PageSection`** (`components/shared/page-section.tsx`) — a `SectionHeader` and its content at 12px, sections 24px apart. Dashboard and Analytics compose with it.

### 14.1a Dialogs and sheets

- **A 16px gutter until the max width takes over.** From `sm` the popup is `calc(100% − 2rem)` wide, capped by its `max-w-*` and still centred by symmetric insets and auto margins (never a logical inset with a physical translate — SYS). Between 640 and ~930px the wide shell had run edge to edge.
- **A confirmation is a bottom sheet on a phone**, not a full screen holding two lines. `DialogShell size="narrow"` below `sm`: anchored to the bottom, full width, rounded top corners, at most 85% of the viewport, the footer's buttons stacked. A **form** dialog stays the full-screen sheet of §6. Both pad their footer by the device's safe area.
- **No empty body band.** A shell whose body has nothing in it draws no body (the title and description already say it all).
- **The committing destructive action is solid.** In a confirmation the destructive primary is `danger-solid` (`--danger` fill, white text, 4.83 : 1) so it outweighs "Keep it"; the soft destructive tint stays for the verb that *opens* the confirmation (action bars, rows).
- **A form dialog is not dismissed by a stray click.** A dialog with a form ignores a press on the backdrop (`disablePointerDismissal`); Escape, Cancel and the close button still close it. A half-typed New class is ~15 fields and a schedule.
- **Motion** is opacity + scale only (it had been `transition-all`, which animated the insets on a resize).

### 14.2 Toasts — every mutation answers

- **One toast layer**, on Base UI's `Toast` (already a dependency — no new library), mounted once per shell by `Toaster` (`components/ui/toast.tsx`). A toast is **bottom-centre on a phone** (full width less 16px) and at the **bottom end corner from `sm`** (a logical inset, so it is on the left in Arabic). 360px wide, 12px radius, `shadow-popover`, an icon and one line of text plus an optional second line, and a close button with a translated label. **Success** (green icon, ~4s), **info** (~5s), **error** (red icon, stays until dismissed — an error that disappears before it is read is the "silence" this pass removes). Hovering or focusing pauses the timer. The region is an `aria-live` polite region (errors assertive). No stacking animation beyond a 160ms fade and a short rise; none under reduced motion.
- **When to toast vs. say it inline.** A **success** that leaves the form or row in place, or closes a dialog, toasts ("Student registered", "Settings saved"). An **error that belongs to a field** goes under the field; an **error about the whole submission** goes in the `FormMessage` at the top of the form or dialog body — the form stays open with everything typed. A **refusal that explains a decision** (a blocked student, a full class, an approval that cannot go through) stays **in the card it is about** (§11.3) and is not also toasted. A **network failure** (the action never answered) is an error toast with **Retry**, which re-submits the same `FormData`.
- **One answer, once.** A success already said inline where the person acted (General settings' save bar, the invitation link panel, a dialog that turns into its result) does not also toast.
- **Wiring.** `useActionFeedback(state, { success, error })` (`lib/ui/action-feedback.ts`) toasts a translated success once per result, and — for a control with nowhere inline to say it (an icon-only remove, a confirm dialog that has closed) — a translated error. Every Server Action form state comes from `useGuardedActionState` (same signature as React's `useActionState`): a request that never reaches the server becomes the error toast with **Retry**, and the form keeps what was typed. Plain `useActionState` is not used in `app/` or `components/`. Success messages live in the `Toasts` namespace and name the act in its own words ("Expense voided", "Access to {branch} removed").
- **Every Server Action returns a result.** An action that returned `void` reported a refusal exactly like a success (the page re-rendered either way). Each now returns `ActionState` — the same rules in the same order, each early return naming the rule that refused it (`Settings.errors`). Applied to revoking an invitation and granting or removing branch access, the three that were silent.
- **Client validation is the server's schema.** A form whose action parses `schema.safeParse(Object.fromEntries(formData))` runs that **same** schema on submit (`useClientValidation`, `lib/ui/client-validation.ts`) and shows the same message keys under the same fields, then focuses the first invalid one. It refuses locally only when every failing key is a visible control the person can fix; anything else goes to the server, which stays authoritative — the client must never be what silently blocks a submit. Applied to the student, teacher, expense and General-settings forms.
- **Error summary.** A multi-section form with two or more field errors opens with `ErrorSummary` — "N fields need attention" and a button to the first. One error is clear enough beside its field.
- **Required and optional** follow §5 "Form fields": a field that is genuinely always optional says "(optional)" beside its label (`Field optional`); a required field has no marker, since most fields here are required.
- **Copying a link** (`CopyLinkField`) says when the browser refuses the copy and selects the link instead — it had failed silently.
- **Gates.** `check:design` requires every form-state consumer to report its result (`useActionFeedback`, or a rendered `state.error` / `state.status`), refuses `useActionState` outside `lib/ui/`, refuses a Server Action declared `Promise<void>` outside the auth redirect actions, refuses an empty or comment-only `catch` outside an allowlist with reasons, and requires `error.tsx` and `not-found.tsx` in every route group.

### 14.3 The shell

- **Skip link** — "Skip to content", the first focusable element of every shell, visible on focus, targeting `<main id="main">`.
- **The drawer is `inert` while closed** (it had only been `aria-hidden` and moved off-screen, so its links stayed in the tab order on every phone page). Opening it moves focus to its close button; closing it returns focus to the menu button. **While it is open everything behind it is `inert`** (the skip link and the whole content column) and it is a modal `dialog` — Tab had walked out of an open drawer into the page under the overlay (16 of 30 presses, Phase 4). Widening the window past `lg` closes it, so the content can never be left inert. Its nav scrolls on its own (`overscroll-contain`) and the footer is one row.
- **Collapse toggle** moved from beside **Sign out** (one slip signed a receptionist out) to the **app bar's start edge** — the same spot that opens the drawer below `lg` collapses the rail from `lg` — with an `aria-label` that names what it will do (on the brand row it would have cut the branch name). The collapsed rail's sign-out carries its own `aria-label`.
- **Active nav item** is the solid brand pill only — the white start-edge tab drawn *on* the pill read as a rendering glitch.
- **App bar** — its horizontal padding sits outside `content-shell`, like `main`'s, so the language and account controls end exactly at the content's edge at 1920. The **account button** matches the language toggle (36px visual, 44px hit area, a bordered white circle) — it had been a grey disc that read as disabled.
- **Sign out on a light page** (the branch hub, the invitation) is the light `SignOutButton` variant — a ghost button in the card's footer — never the navy sidebar slab, which had been the heaviest thing on those screens.

### 14.4 Dashboards and analytics

- **The KPI card (`StatCard`).** The label row has a fixed height, so a card with an icon and one without put their figures on the same line. A figure never wraps (`whitespace-nowrap`) and steps down a size when it is long (over 12 characters — a five-figure amount with decimals), so a negative Net no longer drops its minus sign onto its own line. A zero is drawn in `--text-secondary`, not the muted colour: an Arabic zero is a single dot (`٠`), and dimmed it disappeared. `compact` (12px padding, 24px figure) is for a row of short counts.
- **Negative money carries a real minus.** `formatMoney` uses `signDisplay: "negative"` — the locale's own minus sign, on the correct side in Arabic — and a refund's "−" is never glued on by hand. `formatMoney(…, { fixed: true })` always shows two decimals, for columns.
- **KPI grid (`StatGrid`).** `dense` is for short counts: two up from the smallest phone (a lone "3" no longer takes a 110px full-width card), three or four across from `sm` / `xl`. Money rows keep the original arrangement. The rule that every row fills at 375 / 768 / 1280 still holds.
- **The centre dashboard's order is the order of attention.** The title is the screen ("Dashboard"), the description is the branch and today's date, and the role badge is header meta, not an action. Then **Today**: the money (Collected, and the branch share for a role that may see profit) first, then the session counts as one dense row. Then **Today's sessions** as rows on one column grid shared by every row (time · session · teacher · checked-in · status), the count labelled ("6 / 8 checked in"), and on a phone time and status on one line above the name. Then **Branch** — staff, teachers, students — as one compact strip, not three big cards. A row links to the session only for a role that can open it; otherwise it is plain text (the accountant's dashboard linked every row to a page that refused them).
- **Analytics** shows the resolved period in words under the Revenue heading ("1 – 15 Oct 2026"); with a teacher selected, Expenses and Net say they are branch-wide; the Net card's icon follows its sign. The by-teacher and by-branch tables end-align every figure, show two decimals and never truncate money; below `md` each teacher (or branch) is one bordered card with its name as the title and its figures as a two-column definition list. (No totals row: the KPI cards directly above are the totals, read from the same frozen snapshots.)
- **Platform admin.** The adoption list draws a proportional bar per month (brand at 25% on a subtle track), and the month is formatted by `lib/format.ts` — it had printed a Latin year beside an Arabic month.
- **A time never breaks inside itself.** `formatTime` / `formatTimeRange` join with no-break spaces, so "12:10 PM" cannot wrap to "12:10 / PM" in a narrow cell; date ranges stay breakable.

### 14.5 Reception desk — speed and the scan first

Where this differs from §11.17, this wins; §11.17's behaviour (scanner contract, session-first and student-first flows, the confirm panel, the receipt dialog) is unchanged.

- **The find / scan field is the one bold thing on the desk.** A 56px field with a scan icon at its start, focused on arrival and after every action, the label kept for assistive technology but visually hidden (the card title already says "Find a student"), capped at a readable width (`max-w-3xl`) on a wide monitor. In session mode it carries a brand edge and a "Ready to scan" line beneath it, so a receptionist can see at a glance that the next scan goes into the session.
- **Session mode is unmistakable.** The sticky banner is a brand-tinted surface with a brand start edge (`border-s-4`), "Attending" over the session name at 16px / 600, the teacher and time beneath, a Live badge and the running checked-in count; Change session (a real `AnchorButton`) and Exit beside it, stacked under it below `md`. - **One primary per card, and only where it matters.** "Start attending" is solid only on a **Live** card; on an upcoming card it is outline. An upcoming card no longer shows a disabled End session and its hint — the rule is explained where the session is ended — so a card has End session only when it can be used. The card being attended shows an **Attending now** brand badge in its header instead of a button-shaped chip. Inside a card the action bar stays two equal columns at every width, so action rows line up across a row of cards in both languages. Card titles are 16px / 600 links with the focus ring. On the page header, Register student is outline — the desk's primary is the search.
- **The confirm panel is the same identity block on both paths** (`StudentConfirmHeader`): an 80px round photo, the name at 18px / 600, the code (an isolated LTR run), and the Enrolled / Drop-in badge. Student-first had shown a 56px photo and the name inside a muted sentence — the weakest anti-impersonation check on the path most used for walk-ins. "Press Enter to confirm" shows from `sm` only (a phone has no Enter key).
- **Recent check-ins** are single-line rows from `sm` (photo · name and code · status · time), the code and time in `--text-secondary`, the code bidi-isolated so it stays under the name in Arabic.
- **Phones.** The page subtitle hides below `sm` so the search starts higher; the session filter is one row of four segments; the payment-method and session-picker buttons are 48px (§6: desk controls larger than the 44px floor).
- **A scan that finds nobody says what to do next** ("Search by name, or register them.").

### 14.6 Lists, and confirming a destructive verb

- **`ConfirmAction`** (`components/shared/confirm-action.tsx`) — the one confirmation for a destructive or irreversible verb on a row or a card: the trigger button, then the shared narrow `DialogShell` (§14.1a — a bottom sheet on a phone) whose title names the act and whose description states the consequence, **Keep it** (outline) and the solid destructive confirm. It posts the row's existing form action with the same hidden fields as before — the action, its rules and its result are unchanged; only a second, deliberate tap was added. The result still lands in the row (the error inline, the success as a toast). Used for: revoking a staff invitation (DES's one behaviour change), deactivating a staff member, a student or a teacher, declining an approval request, removing a holiday, removing or blocking a student from a class, and approving / paying / cancelling a settlement. Re-activating is not destructive and stays one tap. A confirmation that needs input (a void reason) stays the inline panel of §11.18.
- **Rows.** The name is the row's link; the separate "Open" button that every row also carried (a second tab stop to the same page) is gone, and a row takes the hover tint from `md`. A per-cell label is visible on a phone's card and `sr-only` from `md` (it had been `display: none`, so a screen reader heard values with no column names while the header row is `aria-hidden`). Numeric columns are end-aligned under end-aligned headers. Fixed column widths are narrow enough that the name and teacher keep their room at 768 (Sessions and Classes had squeezed them to nothing); a low-priority column joins from `lg`.
- **Counts in a list's description are plural-aware and filtered honestly**: with a search active the description counts the matches ("3 students match “Mona”"), never "0 registered at this branch".

### 14.7 Forms and dialogs (DES)

- **Nothing typed is lost on a refusal.** Every create or settings form that is uncontrolled submits through `startTransition` with the form's own `FormData` — the settings "Add" dialogs, the inline create card, the expense form and General settings joined the student, teacher, class and session dialogs (`<form action>` resets an uncontrolled form once the action returns, which had cleared a refused submit).
- **The settings "Add" dialogs are the shared `DialogShell` (narrow)**: a fixed header, the fields, and the footer's Cancel + primary — a bottom sheet on a phone. With an odd number of fields the first takes the whole row, so a lone Name is not stranded at half width and two dates pair up beneath it.
- **Someone else's details are never autofilled with yours.** Person, contact and parent fields entered by staff set `autoComplete="off"`; the same fields on a person's *own* profile (`ownProfile`) use `given-name` / `family-name` / `tel` / `email`.
- **The phone lookup is a labelled field** with a translated example and an announced answer.
- A primary submit in a column form is `sm:self-start` — `w-full sm:w-auto` alone does nothing inside `flex-col`, which had stretched "Add expense", "Create invitation" and "Create branch" across the card.
